### §3. Sealed classes and interfaces · `SEC-M07-03` (M)
- Topics: the problem (a `Shape` hierarchy where any library user can add a subclass, so no code can rely on knowing all cases; an `if/else instanceof` chain that silently misses a new subtype); `sealed`, `permits`, and the rule that every permitted subclass is `final`, `sealed` or `non-sealed` (JLS §8.1.1.2, §8.1.6); where permitted subclasses may live (the same module, or the same package in the unnamed module: JLS §8.1.6, verify the wording); omitting `permits` when all subclasses are in the same compilation unit; records and enums as implicitly final permitted subtypes; sealed interfaces; what the class file records (`PermittedSubclasses`, JVMS §4.7.31) and that the JVM enforces it when a class is defined (JVMS §5.3.5: verify; an attempt to define an unlisted subclass fails with `IncompatibleClassChangeError`); `Class.isSealed()` and `getPermittedSubclasses()` (Java 17); algebraic data types: sum types (sealed) of product types (records), and how that replaces the visitor pattern for closed hierarchies (and when the visitor still wins: open operations over a closed type vs open types); `non-sealed` as an explicit extension point; enum constants with bodies are implicitly sealed (01 §12, one sentence).
