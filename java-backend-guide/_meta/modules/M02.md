### §1. Identity and equality: `==`, `equals` and its contract · 900 words · `SEC-M02-01` (M)
- Topics: identity (`==` on references) vs logical equality (`equals`); `Object.equals` is identity; which JDK types override it (`String`, wrappers, collections, records) and which do not (arrays, `StringBuilder`); the five clauses of the contract; `equals(Object)` signature and the `equals(Point)` overload trap (→ 01 §8); null-safe `Objects.equals`; `Arrays.equals` for arrays; the String pool and `intern` stay in 06, the `Integer` cache in 01 §13.
- Key claims: the contract clauses [Doc: `Object.equals` Javadoc, Java 25]; `Object.equals` returns `this == obj` [Src: JDK 25 `java.lang.Object`]; arrays inherit `Object.equals` (R1 `M02 §1 · arrays compare by identity, Arrays.equals by content`); `StringBuilder` does not override `equals` (R1, and [Doc: `StringBuilder` Javadoc 25, verify it states `compareTo` is provided instead]); `equals(Point)` is an overload, so `HashSet.contains` misses (R1 `M02 §1 · equals(Point) is an overload and collections ignore it`) and `@Override` turns it into `compiler.err.method.does.not.override.superclass` (R2).
- Diagram: flowchart of `a.equals(b)` decision for a well-written class (same reference? → null/type check → field comparison).
- Callouts: none required (no production failure class specific to this section; §2 carries the hash-collection incidents).
- Failure modes: short: a broken `equals` surfaces as collection misbehavior (duplicates, failed `remove`), not exceptions; link §2.
- Misconceptions: "`==` compares values for objects" (true for primitives; the cache makes it look right, → 01 Q01.28); "`equals` must be overridden in every class" (only for value-like classes; entities have identity → 23).

### §2. `hashCode` and hash-based collections · 950 words · `SEC-M02-02` (M)
- Topics: the `hashCode` contract (equal ⇒ equal hash; unequal may collide; consistent while the fields used by `equals` do not change); how `HashMap` uses the hash to choose a bucket, then `equals` to choose the entry (one paragraph, internals → 04); `equals` without `hashCode`; mutable keys (mutating a field used by `hashCode` after insertion); hash quality: constant or low-entropy `hashCode` degrades lookups (treeification softens it, → 04); `Objects.hash` allocates a varargs array and boxes primitives; `31 * h + …` hand-written form; caching the hash in immutable types (`String` caches its hash lazily).
- Key claims: contract [Doc: `Object.hashCode` Javadoc, Java 25]; `HashMap` compares hash then `equals` [Src: JDK 25 `HashMap.getNode`]; R1 `M02 §2 · equals without hashCode: HashSet keeps both copies` (assert `size() == 2` is *permitted*, not guaranteed: two distinct identity hashes almost always differ, so the test asserts `contains` of a fresh equal instance is false for the identity-hash class only when the hashes differ; writer designs the assertion so it never flakes, for example by asserting the outcome conditionally on `h1 != h2` and checking that branch over many instances); R1 `M02 §2 · a mutated key is not found by get but is still in entrySet`; `Objects.hash(Object...)` is varargs and delegates to `Arrays.hashCode` [Src: JDK 25 `java.util.Objects`]; `String` caches its hash in a field [Src: JDK 25 `java.lang.String` `hash`, `hashIsZero`]; constant `hashCode` puts every key in one bucket [Src: JDK 25 `HashMap`; cost numbers only if measured, otherwise none].
- Diagram: flowchart of `map.get(k)`: `hashCode` → bucket → `equals` per entry → value; mark where a mutated key goes wrong.
- Callouts: **Production scenario: cache hit rate collapses after a key class change** (hit rate drops or memory grows; evidence: the map's size grows while lookups miss, heap histogram shows duplicate keys; fix: immutable key with consistent `equals`/`hashCode`; prevention: an `equals`/`hashCode` contract test, keys as records). Q02.08 is the drill.
- Failure modes: duplicates and misses (silent), memory growth from unreachable-by-lookup entries (a leak), lookups degrading under load with a low-entropy hash (bounded by treeification for `Comparable` keys, → 04; verify the treeify condition in `HashMap` source before stating it, or link only).
- Security: **Security:** keys derived from attacker-controlled strings in a hash map: collisions were the classic DoS; Java 8 treeification bounds it (verify against JEP 180 before stating it, else link 04).

### §3. Equality across a class hierarchy · 750 words · `SEC-M02-03` (M)
- Topics: `instanceof`-based `equals` in a subclass that adds a field breaks symmetry; the "fix" that ignores the extra field when comparing with the base breaks transitivity; `getClass()`-based `equals` keeps the contract but breaks substitutability (a subclass instance never equals a base instance: Liskov); the rule from the `Object.equals` Javadoc and JLS-independent reasoning; options: make `equals` `final` in the base with `instanceof` (subclasses add no state to equality), `getClass`, or composition (the subclass becomes a class that *has* the base value and exposes a view); records and `final` classes sidestep the problem.
- Key claims: R1 `M02 §3 · instanceof equals in a subclass with an extra field is asymmetric`, `… the symmetric patch is not transitive`, `… getClass equals rejects a subclass with no extra state`, `… composition keeps all three clauses`; records are implicitly `final` [Doc: JLS 25 §8.10]; JDK example: `java.sql.Timestamp` documents that its `equals` is not symmetric with `java.util.Date` [Doc: `Timestamp` Javadoc 25, verify the wording].
- Diagram: classDiagram `Point` ← `ColorPoint` (inheritance) vs `ColorPoint` *-- `Point` (composition).
- Failure modes: skipped except one line: asymmetric `equals` makes `list.contains` depend on which side is the argument (shown by the R1 test). Pure-language reasoning otherwise (the reviewer accepts the gap).
- Misconceptions: "`getClass` is always safer" (it breaks proxies and subclasses with no extra state; Hibernate proxies → 23); "`canEqual` solves it in Java" (a Scala idiom; it works but couples every subclass; mention only if the writer can tag it [Doc] or drop).

### §5. Immutability · 1,000 words · `SEC-M02-05` (M)
- Topics: what immutable means (state cannot change after construction, observably); the recipe: `final` class (or private constructor), `private final` fields, no setters, defensive copies in (constructor) and out (getters), no `this` escape during construction; why `final` alone is not enough (→ 01 §10); unmodifiable view (`Collections.unmodifiableList`) vs unmodifiable copy (`List.copyOf`) vs a truly immutable element type; why `String` is immutable (pool sharing, hash caching, security of class names and file paths, thread safety); thread safety: immutable objects are safe to share, and `final` field semantics give safe initialization (one paragraph, JLS §17.5, → 11); cost: copies and allocation, and when a mutable builder is the answer (→ §7).
- Key claims: R1 `M02 §5 · unmodifiable view reflects later source changes, List.copyOf does not`; R1 `M02 §5 · a constructor that does not copy leaks the caller's list`; R1 `M02 §5 · getter returning the internal list lets callers mutate`; `List.copyOf` returns the argument itself when it is already an unmodifiable list from `List.of` [Src: JDK 25 `ImmutableCollections.listCopy`, verify, else omit]; `final` field guarantee [Doc: JLS 25 §17.5]; `String` hash caching [Src: JDK 25 `String`]; `String` design reasons are "the reasons usually given" unless a Doc tag supports them.
- Diagram: flowchart: caller list → constructor (copy) → internal list → getter (unmodifiable view or copy) → caller; mark the two leak points.
- Callouts: **Production scenario: a "constant" configuration changes at run time** (one request mutates a list returned by a shared config object; evidence: the value differs between requests and a heap dump or a log shows the list grown; fix: copy in and out, `List.copyOf`; prevention: a test that mutates the returned list and expects `UnsupportedOperationException`, records with copied components). - Failure modes: aliasing bugs (above); allocation from copying on hot paths (measure first, → 09, 10); a mutable object shared across threads without safe publication (→ 11).
- Security: **Security:** copy mutable arguments *before* validating them, because the caller can change them between the check and the use (time-of-check to time-of-use) [verify a basis: the Secure Coding Guidelines for Java SE, guideline on defensive copies, or drop the tag and keep the reasoning].
