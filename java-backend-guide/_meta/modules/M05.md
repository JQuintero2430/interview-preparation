### §1. Functional interfaces and lambda expressions · `SEC-M05-01` (M)
- Topics: the problem lambdas solve (behavior as a value: a callback, a predicate, a comparator, without an anonymous-class ceremony); a functional interface is an interface with exactly one abstract method, not counting public `Object` methods, defaults or statics (JLS §9.8; the ledger premise); `@FunctionalInterface` is a compile-time check, optional; target typing: a lambda has no type of its own, it takes the type its context demands (assignment, invocation, cast, return; JLS §15.27.3); the `java.util.function` families (`Function`, `Consumer`, `Supplier`, `Predicate`, `UnaryOperator`, `BinaryOperator`, the `Bi…` forms, primitive specializations such as `IntPredicate` and `ToIntFunction`, why they exist: boxing); composition (`Function.andThen`/`compose`, `Predicate.and`/`or`/`negate`, `Predicate.not` since 11); lambda vs anonymous class: `this` means the enclosing instance, a lambda opens no new scope (redeclaring a local is an error), an anonymous class can hold state and implement any interface or class (link 01 §11, Q01.26 for the leak); pre-Java 8 interfaces that are functional (`Runnable`, `Callable`, `Comparator`); one sentence on Strategy/Command → 51.
- Key claims: [Doc: JLS 25 §9.8 (functional interfaces), §15.27 (lambda expressions), §15.27.3 (type of a lambda)]; [Doc: JEP 126]; [Src: JDK 25 `java.util.function` package-info and `FunctionalInterface` Javadoc]; [Src: JDK 25 `Predicate.not` `@since 11`]; R2 `M05 §1 · @FunctionalInterface rejects an interface with two abstract methods` (verify the key, for example `compiler.err.bad.functional.intf.anno.1`); R2 `M05 §1 · an interface with one abstract method plus equals and a default is functional`; R2 `M05 §1 · a lambda cannot redeclare a local of the enclosing method` (verify the key, for example `compiler.err.already.defined`); R1 `M05 §1 · this inside a lambda is the enclosing instance, inside an anonymous class it is the anonymous object`.
- Diagram: none required (a table: family → shape → example → primitive variants).
- Callouts: **Version notes** (Java 8 lambdas and `java.util.function`, JEP 126; Java 11 `Predicate.not`; each with its basis).
- Failure modes: skipped except one line (a lambda's runtime behavior is its body's; capture and allocation are §2, performance in streams §6); the reason goes in the LOG line.
- Misconceptions: "a functional interface can only have one method" (ledger 01-09); "`@FunctionalInterface` is what makes an interface functional"; "a lambda is an anonymous class with shorter syntax" (link §2).

### §2. How lambdas compile and capture: `invokedynamic` and effectively final · `SEC-M05-02` (M)
- Topics: what javac emits: the body becomes a private synthetic method (named `lambda$<method>$<n>` by javac convention), and the lambda expression becomes an `invokedynamic` call site whose bootstrap is `LambdaMetafactory.metafactory`; on first execution the bootstrap spins a hidden class implementing the interface (hidden classes since Java 15, JEP 371: verify in src.zip `InnerClassLambdaMetafactory`), later executions reuse the linked call site; an anonymous class instead is an ordinary `Outer$1` class file loaded like any class; capture: a lambda may use locals that are final or effectively final (JLS §4.12.4, §15.27.2), because it receives copies of their values; why the rule exists (the copy would silently diverge from a variable that changes; locals live on a stack frame that may be gone); instance fields are not copied: using one captures `this` (link Q01.26); a non-capturing lambda needs no per-evaluation state, so JDK 25 may hand back one instance (implementation behavior, JLS §15.27.4 allows either; verify in the task); the one-element-array and `AtomicInteger` workarounds and why they are a smell (shared mutable state, unsafe under §8 parallelism); side effects in lambdas: allowed by the language, forbidden by the stream contract in most places (link §4 non-interference); serializable lambdas (`$deserializeLambda$`, intersection cast `(Runnable & Serializable)`) only if verified, with a **Security:** item on deserialization (link 06).
- Key claims: [Doc: JLS 25 §4.12.4, §15.27.2, §15.27.4]; [Doc: JVMS 25 §6.5 `invokedynamic`]; [Src: JDK 25 `java.lang.invoke.LambdaMetafactory` (class Javadoc), `InnerClassLambdaMetafactory`]; [Doc: JEP 371] (verify that lambdas use hidden classes); R2 `M05 §2 · a lambda cannot capture a local that is reassigned` (verify the key, for example `compiler.err.cant.ref.non.effectively.final.var`); R3 `M05 §2 · a lambda compiles to invokedynamic bootstrapped by LambdaMetafactory` and `M05 §2 · an anonymous class compiles to its own class file` (route per §1, verify in the task); R1 `M05 §2 · a lambda reading a field sees the field's current value, a captured local keeps its value`.
- Diagram: sequenceDiagram: first execution of the call site → bootstrap `metafactory` → hidden class defined → `CallSite` linked → instance returned; second execution → linked call site → instance. "What to notice": the bootstrap runs once per call site, not once per evaluation.
- Callouts: **Version notes** (Java 8 `invokedynamic` lambdas; Java 15 hidden classes, if verified).
- Failure modes: first-call linkage cost at startup (qualitative; many distinct lambda sites in a large application; link 10 for startup profiling, no invented numbers); a lambda that captures `this` and outlives its owner (link Q01.26); stack traces with `lambda$…` frames and how to read them (verify a test that inspects `StackTraceElement` method names start with `lambda$`).

### §3. Method references · `SEC-M05-03` (M)
- Topics: four kinds (JLS §15.13): static (`Integer::parseInt`), bound instance (`prefix::concat`, `System.out::println`), unbound instance (`String::length`, where the first parameter becomes the receiver), constructor (`ArrayList::new`, array constructor `int[]::new`); how each maps onto a functional-interface signature (the unbound form adds the receiver as the first argument, so `String::compareToIgnoreCase` fits `Comparator<String>`; ledger 01-08 secondary, link Q02.11); when the receiver of a bound reference is evaluated: at the time the reference is evaluated, not when it is called, so `obj::method` with `obj == null` throws `NullPointerException` immediately while the lambda `() -> obj.method()` throws only when called (JLS §15.13.3: verify the wording); ambiguity: a method reference to an overloaded method or one that fits both a static and an unbound instance form fails to compile (for example `Integer::toString` as `Function<Integer, String>`: verify the key); when a lambda reads better than a reference.

### §4. Stream pipelines: laziness, short-circuiting and encounter order · `SEC-M05-04` (M)
- Topics: a stream is not a collection: a single-use view of a source with a pipeline of operations (package `java.util.stream` summary); source (collection, array, `Stream.of`, `iterate`, `generate`, `Files.lines` → §9, `String.chars`), intermediate operations (lazy, return a stream) and one terminal operation (eager, triggers traversal); vertical execution: each element passes through all stages before the next one starts (except across stateful barriers such as `sorted`); short-circuiting operations (`findFirst`, `anyMatch`, `limit`, `takeWhile`) make infinite sources usable; stateless vs stateful intermediate operations (`sorted`, `distinct` buffer elements); encounter order: defined by the source (`List` ordered, `HashSet` not), preserved by most operations, `unordered()` lets parallel pipelines drop it (link §8); non-interference (do not modify the source during the pipeline; link 04 §7 for CME) and statelessness of behavioral parameters; `peek` is for debugging and may not run: `count()` may skip the pipeline when it can compute the count from the source (Java 9 Javadoc change); reuse throws `IllegalStateException`; `Stream` vs `Iterator` vs reactive streams (one sentence, link 19).
- Key claims: [Doc: Java 25 API `java.util.stream` package summary (laziness, non-interference, stateless behaviors, ordering), `Stream.count` ("An implementation may choose to not execute the stream pipeline"), `Stream.peek`]; [Src: JDK 25 `AbstractPipeline` (`linkedOrConsumed`, the "stream has already been operated upon or closed" message)]; R1 `M05 §4 · stages run per element, not per stage`; R1 `M05 §4 · no terminal operation means no lambda runs`; R1 `M05 §4 · findFirst on an infinite iterate stops after the first match`; R1 `M05 §4 · count on a sized List source skips peek` (verify in the task on JDK 25 and phrase it as an observation of what the specification permits); R1 `M05 §4 · reusing a stream throws IllegalStateException`; R1 `M05 §4 · sorted buffers every element before the next stage runs`.
- Diagram: flowchart: source → filter → map → findFirst, with one element's path drawn through all stages, and a `sorted` barrier variant. "What to notice": the terminal operation pulls elements.
- Callouts: **Production scenario: an audit `peek` stops writing after a refactor to `count()`** (an audit step that used `peek` to log processed records writes nothing once the pipeline ends in `count()` over a sized source; evidence: the missing log lines against the returned count, the `Stream.count` Javadoc; fix: do the side effect in `forEach` or a mapping stage that the result depends on, or count in the terminal operation itself; prevention: no business side effects in `peek`). Must differ from every question (Q05.10 and Q05.11 are evaluation-order puzzles, not incidents). **Version notes** (Java 8 streams; Java 9 `takeWhile`, `dropWhile`, three-argument `iterate`, `ofNullable`, and the `count` change; Java 16 `toList`, `mapMulti` → §6; each from `@since` in src.zip or the Javadoc).
- Failure modes: a side effect hidden in a lazy stage that never runs; an infinite stream without a short-circuiting operation (hangs, or `OutOfMemoryError` behind `sorted`: verify that only the hang is asserted, with a bounded `limit` in the test, never a real hang); `sorted` on a large stream holding every element in memory (qualitative); mutating the source mid-pipeline (`ConcurrentModificationException`, link 04 §7).
- Misconceptions: "`peek` always runs"; "intermediate operations run when they are called"; "a stream stores its elements".

### §5. Collectors: `toMap`, `groupingBy`, `teeing` and writing your own · `SEC-M05-05` (M)

### §6. Primitive streams, `flatMap`, `mapMulti` and `reduce` vs `collect` · `SEC-M05-06` (M)
- Topics: `IntStream`, `LongStream`, `DoubleStream` and why they exist (no boxing of each element; `sum`, `average` returning `OptionalDouble`, `summaryStatistics`, `range`/`rangeClosed`); converting: `mapToInt`, `boxed`, `mapToObj`, `asLongStream`; boxing costs stated qualitatively (one `Integer` object per element outside the cache, link 01 §13 for the `Integer` cache; no invented numbers); `map` (one to one), `flatMap` (one to a stream of many), `mapMulti` (since 16: push zero or more elements to a consumer, avoids creating a stream per element; the Javadoc's two "preferable" cases: verify the wording); `reduce` (immutable reduction: identity, accumulator, combiner; the identity must be an identity for the combiner and the operation associative, Javadoc) vs `collect` (mutable reduction into a container); the classic bug of `reduce` into a mutable `ArrayList` (works sequentially by accident, broken in parallel; link §8); `Stream.iterate`, `generate`, `takeWhile`, `dropWhile` placement (or keep them in §4: decide in the task and say where).

### §7. Stream gatherers · `SEC-M05-07` (M)
- Topics: the gap: intermediate operations were a fixed set; anything stateful beyond `distinct`/`sorted`/`limit` (fixed windows, sliding windows, running totals, deduplicating consecutive elements) needed a collector plus post-processing or a custom `Spliterator`; `Stream.gather(Gatherer)` (since 24, JEP 485 final; JEP 461 and 473 previews in 22 and 23); a `Gatherer<T, A, R>` has an initializer (state), an integrator (per element; returns `false` to short-circuit), an optional combiner (parallel), and a finisher (flush at the end); `Gatherer.of` and `Gatherer.ofSequential`; built-ins in `Gatherers`: `windowFixed`, `windowSliding`, `fold`, `scan`, `mapConcurrent` (runs a function concurrently with a bound, on virtual threads: verify the Javadoc wording, link 14); chaining with `andThen`; gatherer vs collector (intermediate vs terminal) vs `flatMap`/`mapMulti` (stateless one-to-many).
- Key claims: [Doc: JEP 485], [Doc: JEP 461], [Doc: JEP 473]; [Src: JDK 25 `Gatherer`, `Gatherers` (`windowFixed`, `windowSliding`, `fold`, `scan`, `mapConcurrent`), `Stream.gather` `@since 24`]; R1 `M05 §7 · windowFixed groups elements and keeps a short last window`; R1 `M05 §7 · windowSliding produces overlapping windows`; R1 `M05 §7 · scan emits running totals`; R1 `M05 §7 · an integrator returning false short-circuits an infinite stream`; R1 `M05 §7 · mapConcurrent keeps encounter order` (verify in the Javadoc first; assert only order and results, never concurrency level or timing).

- Callouts: **Version notes** ([Final since Java 24, JEP 485] with the two preview JEPs; code compiled with `--enable-preview` on 22 or 23 must be rebuilt on 24+ only if the API changed between previews: verify against JEP 485 "changes" text or drop the clause).
- Failure modes: a gatherer whose state is shared across parallel chunks without a combiner (it then runs sequentially: verify what `ofSequential`/no combiner means in the Javadoc); unbounded windows holding memory; `mapConcurrent` with a blocking function (bounded by its `maxConcurrency` argument; qualitative).

### §8. Parallel streams and the common `ForkJoinPool` · `SEC-M05-08` (M)
- Topics: `parallel()`/`parallelStream()` splits the source with its `Spliterator` (`trySplit`, characteristics `SIZED`, `SUBSIZED`, `ORDERED`), processes chunks on the common `ForkJoinPool`, and combines results; the calling thread also takes part (verify in the task by observing thread names as a permitted set); the common pool's parallelism defaults to `availableProcessors() - 1` (at least 1), configurable with `java.util.concurrent.ForkJoinPool.common.parallelism` (src.zip `ForkJoinPool` L3056/L3081); sources that split well (`ArrayList`, arrays, `IntStream.range`) vs badly (`LinkedList`, `Stream.iterate`, `BufferedReader.lines`: verify each in the spliterator Javadoc or source); ordering costs (`findFirst`, `limit`, `forEachOrdered`, `sorted` vs `findAny`, `unordered()`); when it helps: large data, CPU-bound and independent per element work, cheap combine; when it hurts: small data, blocking I/O inside the pipeline (it occupies common-pool workers that every other parallel stream and `CompletableFuture.*Async` default executor use: verify the default executor claim in `CompletableFuture` Javadoc), shared mutable state, stateful lambdas; running a parallel stream inside a custom `ForkJoinPool` via `submit` works today but is an implementation detail (verify whether the Javadoc says anything; otherwise call it undocumented and discourage); `parallel()` and `sequential()` apply to the whole pipeline (the last call wins); work stealing and the pool's internals → 13; virtual threads do not make CPU-bound work faster → 14 (one sentence).
- Key claims: [Doc: Java 25 API `java.util.stream` package summary "Parallelism", `BaseStream.parallel`, `Spliterator` characteristics, `ForkJoinPool` (common pool, system property), `CompletableFuture` (default async executor)]; [Src: JDK 25 `ForkJoinPool` common-pool parallelism computation]; R1 `M05 §8 · a parallel sum equals the sequential sum`; R1 `M05 §8 · parallel work runs on the caller and common-pool workers` (permitted set of thread names); R1 `M05 §8 · forEach in parallel may lose encounter order and forEachOrdered keeps it` (assert only that `forEachOrdered` gives encounter order and that `forEach` gives the same multiset); R1 `M05 §8 · the last parallel or sequential call decides the whole pipeline` (observe `isParallel()`).

- Security: none expected; the reviewer confirms (a request-size bound belongs to the endpoint, link 18 only if a sentence needs it).
- Misconceptions: "`parallelStream()` is always faster"; "each parallel stream gets its own threads"; "`forEach` keeps order in parallel".

### §9. Checked exceptions and resources in lambdas and streams · `SEC-M05-09` (M)
- Topics: the standard functional interfaces declare no checked exceptions, so a lambda body that throws `IOException` does not compile as a `Function` (JLS §11.2.3, §15.27.3: verify the key, for example `compiler.err.unreported.exception.need.to.catch.or.throw`); workarounds, ranked: (1) catch and wrap in an unchecked exception that keeps the cause (`UncheckedIOException` for I/O), (2) a project functional interface that declares `throws Exception` plus an adapter method, (3) return a result value per element (a small sealed `Result` or a record with the value or the error) and decide after the pipeline, (4) "sneaky throw" via generic exception-type inference (works, hides a checked exception from the compiler, discouraged); never swallowing (log and continue) inside a lambda (Q05.27); how an unchecked exception propagates out of a terminal operation (the stack trace shows the pipeline frames; in parallel, which element's exception surfaces is not specified: verify the Javadoc wording, assert only the exception type); I/O-backed streams hold resources: `Files.lines`, `Files.list`, `Files.walk` must be closed, `BaseStream` is `AutoCloseable`, use try-with-resources (Javadoc "must be used within a try-with-resources statement"); `onClose` handlers; exception basics → 06.
- Key claims: [Doc: JLS 25 §11.2.3]; [Doc: Java 25 API `java.io.UncheckedIOException`, `java.nio.file.Files.lines` (the try-with-resources sentence and `UncheckedIOException` on read errors), `BaseStream.close`, `BaseStream.onClose`]; R2 `M05 §9 · a lambda that throws IOException does not compile as a Function` (verify the key); R1 `M05 §9 · a wrapped IOException surfaces with its cause`; R1 `M05 §9 · onClose runs when a try-with-resources closes the stream`; R1 `M05 §9 · a Result-per-element pipeline keeps every failure` (lab files in a `@TempDir`); "sneaky throw" compiles and throws the checked exception at run time: R1, or drop it from the text (verify in the task).

### §10. `Optional`: a return type for maybe-absent results · `SEC-M05-10` (M)
- Topics: the problem: `null` returns that callers forget to check; `Optional<T>` is "intended for use as a method return type where there is a clear need to represent 'no result'" (Javadoc API note: verify the quote) and is value-based (link 02 §8, Q02.22: no `==`, no `synchronized`); creation (`of` rejects `null`, `ofNullable`, `empty`); consuming: `orElse` (argument evaluated eagerly, always), `orElseGet` (supplier, lazy), `orElseThrow()` (since 10, the preferred spelling of `get()`), `orElseThrow(Supplier)`, `ifPresent`, `ifPresentOrElse` (9), `isEmpty` (11); transforming: `map` (a `null` result becomes empty), `flatMap` (for a function that already returns `Optional`), `filter`, `or` (9, a lazily supplied alternative `Optional`), `stream` (9, for `flatMap(Optional::stream)` over a stream of optionals); primitive `OptionalInt`/`OptionalLong`/`OptionalDouble`; anti-patterns: fields (not `Serializable`: verify), method parameters, `Optional<List<T>>` (return an empty list), `isPresent()` followed by `get()`, `Optional.of(maybeNull)`, `Optional` as a JPA entity attribute or JSON DTO field (one sentence each, Spring/Jackson side → 23 and 18 links only); `Optional` from stream terminals (`findFirst`, `max`, `reduce` without identity).
- Key claims: [Doc: Java 25 API `Optional` (class API note, each method's `@since`: `or`/`stream`/`ifPresentOrElse` 9, `orElseThrow()` 10, `isEmpty` 11 from src.zip), `ValueBased`]; R1 `M05 §10 · orElse evaluates its argument when a value is present and orElseGet does not`; R1 `M05 §10 · map with a null-returning function gives an empty Optional`; R1 `M05 §10 · flatMap avoids Optional<Optional<T>>`; R1 `M05 §10 · or supplies an alternative only when empty`; R1 `M05 §10 · Optional.of(null) throws NullPointerException`; R1 `M05 §10 · Optional is not Serializable` (`assertThat(Serializable.class.isAssignableFrom(Optional.class)).isFalse()`).
- Diagram: none (a table: method → when the argument runs → result when empty → since).
- Callouts: **Version notes** (Java 8 `Optional`; 9 `or`, `stream`, `ifPresentOrElse`; 10 `orElseThrow()`; 11 `isEmpty`; each from `@since`).

- Misconceptions: "`Optional` removes `NullPointerException`s" (it documents absence for return values; the reference itself can be `null`); "`orElse` is lazy"; "use `Optional` everywhere instead of `null`".
