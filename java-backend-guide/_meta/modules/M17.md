### §1. Local transactions on a JDBC connection · 600 words · `SEC-M17-01` (M, needs: docker)
- Topics: atomicity across statements; auto-commit default; `setAutoCommit(false)`, `commit`, `rollback`; one transaction = one connection.
- Key claims: a new JDBC connection is in auto-commit mode [Doc: `java.sql.Connection` Javadoc, Java 25]; in the lab, the second insert's failure leaves the first row committed under auto-commit and absent with manual commit (R2, `M17 §1 · auto-commit commits each statement`, `M17 §1 · rollback undoes both inserts`).
- Diagram: none needed (sequence optional). Creates `PostgresTestBase` and `schema.sql`.
- Delegates: pooling, `DataSource` → 22.

### §2. Spring's transaction abstraction · 1,120 words (900 + 220 moved from §11 and §13 by SEC-M17-02) · `SEC-M17-02` (M)
- Topics: `PlatformTransactionManager` (`getTransaction`, `commit`, `rollback`), `TransactionDefinition`, `TransactionStatus`; `DataSourceTransactionManager` vs `JpaTransactionManager` vs `JtaTransactionManager` (one line); `TransactionSynchronizationManager` binds the connection holder to the thread; why code using a raw `DataSource` outside `DataSourceUtils` runs outside the transaction (→ Q17.03); `ReactiveTransactionManager` exists for reactive stacks → 19.
- Key claims: [Src: spring-tx 7.0.10 `AbstractPlatformTransactionManager.getTransaction`, `TransactionSynchronizationManager` (ThreadLocal resources)]; Boot auto-configures a `JpaTransactionManager` when JPA is present [Src: spring-boot 4.1.2 auto-configuration class, name verified in the task]; R1 test `M17 §2 · getTransaction/commit sequence`.
- Diagram: flowchart of manager → resource holder → thread.
- Creates `RecordingTransactionManager` (R1). Q17.03's DB demonstration is part of QB-M17-01.

### §3. `@Transactional` through the proxy · 1,000 words · `SEC-M17-03` (M)
- Topics: `@EnableTransactionManagement` / Boot auto-configuration; `BeanFactoryTransactionAttributeSourceAdvisor`, `TransactionInterceptor`, `AnnotationTransactionAttributeSource`; JDK vs class-based proxies (Boot default class-based, `spring.aop.proxy-target-class`), mechanics → 16; where the annotation may go (class, method, interface) and precedence; `jakarta.transaction.Transactional` also honoured; diagnostics: `TransactionSynchronizationManager.isActualTransactionActive()`, TRACE logging of `org.springframework.transaction`.
- Key claims: [Src: spring-tx 7.0.10 `TransactionAspectSupport.invokeWithinTransaction`], R1 `M17 §3 · proxied call begins and commits`, `M17 §3 · isActualTransactionActive inside and outside`.
- Diagram: sequence caller → proxy → interceptor → manager → target.
- Callouts: **Framework vs language** (a Java method call has no transaction; the proxy is Spring's); **Version notes** (Spring Framework 6.0: class-based proxies advise protected and package-visible methods, verify; `javax` → `jakarta` in Boot 3).

### §4. When `@Transactional` silently does nothing · 820 words (800 + 20 moved from §13 by SEC-M17-04) · `SEC-M17-04` (M)
- Topics: self-invocation; `private`, `final`, `static` methods; a bean created with `new` or not a Spring bean; wrong or missing transaction manager (qualifier); exception caught inside; fixes (extract a bean, self-injection, `TransactionTemplate`, AspectJ mode → 16).
- Key claims: R1 tests per case (`M17 §4 · self-invocation runs without a transaction`, `M17 §4 · final method is not advised`, `M17 §4 · private method is not advised`, `M17 §4 · protected method on class proxy is advised`).
- Callout: **Production scenario: half an order saved, no error** (framing differs from Q17.08: the callout is a refactoring that moved a call into the same class; Q17.08 is a caught exception plus self-invocation triage).

### §5. Rollback rules and rollback-only · 800 words · `SEC-M17-05` (M)
- Topics: default rollback on `RuntimeException` and `Error`, commit on checked exceptions; `rollbackFor`, `noRollbackFor`, rollback rules by class name pattern; `setRollbackOnly()`; inner `REQUIRED` failure marks the shared transaction rollback-only → `UnexpectedRollbackException` at outer commit.
- Key claims: [Src: spring-tx 7.0.10 `DefaultTransactionAttribute.rollbackOn`, `RuleBasedTransactionAttribute`], R1 tests `M17 §5 · checked exception commits`, `M17 §5 · rollbackFor rolls back`, `M17 §5 · rollback-only surfaces UnexpectedRollbackException`.
- Diagram: state machine active → rollback-only → rolled back.
- Callout: **Version notes** only if a default changed (check spring-tx 6.x/7.0 release notes; omit otherwise).

### §6. Propagation · 1,100 words · `SEC-M17-06` (L, needs: docker)
- Topics: the seven behaviours; suspend/resume; `NESTED` via JDBC savepoints (`DataSourceTransactionManager`; `JpaTransactionManager` support limits, verify); `REQUIRES_NEW` takes a second connection; pool deadlock when every thread holds one connection and waits for a second.
- Key claims: R1 event sequences for each propagation (`M17 §6 · REQUIRES_NEW suspends outer`, `M17 §6 · NESTED creates savepoint`, `M17 §6 · MANDATORY without transaction throws`); R2 `M17 §6 · REQUIRES_NEW row survives outer rollback`, `M17 §6 · pool of N with N concurrent REQUIRES_NEW callers times out` (bounded HikariCP `connectionTimeout`, asserts bounds, not exact times).
- Diagram: timeline of outer/inner transactions and connections.
- Callout: **Production scenario: every request hangs for 30 s after adding an audit log** (the pool deadlock; distinct from Q17.15, which is the interviewer drill with given numbers: keep the callout short and link Q17.15).

### §7. Isolation levels and anomalies · 1,100 words · `SEC-M17-07` (L, needs: docker)
- Topics: dirty read, non-repeatable read, phantom, lost update, write skew; SQL standard table vs PostgreSQL (READ UNCOMMITTED behaves as READ COMMITTED; REPEATABLE READ is snapshot isolation; SERIALIZABLE is SSI with serialization failures, SQLSTATE 40001); `Isolation.DEFAULT`; MVCC one sentence → 26.
- Key claims: [Doc: PostgreSQL 18 §13.2 Transaction Isolation]; R2 permitted-outcome tests: `M17 §7 · read committed allows non-repeatable read`, `M17 §7 · repeatable read prevents it`, `M17 §7 · serializable rejects write skew (one commits, the other fails 40001)`.
- Trade-off table: level × anomalies prevented × cost (qualitative cells unless verified).
- Callout: **Framework vs language** not needed; **Production scenario** optional (lost update lives in §10).

### §8. Read-only, timeouts and programmatic transactions · 800 words · `SEC-M17-08` (M, needs: docker)
- Topics: `readOnly` → `Connection.setReadOnly` hint and Hibernate flush mode `MANUAL` / read-only session (verify exact behaviour in spring-orm 7.0.10 `HibernateJpaDialect.beginTransaction`); `timeout` (when it is checked, what it bounds; verify against `ResourceHolderSupport` / JPA query timeout); transaction names; `TransactionTemplate`, `TransactionCallback`, `executeWithoutResult`; when programmatic wins (fine-grained boundaries, loops, self-invocation-free code).
- Key claims: R2 `M17 §8 · readOnly skips flush of a dirty entity` (→ Q17.21), `M17 §8 · timeout aborts a long statement` (bounds); R1 `M17 §8 · TransactionTemplate commits and rolls back`.
- Callout: **Version notes** if read-only handling changed in Spring 5.1 / 6.x (verify; omit if not).

### §9. Transactions and the JPA persistence context · 500 words · `SEC-M17-09` (M, needs: docker)
- Topics: the persistence context is bound to the transaction; flush before commit and before queries (`FlushModeType.AUTO`); dirty checking; what `JpaTransactionManager` does vs `DataSourceTransactionManager`. Internals → 23, performance → 24.
- Key claims: R2 `M17 §9 · managed entity change is flushed at commit without save()`; [Doc: Jakarta Persistence 3.2 flush mode].
- Callout: **Framework vs language** (JDBC vs JPA vs Hibernate vs Spring layers).

### §10. Optimistic and pessimistic locking, retries and deadlocks · 1,000 words · `SEC-M17-10` (L, needs: docker)
- Topics: lost update; `@Version` (`UPDATE … WHERE version = ?`, `OptimisticLockException` / Spring `ObjectOptimisticLockingFailureException`); `PESSIMISTIC_WRITE` → `SELECT … FOR UPDATE`; deadlock detection in PostgreSQL (`deadlock_timeout`, SQLSTATE 40P01); retry the whole transaction, outside the proxy, bounded (→ 42 for backoff/jitter); "switch to pessimistic" changes the failure mode. Applied JPA locking → 24.
- Key claims: R2 `M17 §10 · concurrent updates with @Version: exactly one commits`, `M17 §10 · FOR UPDATE serialises the second writer`, `M17 §10 · opposite lock order: one transaction fails with 40P01`; [Doc: PostgreSQL 18 explicit locking, `deadlock_timeout`].
- Trade-off table: optimistic vs pessimistic on contention, connection holding, failure mode, retry need.
- Callout: **Production scenario: stock goes negative under a flash sale** (lost update).

### §11. Side effects after commit: transaction-bound events · 690 words (110 moved to §2) · `SEC-M17-11` (M)
- Topics: `TransactionSynchronization` (`beforeCommit`, `afterCommit`, `afterCompletion`); `@TransactionalEventListener` phases (`BEFORE_COMMIT`, `AFTER_COMMIT` default, `AFTER_ROLLBACK`, `AFTER_COMPLETION`), `fallbackExecution`; what happens to writes in an `AFTER_COMMIT` listener (verify: needs `REQUIRES_NEW`); the dual-write problem and the outbox → 43; Kafka transactions → 31.
- Key claims: R1 `M17 §11 · AFTER_COMMIT listener not called on rollback`, `M17 §11 · no transaction and no fallbackExecution: listener not called`; [Src: spring-tx 7.0.10 `TransactionalApplicationListenerMethodAdapter`].
- Diagram: sequence commit → synchronization callbacks → listener.
- Security item: events carrying personal data must not be logged whole.

### §12. Transactions across threads · 530 words (500 + 30 moved from §14 by SEC-M17-12) · `SEC-M17-12` (M)
- Topics: thread-bound resources do not follow `@Async`, `CompletableFuture`, executors or virtual threads; the async work runs in its own transaction or none, and may not see uncommitted rows; ordering of `@Async` and `@Transactional` on one method.
- Key claims: R1 `M17 §12 · work on another thread sees no active transaction` (latch-coordinated); [Src: `TransactionSynchronizationManager` ThreadLocals].
- Callout: **Framework vs language** (Spring executors vs JDK executors and virtual threads; ThreadLocal scope is the JVM's).

### §13. Long transactions in production · 670 words (110 moved to §2, 20 to §4) · `SEC-M17-13` (M, needs: docker)
- Topics: holding a connection during network I/O; HikariCP `connectionTimeout`, `maximumPoolSize` (defaults with a basis tag: HikariCP 7.0.2 source or Boot docs); lock waits and `lock_timeout`; retries that duplicate records ("no response" ≠ "no effect"); check-then-insert race; unique constraints and `INSERT … ON CONFLICT` (→ 26); idempotency keys (→ 33, 43); observing it: `hikaricp_connections_pending`, `pg_stat_activity` `idle in transaction`, `idle_in_transaction_session_timeout`.
- Key claims: R2 `M17 §13 · slow call inside transaction exhausts a small pool`, `M17 §13 · unique constraint turns duplicate retry into a constraint violation`; [Doc: PostgreSQL 18 runtime config], [Src: HikariCP 7.0.2 `HikariConfig` defaults].
- Callout: **Production scenario: lock waits pile up behind one idle-in-transaction session** (distinct from Q17.30, which is pool exhaustion with an idle database).
- Security item: idempotency keys scoped per client, so one client cannot replay another's request.

### §14. Testing transactional code · 670 words (30 moved to §12) · `SEC-M17-14` (M, needs: docker)
- Topics: Spring TestContext `@Transactional` tests roll back by default (`@Commit`, `@Rollback(false)`); what that hides (no flush → no constraint violation, lazy loading works, `AFTER_COMMIT` listeners never run, `REQUIRES_NEW` commits leak); Testcontainers PostgreSQL with `@ServiceConnection`; asserting anomalies with barriers and permitted outcomes.
- Key claims: R2 `M17 §14 · rolled-back test never runs AFTER_COMMIT listener`, `M17 §14 · constraint violation appears only on flush`; [Doc: Spring Framework 7.0 testing reference, transaction management].
- Link: `../angular-fullstack-guide/modules/30-e2e-and-testing-strategy.md` mentions rolling-back tests from the frontend side (Connections, not here).
