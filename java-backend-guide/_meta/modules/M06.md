### §1. The exception hierarchy: `Throwable`, `Error`, checked and unchecked · `SEC-M06-01` (M)
- Topics: the problem (error codes returned and ignored; a failure detected deep in the stack that the caller cannot miss); `Throwable` as the root of everything `throw` and `catch` accept (JLS §11.1.1); `Error` ("serious problems that a reasonable application should not try to catch": verify the Javadoc wording) vs `Exception`; `RuntimeException` and `Error` are the unchecked classes, everything else checked (JLS §11.1.1); the catch-or-declare rule (JLS §11.2) and what the compiler checks; `throw` takes any `Throwable` expression and `throws` lists checked types (unchecked ones allowed, for documentation); exceptions the JVM raises itself (`NullPointerException`, `ArithmeticException`, `ArrayIndexOutOfBoundsException`, `ClassCastException`, `NegativeArraySizeException`, `ArrayStoreException`, `OutOfMemoryError`, `StackOverflowError`: verify the list against JLS §11.1.3 and JVMS §2.10, name only what they list); what handling buys (separate error path, typed handlers, propagation up the call stack until a matching `catch`, then the thread's uncaught handler → §5); the override rule: an overriding method may not declare broader checked exceptions (JLS §8.4.8.3); when to use checked vs unchecked (recoverable by the immediate caller vs programming errors and unrecoverable conditions; the JDK's own split, and why most frameworks, Spring's `DataAccessException` among them, chose unchecked: one sentence, link 17/22); helpful `NullPointerException` messages since 14 (JEP 358).
- Key claims: [Doc: JLS 25 §11.1, §11.1.1, §11.1.3, §11.2, §8.4.8.3]; [Doc: Java 25 API `Throwable`, `Error`, `Exception`, `RuntimeException`]; [Doc: JEP 358]; R2 `M06 §1 · an unreported checked exception does not compile` (verify the key, for example `compiler.err.unreported.exception.need.to.catch.or.throw`); R2 `M06 §1 · an override that adds a checked exception does not compile` (verify the key); R1 `M06 §1 · an unchecked exception propagates through methods that do not declare it`; R1 `M06 §1 · a helpful NullPointerException message names the null expression` (assert the message contains the variable or method name, as JEP 358 specifies; verify the exact phrasing in a test, assert only a substring).

### §2. `try`, `catch` and `finally`: control flow and compile-time rules · `SEC-M06-02` (M)
- Topics: how a `try` statement completes (JLS §14.20.1, §14.20.2: "completes abruptly" and its reasons); catch selection: the first `catch` whose type matches, in order, so a subclass after its superclass is a compile error; `try` needs at least one `catch` or `finally` (or resources → §3); nothing may sit between `try`, `catch` and `finally` (grammar); nested `try`; an exception with no matching `catch` propagates after `finally` runs; `finally` runs on normal completion, on a caught or uncaught exception, on `return`, `break` and `continue`; a `return` in `try` evaluates the value first, then runs `finally` (so changing the variable in `finally` does not change a returned primitive, but mutating a returned object does); a `return` or `throw` in `finally` replaces the pending result or exception (the lost-exception trap); when `finally` does not run: `System.exit`/`Runtime.halt` (verify `exit` runs shutdown hooks and `finally` blocks do not run: JLS or `Runtime.exit` Javadoc), the JVM crashing, the thread never finishing the `try` (infinite loop or deadlock), daemon threads at JVM exit (verify in `Thread` Javadoc); multi-catch (Java 7): `catch (A | B e)` with `e` implicitly final and alternatives that must not be subclasses of each other; precise rethrow: rethrowing a `final` or effectively final catch parameter declares only the checked types the `try` can throw (JLS §11.2.2); a statement after `throw` is unreachable (JLS §14.22); catching a checked exception the `try` cannot throw is an error, while `catch (Exception e)` is always allowed (JLS §11.2.3).
- Key claims: [Doc: JLS 25 §14.20, §14.20.1, §14.20.2, §11.2.2, §11.2.3, §14.22]; [Doc: Java 25 API `Runtime.exit`, `Runtime.halt`, `Thread` (daemon threads)]; R1 `M06 §2 · finally runs after return and before the caller sees the value`; R1 `M06 §2 · a return in finally discards the exception from try`; R1 `M06 §2 · a returned int is not changed by finally, a returned list is` ; R1 `M06 §2 · System.exit inside try skips finally` (run in a child JVM through `ProcessBuilder` with the current `java` binary, as 01's `LaunchProtocolTest` does, stripping `JAVA_TOOL_OPTIONS`/`_JAVA_OPTIONS`/`JDK_JAVA_OPTIONS`; verify in the task, or keep the claim at Doc level); R2 `M06 §2 · a catch for a subclass after its superclass does not compile`, `M06 §2 · catching a checked exception the try cannot throw does not compile`, `M06 §2 · a statement after throw is unreachable`, `M06 §2 · a multi-catch parameter cannot be assigned`, `M06 §2 · multi-catch alternatives may not be related by subclassing` (each key verified in the task); R2 `M06 §2 · precise rethrow lets a method declare only IOException after catch (Exception e)`.
- Diagram: flowchart of `try` → (normal | exception matched | exception unmatched) → `finally` → (continue | return | propagate), with the "`finally` completes abruptly" branch replacing the outcome. "What to notice": `finally` sees every exit path and can overwrite it.
- Callouts: **Version notes** (Java 7 multi-catch and precise rethrow, JEP 213 is 9's Coin follow-up: verify which JEP or JSR 334 introduced Java 7's forms and cite that; Java 9 effectively final resources → §3).
- Failure modes: an exception lost because `finally` threw or returned (Q06.08 is the incident); cleanup code in `finally` that itself fails; `System.exit` in library code (skips caller cleanup, kills the container's other work).
- Misconceptions: "`finally` always runs" (exit, halt, crash, infinite loop); "a `return` in `finally` is harmless"; "the catch order does not matter as long as each type appears once".

### §3. try-with-resources, suppressed exceptions and chaining · `SEC-M06-03` (M)
