### §1. Why generics: compile-time safety and raw types · 800 words · `SEC-M03-01` (M)
- Topics: the pre-Java-5 collection (`List` of `Object`, casts at every read, the `ClassCastException` far from the bad `add`); what a type argument buys (the check moves to compile time, casts are inserted by the compiler); raw types: what they are (JLS §4.8), why they still compile (migration compatibility), the `rawtypes` and `unchecked` lint warnings and what each means; `@SuppressWarnings("unchecked")` scoped to one declaration with a comment that proves safety; `Collections.checkedList` as the diagnostic that moves the failure back to the bad `add`.
- Key claims: [Doc: JLS 25 §4.8 raw types, including the warning on unchecked calls through a raw type]; R2 `M03 §1 · a raw List accepts any element and warns under -Xlint:rawtypes,unchecked` (assert the warning keys; verify the exact keys in the task, for example `compiler.warn.raw.class.use` and `compiler.warn.unchecked.call.mbr.of.raw.type`); R1 `M03 §1 · a raw-typed add makes the ClassCastException appear at the typed read`; R1 `M03 §1 · Collections.checkedList throws at the bad add`; [Src: JDK 25 `java.util.Collections.CheckedCollection.typeCheck`].
- Diagram: sequenceDiagram: raw `add(Integer)` → typed `get` → compiler-inserted `checkcast` → `ClassCastException`; with `checkedList` the exception moves to `add`.
- Callouts: **Version notes** (Java 5: generics, JSR 14; Java 7: diamond; Java 10: `var`; Java 25: unchanged) with markers where a JEP exists (verify JEP 286 for `var`; diamond was Project Coin, JSR 334: verify or name without a tag).
- Failure modes: the delayed `ClassCastException` (above); legacy APIs that return raw types (link Q03.03); a `@SuppressWarnings` at class level that hides a new warning.
- Misconceptions: "raw `List` and `List<Object>` are the same" (→ Q03.12); "generics have a run-time cost" (no: erasure, casts only).

### §2. Generic types, generic methods and type inference · 900 words · `SEC-M03-02` (M)
- Topics: declaring type parameters on a class or interface (`Box<T>`) vs on a method (`static <T> List<T> listOf(T…)`); who chooses `T` (the declaration site's user vs each call); naming conventions (`T`, `E`, `K`, `V`, `R`); inference: the diamond, target typing (the assignment or argument type drives inference, JLS §18), explicit type witnesses (`Collections.<String>emptyList()`), `var` with a diamond infers `ArrayList<Object>`; generic constructors (rare, one line); the `<T> T get(String key)` signature as an unchecked cast hidden from the caller.
- Key claims: [Doc: JLS 25 §8.1.2 generic classes, §8.4.4 generic methods, §15.9.1 diamond, §18 type inference]; R2 `M03 §2 · var with a diamond infers ArrayList<Object>` (a `String s = list.get(0)` after `var list = new ArrayList<>()` fails with an incompatible-types key; verify the key); R1 `M03 §2 · a <T> T getter throws ClassCastException at the caller's assignment`; R2 `M03 §2 · a type witness selects T where inference cannot`.
- Diagram: none (a short table: declaration site, who chooses `T`, example).
- Failure modes: skipped except one line: the `<T> T` getter moves the `ClassCastException` to the call site (Q03.06). Pure-language otherwise.
- Misconceptions: "the diamond means raw type" (it means "infer"); "`var` makes code dynamically typed".

### §3. Bounded type parameters · 750 words · `SEC-M03-03` (M)
- Topics: upper bounds (`<T extends Number>`) and what they let the body call; multiple bounds (`<T extends Number & Comparable<T>>`: one class first, then interfaces); the erasure of a bounded type variable is its leftmost bound (link §5); recursive bounds (`<T extends Comparable<T>>`, `Enum<E extends Enum<E>>`); why `Comparable<? super T>` is the robust form (`LocalDate` implements `Comparable<ChronoLocalDate>`, `java.sql.Timestamp` inherits `Comparable<Date>`); no lower bounds on type parameters (`<T super X>` does not exist).
- Key claims: [Doc: JLS 25 §4.4 type variables and bounds]; [Doc: JLS 25 §4.6 erasure of a type variable is the erasure of its leftmost bound]; R3 `M03 §3 · a type variable's bounds are visible by reflection` (`TypeVariable.getBounds`); R2 `M03 §3 · max(List<LocalDate>) fails with <T extends Comparable<T>> and compiles with Comparable<? super T>`; [Src: JDK 25 `java.time.LocalDate` implements `ChronoLocalDate`, which extends `Comparable<ChronoLocalDate>`, verify]; R2 `M03 §3 · a class bound after an interface bound does not compile` (verify the key).
- Diagram: none.
- Failure modes: skipped (pure type checking, STYLE-GUIDE §2.2 item 5 example).
- Misconceptions: "`extends` in a bound means subclass only" (it covers interfaces too); "`Comparable<T>` is enough for every comparable type".

### §4. Wildcards, PECS and variance · 1,000 words · `SEC-M03-04` (M)
- Topics: invariance (`List<Integer>` is not a `List<Number>`) and why (a write would break the type); array covariance and its run-time check (`ArrayStoreException`); `? extends T` (read as `T`, cannot add except `null`), `? super T` (add `T`, read as `Object`), `?` (read as `Object`); PECS ("producer extends, consumer super", Bloch) with `Collections.copy(List<? super T>, List<? extends T>)` and `Collections.addAll`; wildcard capture and the private helper method idiom; wildcards in return types (avoid: they leak into callers); `List<?>` vs `List<Object>` vs raw `List`.
- Key claims: [Doc: JLS 25 §4.5.1 type arguments and wildcards, §4.10.2 subtyping among parameterized types, §10.5 array store exception]; R1 `M03 §4 · storing an Integer through an Object[] view of a String[] throws ArrayStoreException`; R2 `M03 §4 · List<Integer> is not assignable to List<Number>`; R2 `M03 §4 · add on List<? extends Number> does not compile` (verify the key); R1 `M03 §4 · a List<? super Integer> accepts Integers and reads Objects`; R2 `M03 §4 · a capture helper makes swap(List<?>) compile`; [Src: JDK 25 `java.util.Collections.copy` signature]; PECS attributed to *Effective Java* (name the book, no page claim).
- Diagram: flowchart (or class-style diagram) of the subtyping lattice: `List<Integer>` → `List<? extends Integer>` → `List<? extends Number>` → `List<?>`, and `List<Number>` → `List<? super Integer>`.
- Callouts: none required (the production scenario is Q03.13).
- Failure modes: one paragraph: `ArrayStoreException` is the run-time cost of covariant arrays; an over-tight API signature forces callers to copy collections (Q03.13).
- Misconceptions: "`List<? extends Number>` is read-only" (`null` can be added, and `remove`/`clear` still work); "`? super` is for reading".

### §5. Type erasure and bridge methods · 1,000 words · `SEC-M03-05` (M)
- Topics: what erasure does (type parameters replaced by their leftmost bound, casts inserted, JLS §4.6); what remains in the class file (the `Signature` attribute: declared generic types of classes, fields and methods, readable by reflection; not the type arguments of an object at run time); `getClass()` of `ArrayList<String>` and `ArrayList<Integer>`; `instanceof List<String>` is an error, `instanceof List<?>` is fine, and pattern matching allows `instanceof ArrayList<String>` when the static type is already `List<String>` (verify JLS 25 §15.20.2 reifiability rule for patterns in the task); bridge methods: why javac generates them (overriding after erasure, covariant returns), `Method.isBridge`, `isSynthetic`; overloads that clash after erasure (`name clash`); static members are shared across all parameterizations; why `T.class` and `new T()` do not exist.
- Key claims: [Doc: JLS 25 §4.6, §8.4.2 (override-equivalent signatures), §15.20.2]; [Doc: JVMS 25 §4.7.9 `Signature` attribute]; R1 `M03 §5 · ArrayList<String> and ArrayList<Integer> have the same runtime class`; R2 `M03 §5 · instanceof List<String> does not compile, instanceof List<?> does` (verify the key); R3 `M03 §5 · a Comparable<Money> implementation has a bridge compareTo(Object)`; R1 `M03 §5 · the bridge method casts, so a raw call with the wrong type throws ClassCastException`; R2 `M03 §5 · process(List<Order>) and process(List<Invoice>) clash after erasure` (verify the key, for example `compiler.err.name.clash.same.erasure`); R3 `M03 §5 · a field's generic type survives in the Signature attribute`.
- Diagram: flowchart: source `compareTo(Money)` → javac → class file with `compareTo(Money)` and bridge `compareTo(Object)` that casts and delegates.
- Callouts: **Framework vs language** (javac generates bridges and `Signature`; Spring's `BridgeMethodResolver` exists because reflection sees both methods; verify the class in spring-core 7.0.10).
- Failure modes: reflection-driven frameworks see bridge methods (Q03.18); a raw call reaches the bridge's cast; erasure clash appears when an overload is added late.
- Misconceptions: "generic type information is completely gone at run time" (declared signatures remain; only per-instance arguments are erased); "bridge methods are a JVM feature" (javac emits them).

### §6. Reifiable types, generic arrays and heap pollution · 850 words · `SEC-M03-06` (M)

- Diagram: none.
