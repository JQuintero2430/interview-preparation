## Factual errors

**F-1 · Medium · "Only traversal fires `popstate`" is false for fragment navigation.**
- Location: line 383 ("**Do treat `popstate` as traversal only**"), line 389 ("`pushState` triggers `popstate`. It never does; only traversal does."), line 759 (Q08.18 short answer: "tells you only about traversals (`popstate`)"). The first half of line 389 and the MDN quote at line 361 are correct.
- Wrong: the HTML Standard's *navigate to a fragment* algorithm ends with *update document for history step application*, and that algorithm, when the document's entry changed and the document is not new, runs "Fire an event named popstate", and then, if the fragment differs, queues `hashchange`. So `location.hash = '#y'` and a click on `<a href="#x">` fire `popstate` and then `hashchange`, with no traversal. I ran it: in jsdom 30.1.1 `window.location.hash = '#y'` logged `popstate,hashchange`. MDN's `popstate` page prose reads as if hash changes fire only `hashchange`, which may be where the module's wording comes from; the spec says otherwise. A router that listens to `popstate` and treats every call as back/forward will therefore also see hash navigations.
- Correction: "`popstate` fires when the active history entry changes without a new document: traversal (back, forward, `history.go()`) and fragment navigation (`location.hash`, `<a href="#x">`). `pushState` and `replaceState` never fire it." Reword the practice at 383 ("because your own `pushState` calls never fire it, and it also fires for `#` navigations"), the trap at 389-390, the Q08.18 short answer, and add a jsdom assertion to `section-7-history.test.ts` ("Section 7: a fragment navigation fires popstate, then hashchange"), with the prose saying "jsdom follows the spec algorithm; not observed in a real browser" (V-1).
- Basis: ran (jsdom probe); read spec (HTML Standard `browsing-the-web`, both algorithms); MDN `popstate` read. Not observed in Chrome, Firefox or Safari.

**F-2 · Low · Q08.12 follow-up understates which listeners see a composed, non-bubbling event.**
- Location: line 662. Quote: "*Without `bubbles`?* The composed event reaches only the host's own listeners outside."
- Wrong: the host is the retargeted target, so its listeners run in the at-target phase, but capture listeners on the host's ancestors also run (the capture pass walks the whole path). I ran it: a composed, non-bubbling event on a button in an open shadow root logged `doc-capture, host` (a `document` capture listener fired; the `document` bubble listener did not). The test `events-and-shadow.test.ts` (Q08.12 follow-up) asserts only a bubble listener on `document`, so it does not contradict the text, but the text is broader than what it shows.
- Correction: "The host's own listeners run (at target), and capture listeners above it run; no bubble listener above the host does." Extend the test with a capture listener on `document`.
- Basis: ran (jsdom probe); read DOM Standard dispatch (module line 561 describes the same two passes).
