## Factual errors

1. **Medium. Line 849 (Q03.08 follow-up).** Quote: "*What does `class X extends null` do?* It creates a class whose instances do not inherit from `Object.prototype`. It is rare, and its constructor needs care because there is no parent constructor to call." Misleading: `new X()` throws, so such a class has no ordinary instances at all. Only `X.prototype` has a `null` prototype. Correction: "`X.prototype` gets a `null` prototype, but `new X()` throws a `TypeError` (the implicit constructor calls a `null` super constructor) unless the constructor returns an object, for example `Object.create(X.prototype)`. It is a niche way to build prototype-less class hierarchies." Evidence: `node -e 'class X extends null {}; try { new X() } catch (e) { console.log(e.constructor.name, e.message) }; console.log(Object.getPrototypeOf(X.prototype), Object.getPrototypeOf(X) === Function.prototype)'` printed `TypeError Super constructor null of X is not a constructor` and `null true`.
2. **Medium. Line 313 and line 1036.** Quotes: "A `false` from `set`, `deleteProperty` or `defineProperty` means "refused". In strict mode the operation then throws a `TypeError`." and "`set`, `deleteProperty` and `defineProperty` report success with a boolean, and in strict code a `false` becomes a `TypeError`." Wrong for `defineProperty`: `Object.defineProperty` throws a `TypeError` in sloppy and strict code alike, while `Reflect.defineProperty` returns `false` and never throws. Only `set` and `deleteProperty` (assignment and `delete` operators) depend on strict mode. Correction: split the sentence: "`set` and `deleteProperty`: the operator throws in strict mode and returns `false` silently in sloppy code. `defineProperty`: `Object.defineProperty` always throws, `Reflect.defineProperty` returns `false`." Evidence: in a sloppy `node -e` script, `Object.defineProperty(new Proxy({}, {defineProperty: () => false}), 'x', {value: 1})` threw `TypeError`; `Reflect.defineProperty(...)` returned `false`; `new Proxy({a:1}, {set: () => false}).a = 2` did not throw.
3. **Low. Line 233.** Quote: "**Do keep constructors cheap and side-effect free**, because subclasses cannot run code before `super()`". Overbroad: a derived constructor can run any code that does not touch `this` before `super()`. Correction: "...because a subclass cannot touch `this` before `super()` returns, and work done in the base constructor runs for every instance". Evidence: `class B extends A { constructor() { const v = 1 + 1; super(v); } }` ran and `new B().x` printed `2`; `this.y = 1; super(1)` threw `ReferenceError: Must call super constructor in derived class before accessing 'this'...`.
4. **Low. Line 193.** Quote: "That is what lets `class MyError extends Error` and `class MyArray extends Array` produce real exotic objects". `Array` instances are exotic (special `length` behavior); `Error` instances are ordinary objects that carry an `[[ErrorData]]` internal slot (`Object.prototype.toString.call(new Error('x'))` is `[object Error]`; its own names are `stack` and `message`). Correction: "...produce real arrays (exotic `length` behavior) and real errors (with the internal slots the engine and `Error.prototype.toString` expect)". Module 02 line 296 already defines "exotic object" inline, so link it rather than redefine.
5. **Low. Line 341 (Coming from the backend, section 5).** Quote: "it has no equivalent of Spring's self-invocation problem: inside a method called through the proxy, `this` *is* the proxy." True only while the `get` trap does not bind methods to the target. The module itself recommends exactly that fix for `Map`/private fields (lines 314, 887), and with it `this` is the raw target, so calls made inside the method bypass the traps: Spring's self-invocation problem again. Correction: add "unless a `get` trap binds methods to the target, which is the usual fix for internal slots and reintroduces the problem".
6. **Low. Line 796 vs 798 (Q03.07a).** Short answer: "`Object.create(null)` ... whose keys are still strings only"; full explanation (798): "Keys are strings (or symbols)". Contradiction inside one answer. Correction: "string or symbol keys only" in the short answer.
7. **Low. Lines 772-779 (Q03.07 `safeMerge`, an Excerpt of `sections.test.ts` line 77-84).** The snippet is presented as the fix, but it throws when the defaults hold a primitive or `null` where the user input has an object. Evidence: ran the excerpt on Node 24: `safeMerge({a: 1}, {a: {b: 2}})` threw `TypeError: Cannot create property 'b' on number '1'`; `safeMerge({a: null}, {a: {b: 2}})` threw `TypeError: Cannot set properties of null (setting 'b')`. Correction: descend only into an existing own value that `isBag`, otherwise replace it: `const existing = Object.hasOwn(target, key) ? target[key] : undefined; safeMerge(isBag(existing) ? existing : (target[key] = {}) as Bag, value)`. The Excerpt and the test `Q03.07 ...` in `sections.test.ts` must change together, with a new assertion for the primitive-default case.
