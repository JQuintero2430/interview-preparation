### 1. Why render on the server: CSR, SSR, SSG and hybrid rendering, and what each costs · delta 850 (750 + 100 verification paragraph) · SEC-M32-01 (Opus)

Analogy: a restaurant that serves some dishes from the fridge (SSG), cooks others to order (SSR), and hands out kits for the rest (CSR). ### 4. Hydration: reusing the server's DOM, mismatches and `ngSkipHydration` · delta 850 · SEC-M32-04 (Opus)
- **Problem:** before v16 the client threw away the server DOM and rendered again: a flicker, lost scroll and focus, and twice the DOM work (read the "destructive hydration" history from the docs or CHANGELOG before saying it, C5); today a component that adds nodes with `document.createElement` breaks hydration of the page, and a team's fix is `ngSkipHydration` on the root.
- **Model:** **hydration** is the client **taking over** the server's DOM: Angular walks its templates and **claims** the existing nodes instead of creating new ones, then attaches listeners. Analogy: a new tenant moving into a furnished flat with the inventory list (annotations), not buying new furniture; a missing chair on the list stops the move. Diagram: `sequenceDiagram`: Server, Browser, Angular: `"HTML + ngh + state script"` → `paint` → `"main.js loads"` → `"read annotations"` → `"claim nodes, attach listeners"` → `alt "DOM matches"` `hydrated` `else` `"mismatch error (NG05xx)"`. **What to notice:** nothing is re-rendered when hydration succeeds.

### 5. Event replay: keeping the clicks made before the code arrives · delta 600 · SEC-M32-05

### 8. Data across the boundary: the HTTP transfer cache, `TransferState` and `resource` ids · delta 800 · SEC-M32-08
