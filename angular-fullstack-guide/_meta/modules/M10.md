## Facts established while planning (re-check in the task that uses them)

Probes ran on 2026-10-06 in Node 24.21.0 against jsdom 30.1.1 (`labs/ts-js/node_modules`) and Sass 1.104.1; scratch files deleted. Each task re-verifies before writing.

**Ran, jsdom 30.1.1 (`getComputedStyle` over `<style>` in a document), these work:**
- Specificity and order: `#a` beats `.b` beats `p` regardless of order (computed `rgb(255, 0, 0)` for the id rule); equal specificity, the later rule wins; a class beats a later type selector; an inline `style` beats an id rule; an author `!important` beats a higher-specificity normal rule; an `!important` sheet rule beats a normal inline style; `style="color:red !important"` reports priority `important`.
- `:is(#a, .z)` takes the specificity of its most specific argument (beat a later `.b`); `:where(#a)` counts zero (a `.b` rule written *before* it still wins); `:where(.b)` loses to an earlier `p` rule. `querySelectorAll(':is(p,i)')` and `:where(p,i)` both match 2; `div:has(p)` matches 1; `h2:has(+ p)` matches 1; `:has()` inside a stylesheet colours the right element; `:not(:is(.a))` and `:nth-child(2n+1)` work.
- Inheritance: `color` inherits (`div{color:red}` reaches the child `p`); `border-top-width` does not (computed `0px`). `em` compounds (`2em` inside `2em` of 16px gives `64px`), `rem` follows the root (`html{font-size:20px}`, `2rem` gives `40px`). Shorthands expand (`margin:1px 2px 3px 4px` gives `margin-left: 4px`).
- Custom properties: `getPropertyValue('--c')` returns the declared value on the declaring element and on descendants (`red` outside `.d`, `blue` inside `.d{--c:blue}`); `style.setProperty('--c','green')` is read back.
- Declared values are readable without layout: `position`, `z-index`, `opacity`, `transform`, `filter`, `isolation`, `will-change`, `contain`, `mix-blend-mode`, `perspective`, `container-type` (`inline-size`), `display` (`flex`, with `gap`), `color-scheme` (`light dark`), and a flex child's `z-index` (`1`, with `position: static`).

**Ran, jsdom 30.1.1, these are NOT implemented (pinned by `Section 1:` tests so a jsdom upgrade is noticed):**
- No layout: `offsetWidth` and `getBoundingClientRect().width` are `0` even for `width:100px`.
- `@layer`: the sheet parses (`CSSLayerBlockRule`, `CSSLayerStatementRule`) but rules inside layers **are ignored** by `getComputedStyle` (colour stays `rgb(0, 0, 0)`, even against an unlayered rule). Layers are documented only (and modelled in Exercise 10.2).
- `@media (min-width: 500px)` with `innerWidth` 1024 is not applied; `window.matchMedia` is `undefined`. `@container` parses (`CSSContainerRule`) and is not applied.
- Native nesting parses (`cssText` shows `& .b`, with a "Could not parse CSS stylesheet" console error for the unprefixed form) and nested rules are **not applied**.
- `var()` is not resolved: `getComputedStyle(p).color` returns the string `var(--c)`; `margin-inline-start: 4px` does not map to `margin-left` (stays `0`); `@scope` is not applied; `@property` is not applied (`width: var(--x)`).
- Do not rely on: `clamp(1rem, 2vw, 2rem)` computed to `20.48px` (jsdom resolved `vw` against its 1024 default; not a statement about browsers).

### 1. The box model and formatting contexts · ~620 words · SEC-M10-01
- **Problem:** a `width: 100%` input with padding overflows its column; two stacked cards leave a 24px gap, not 48px; a child's `margin-top` pushes the whole parent down; a floated image escapes its container.
- **Model:** every element generates boxes of four nested rectangles (content, padding, border, margin), and boxes are laid out inside a **formatting context**, a region with one set of layout rules (block, inline, flex, grid). Diagram: `flowchart` decision "two vertical margins meet: same block formatting context? adjacent siblings, or parent and first/last in-flow child with nothing between? then collapse; flex/grid item, float, absolute box or `flow-root` boundary? then do not". **What to notice:** collapse is a decision about *where the boxes live*, not about the margin values.
- **Mechanism:** `content-box` versus `border-box` (which box `width` sets; `box-sizing` is not inherited, hence the `*, *::before, *::after` reset); percentage padding and margin resolve against the containing block's inline size (read before stating); outer versus inner `display` (`block`, `inline`, `inline-block`, `flow-root`, `flex`, `grid`); `width`/`height` do not apply to non-replaced inline boxes; margin collapsing's three cases and the positive/negative rule (MDN, Facts); what establishes a BFC (`flow-root`, `overflow` other than `visible`, floats, absolute boxes, flex/grid items as their own contexts; list read from CSS Display 3 or MDN) and what a BFC does (contains floats, stops parent-child collapse); `gap` never collapses; flex and grid items do not collapse (forward link to 3).
- **First-use definitions:** box model, containing block, formatting context, block formatting context (BFC), replaced element, margin collapsing, clearance.
- **Verification:** CSS 2.2 §8.3.1 and §9.4.1 read before writing; MDN pages quoted. Lab: `section-1-jsdom-limits.test.ts` (see the Facts list: `Section 1: jsdom does no layout (offsetWidth and getBoundingClientRect are 0)`, and the other pins) and `Section 1: box-sizing is read as declared, content-box by default`. Everything about collapse and BFCs is documented, never observed.
- **Callout:** none required (no named comparison). A *Framework vs platform* sentence is not needed here.
- **Questions drilled:** Q10.01, Q10.02.

### 2. The cascade: origins, specificity and layers · ~700 words · SEC-M10-02
- **Problem:** a component's `.btn` rule loses to a global `.btn` that happens to be later; a team ends up writing `!important` and ids to beat a third-party library; a `:is(#hero, .x)` makes a selector unexpectedly heavy.
- **Model:** a tournament with fixed tie-break rounds: for each property of each element, every declaration from every source competes, and the first round in which they differ decides. Diagram: `flowchart TD` of the sort order (origin and importance, element-attached `style`, layer, specificity, order of appearance). **What to notice:** specificity is only the fourth round; layers and importance outrank it, and order is the last resort.
- **Mechanism:** origins (user agent, user, author) and `!important` reversing their order; the `style` attribute; layers (`@layer a, b;` fixes order by first mention, unlayered styles beat layered ones for normal declarations, the reversal for `!important`, nested and anonymous layers, `@import url() layer(x)`; read from Cascade Level 5); specificity as a triple (ids, classes/attributes/pseudo-classes, types/pseudo-elements; `*`, combinators and `:where()` add nothing; `:is()`, `:not()`, `:has()` take their most specific argument; `&` in nesting behaves like `:is()`, link to 7); source order; inheritance and the defaulting keywords (`inherit`, `initial`, `unset`, `revert`, `revert-layer`; which properties inherit); `@scope` named only (status read in the task). What jsdom runs (Facts) and what it does not (layers).
- **First-use definitions:** cascade, declaration, origin, specificity, cascade layer, inheritance, computed value, pseudo-class versus pseudo-element.
- **Verification:** `section-2-cascade.test.ts` (jsdom): `Section 2: an id selector beats a class beats a type selector`, `… the later rule wins on equal specificity`, `… an inline style beats an id rule and an !important sheet rule beats an inline style`, `… :where adds no specificity and :is takes its most specific argument`, `… :has matches by structure and counts like its argument`, `… color inherits and border-width does not`. Layers: Cascade Level 5 and MDN, documented; `Section 1: jsdom ignores rules inside @layer` is the pin. The model of the algorithm is Exercise 10.2.
- **Callout:** *Framework vs platform* (`> [!NOTE]`): Angular's emulated view encapsulation rewrites component selectors with an attribute, which changes specificity; owner 13, one sentence read from angular.dev, status marker where one applies.
- **Questions drilled:** Q10.03, Q10.04, Q10.05, Q10.06; Exercises 10.1, 10.2.

### 3. Flexbox, Grid and subgrid · ~640 words · SEC-M10-03
- **Problem:** vertical centring by hacks; a row of cards whose buttons do not line up because titles wrap differently; a long word makes a flex child overflow its parent instead of truncating.
- **Model:** flexbox distributes items along **one axis**, sized from the content outward; grid defines **tracks in two dimensions** and places items into them, sized from the layout inward; subgrid lets a nested grid borrow its parent's tracks. Diagram: `flowchart` decision (one dimension or two? content decides sizes or the layout does? nested items must align to the parent's tracks?). **What to notice:** the two systems nest; the decision is per container, not per page.
- **Mechanism:** main and cross axis, `flex` shorthand (`flex: 1` means `1 1 0%`; verify), `flex-basis` versus `width`, `flex-wrap`, `gap`, alignment properties (`justify-*` on the main axis in flex, `align-*` on the cross axis), the automatic minimum size (`min-width: auto`, fixed by `min-width: 0`), grid tracks (`fr`, `minmax()`, `repeat(auto-fill | auto-fit, minmax(…))` and the difference), implicit tracks, `grid-template-areas`, placement and `gap`; no margin collapse inside either (back to 1); `z-index` works on flex and grid items without `position` (forward to 4); subgrid (`grid-template-columns|rows: subgrid`, "Baseline - Widely available since September 2023" per MDN read 2026-10-06); when each wins; a grid with `auto-fill` needs no JavaScript ([Q17.39](../../modules/17-signals.md#q17-39)).
- **First-use definitions:** flex container and item, main and cross axis, track, `fr` unit, implicit grid, intrinsic versus extrinsic sizing.
- **Verification:** CSS Flexbox Level 1 §4.5 and §7, Grid Level 1 and 2, MDN pages. No lab test claims layout (jsdom has none): the section says "documented, not run". `Section 3: jsdom reads display:flex and gap but computes no geometry` is optional if a claim needs it.
- **Callout:** none required.
- **Questions drilled:** Q10.07, Q10.08, Q10.09.

### 4. Positioning, stacking contexts and z-index · ~600 words · SEC-M10-04
- **Problem:** a modal sits behind the header although its `z-index` is 9999; a `position: sticky` header never sticks; a tooltip is clipped by an `overflow: hidden` ancestor; a `position: fixed` banner scrolls with its parent.
- **Model:** painting is a stack of sheets: each stacking context is one sheet painted as a unit inside its parent's context, and `z-index` only orders siblings **inside the same sheet**. Diagram: `flowchart TD` tree (root context, two child contexts with `z-index` 4 and 5, a grandchild with `z-index` 6 that still paints under the 5). **What to notice:** a huge number in a child is bounded by its context's number.
- **Mechanism:** `position` values and what each is relative to (containing block; `fixed` relative to the viewport unless an ancestor with `transform`, `filter` and the like becomes its containing block; read from CSS Positioned Layout 3 and MDN); `inset`; `sticky` needs a scrolling ancestor and breaks under `overflow` on an ancestor (read); the stacking-context creators (MDN list, Facts) and why `opacity`, `transform`, `will-change` (link [Q08.05](../../modules/08-browser-rendering-dom-events.md#q08-05)) and `container-type` create one by side effect; paint order inside a context (CSS 2.2 Appendix E, summarised: backgrounds, negative `z-index`, in-flow blocks, floats, inline content, `z-index: auto`/`0` positioned, positive `z-index`); `isolation: isolate` as the deliberate way; the top layer (`<dialog>`, popover) and why it avoids `z-index` wars (Baseline status read in the task).
- **First-use definitions:** stacking context, containing block (re-used from 1, linked), top layer, paint order, sticky positioning.
- **Verification:** MDN stacking-context page (quoted) and CSS 2.2 Appendix E. Lab: `stacking-context.ts` (`stackingContextReasons(element)` returns the reasons found from computed values, following the MDN list) with `section-4-stacking.test.ts`: `Section 4: positioned with z-index auto creates no context and with z-index 2 does`, `… opacity below 1, transform, filter, isolation, will-change, contain and container-type each create one`, `… a flex child with z-index creates one without position`, `… findCulprit walks the ancestors to the nearest context`. These tests show that the helper reads **declared values**; that a browser paints accordingly is MDN's, documented.

### 5. Responsive CSS: media queries, container queries and fluid type · ~640 words · SEC-M10-05
- **Problem:** a card looks right in the main column and breaks in the sidebar because a media query looks at the viewport; headings jump between breakpoints; `margin-left` is wrong in a right-to-left layout.
- **Model:** three different questions: how wide is the **viewport** (media query), how wide is **this component's container** (container query), how large should a value be **between two sizes** (`clamp()`). Diagram: `flowchart` decision on what the style should respond to. **What to notice:** a container query makes a component portable; a media query makes a page layout.
- **Mechanism:** the viewport meta tag; media features (`min-width`, range syntax `width >= 600px` with its status read, `prefers-color-scheme`, `prefers-reduced-motion`, `hover`, `orientation`), mobile-first `min-width`; units (`rem`, `em`, `%`, `vw`, `dvh`/`svh`/`lvh`, `ch`, container units `cqi`); container queries (`container-type: inline-size`, `container-name`, `@container (min-width: …)`; size containment means the container cannot size itself from its children's inline size and the declaration also creates a stacking context and containing block, MDN, link 4; style queries named only); fluid type with `clamp(min, preferred, max)`, a `rem + vw` preferred value so user zoom still scales (WCAG 1.4.4 and 1.4.10: one sentence, link 11), and the formula slope = (max - min) / (maxViewport - minViewport) used by Exercise 10.3; logical properties (`margin-inline`, `padding-block`, `inline-size`, `inset-inline-start`) follow `writing-mode` and `direction` (RTL itself is 34); intrinsic layouts (`auto-fill`, `aspect-ratio`) before any query.
- **First-use definitions:** viewport, media query, container query, size containment, fluid typography, logical property, writing mode.
- **Verification:** MDN and the specs read in the task (Baseline per page, or left out). Lab: `section-5-units.test.ts`: `Section 5: em compounds through nested elements and rem follows the root (jsdom)`; pins from Section 1 for "jsdom applies no @media or @container rule and has no matchMedia". ### 6. Custom properties, theming and `color-scheme` · ~600 words · SEC-M10-06
- **Problem:** the same colour literal is repeated in forty files; dark mode flashes white on load; a third-party component whose styles live in a shadow tree cannot be recoloured; a Sass variable cannot change when the user switches theme.
- **Model:** a custom property is a value that lives **on the element tree**: declared on a node, inherited by descendants, read by `var()` when the computed value is resolved. Analogy: a per-scope environment variable, not a compile-time constant. Diagram: `flowchart` of `:root` tokens, a `[data-theme="dark"]` override on a subtree, a component reading `var(--surface, white)`, and the theme-selection decision (stored choice, else `prefers-color-scheme`). **What to notice:** nothing is recompiled; only the nearest declaration changes.

## Exercises (3, ceiling 3)

Each follows the full E1 anatomy, at most 380 prose words. Solutions in `labs/ts-js/src/modules/10-css-essentials/<name>.ts` with `<name>.test.ts`, `describe('E10.N …')`, one `it` per criterion titled with its text. **The module never claims "mutation checks" or "checked by hand."** Each exercise's text says it is a **model of the specification, not a browser**, names the ECMAScript edition of any post-ES2015 feature at first use (for example `Array.prototype.at` ES2022, `Object.groupBy` ES2024), and states what is out of scope under Constraints.

1. **Exercise 10.1 · A specificity calculator** (EX-M10-01; section 2; `specificity.ts`). `specificity(selector): [number, number, number]` and `compareSpecificity(a, b)`. Constraints: no nesting `&`, no `@scope`, no escapes. Criteria:
   - ids, classes, attribute selectors and pseudo-classes, and types and pseudo-elements are counted into their own column;
   - `*`, combinators and `:where()` (whatever its argument) add nothing;
   - `:is()`, `:not()` and `:has()` add the specificity of their most specific argument;
   - `compareSpecificity` orders by column left to right, so `[1,0,0]` beats `[0,20,0]`;
   - for a shared table of selector pairs, the calculator's winner equals the colour jsdom computes (the table avoids layers and media).
2. **Exercise 10.2 · A cascade resolver with layers** (EX-M10-02; section 2; `cascade.ts`, uses `specificity.ts` as a read-only module from EX-M10-01). `resolve(declarations, layerOrder)` returns the winning value per property. Constraints: author origin plus an optional user-agent origin; no `@scope`, no `revert`, no animations or transitions. Criteria:
   - an `!important` declaration beats any normal one, whatever the specificity;
   - among normal author declarations an unlayered one beats a layered one, and a later layer beats an earlier one (the order in `layerOrder`);
   - among `!important` author declarations the layer order is reversed and an unlayered one is the weakest;
   - an element-attached (inline) declaration is ranked as the Cascade Level 5 text says (the task reads it and the test names the section it follows);
   - on equal origin, importance and layer, higher specificity wins, then the later declaration;
   - the cases without layers agree with jsdom; layered cases are checked against the specification text only, and the module says jsdom ignores layers.
3. **Exercise 10.3 · A token resolver and a fluid scale** (EX-M10-03; sections 5 and 6, integrates the module; `tokens.ts`). `resolveVar(name, scopeChain, fallback?)`, `fluidClamp({ minPx, maxPx, minViewportPx, maxViewportPx })` and `clampAt(css, viewportPx)`. Constraints: single-value tokens only; px and rem at 16px root. Criteria:
   - a name is resolved from the nearest scope outward (inheritance) and a redefinition in an inner scope wins;
   - an undefined name uses the fallback, and no fallback gives the guaranteed-invalid value (`undefined` in the model);
   - a reference cycle is invalid, not an infinite loop;
   - `fluidClamp` returns a `clamp(<min>rem, <intercept>rem + <slope>vw, <max>rem)` string whose evaluation is `minPx` at and below `minViewportPx` and `maxPx` at and above `maxViewportPx`, linear between;
   - the declared scopes round-trip through jsdom: `getPropertyValue` on a nested element returns what `resolveVar` returns for that scope.
