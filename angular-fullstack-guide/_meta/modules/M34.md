### 1. i18n, l10n and the locale: language tags, what a locale decides, and `LOCALE_ID` · delta 850 (750 + 100 verification paragraph) · SEC-M34-01 (Opus)
- **Problem:** a Chilean shop shows `$1,234.50` to customers who read `$1.235`; a French release translated every word but still says "1 items" for zero; a German user's date reads 07/08 and nobody knows which day it is.
- **Model:** **internationalization** (i18n, the 18 letters between i and n) is the engineering that makes an app adaptable: no hard-coded text, formats or direction; **localization** (l10n) is producing and shipping one adaptation; docs' definitions (F21). A **locale** is a BCP 47 **language tag** (`fr`, `fr-CA`, `zh-Hant-TW`, `ar-EG`): language, optional script and region; it decides text, number and date formats, plural rules, collation, first day of week, numbering system and direction. Angular's **`LOCALE_ID`** is the injection token holding the app's locale (16 §7 link); `DEFAULT_CURRENCY_CODE` is separate because currency is data, not locale. Analogy: the language tag is a postal address read from coarse to fine; formats are the local customs at that address. Diagram: `flowchart LR`: `"language tag fr-CA"` → `"language fr"`, `"region CA"`; both → `"text"`, `"numbers and dates"`, `"plural rules"`, `"collation"`, `"direction"`; separate node `"currency (data)"`. **What to notice:** the currency arrow does not start at the locale.
- **Mechanism:** **read from the `@angular/core` 22.2.1 source** (`_debug_node-chunk.mjs`, internal `getGlobalLocale`, F5): `LOCALE_ID` falls back from a provider to `$localize.locale` to `en-US`, so a localized build sets it without a provider (§7); `DEFAULT_CURRENCY_CODE` is `USD` everywhere; bootstrap copies `LOCALE_ID` into the internal `setLocaleId` used by ICU plurals (§5, §12). `Intl.getCanonicalLocales` and `Intl.Locale` parse tags (ts-js tests). One sentence each on source locale (`i18n.sourceLocale`, default `en-US`, F21) and on "region versus language" (`en-GB` uses `en` data unless registered, link 14 §6).
- **First-use definitions:** internationalization, localization, locale, BCP 47 language tag, subtag, source locale, `LOCALE_ID`, injection token (link 16 §7), CLDR (the Unicode Common Locale Data Repository), ICU (International Components for Unicode, the library engines use; distinct from ICU message syntax in §5).
- **Verification:** `labs/angular/src/app/modules/34-i18n/concepts/section-1-locale-id.spec.ts` (`ng test`): `Section 1: LOCALE_ID is en-US when nothing sets it`, `Section 1: LOCALE_ID follows $localize.locale when no provider sets it` (sets and restores `$localize.locale` before creating the injector, probe first), `Section 1: a LOCALE_ID provider wins over $localize.locale`, `Section 1: DEFAULT_CURRENCY_CODE is USD in a French app`; `labs/ts-js/src/modules/34-i18n/section-1-locales.test.ts`: `Section 1: getCanonicalLocales normalizes the case of a tag`, `Section 1: Intl.Locale splits a tag into language, script and region`, `Section 1: supportedLocalesOf drops a tag the runtime cannot format`.

- **Misconceptions:** "i18n means translating the text" (cause: translation is the visible part; formats, plurals, direction and collation change too, §2-§11); "a locale is a country" (cause: flags in language pickers; `fr-CA` and `en-CA` share a country and differ in everything, Intl test); "setting `LOCALE_ID` to `de` makes prices euros" (cause: currency looks locale-bound; the factory returns `USD`, tested); "the browser language is the user's locale" (cause: `navigator.language` is easy to read; users choose, and the app must let them, §7, §9).
