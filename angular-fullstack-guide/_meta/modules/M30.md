- F11. **Outcomes (r, `lib/common/index.js`, `outcome()`, internal).** A test's outcome is `expected` when no attempt was unexpected, `unexpected` when no attempt was expected (and none skipped), and otherwise **`flaky`**; `ok()` treats `expected`, `flaky` and `skipped` as passing (`lib/runner/index.js`). `--fail-on-flaky-tests` ("Fail if any test is flagged as flaky (default: false)") and `failOnFlakyTests` turn a flaky outcome into a failed run (`lib/program.js`, `lib/cli/testActions.js`).
- F12. **Sharding (r, `lib/runner/index.js` `filterForShard(shard, weights, testGroups)`, internal).** Weights default to 1 per shard (an undocumented `PWTEST_SHARD_WEIGHTS` environment variable can override them, internal); the total is the **number of tests** across test groups; shard sizes are `Math.floor(w * total / totalWeight)` with the remainder spread one by one from shard 1; groups are taken **whole, in order**, into the shard whose `[from, to)` window contains the group's starting test index. Without `fullyParallel` a group is a file, so a large file lands whole in one shard (imbalance); with it, groups are single tests. **No duration data is used.** Docs (d, `test-sharding-js.md`): "Without the fullyParallel setting, Playwright Test defaults to file-level granularity …"; "it is recommended to use `fullyParallel: true` when aiming for balanced distribution across shards"; "`merge-reports` … merge multiple blob reports (for sharded tests) into a single report" (`lib/program.js`). CLI: `--shard <shard>` ("current/all", 1-based), `--last-failed`, `--only-changed [ref]` ("Only supports Git."), `--repeat-each <N>`, `--fail-on-flaky-tests`, `--retries`.
- F13. **Retries and workers (d, `test-retries-js.md`).** "By default failing tests are not retried."; the doc's walkthrough: after a failure the worker process is discarded and a new worker starts with the next test, and with retries the new worker starts by retrying the failed test. - F14. **Trace and video modes (r, `lib/program.js` `kTraceModes`):** `on`, `off`, `on-first-retry`, `on-all-retries`, `retain-on-failure`, `retain-on-first-failure`, `retain-on-failure-and-retries`.
- F15. **Strictness (r, `playwright-core` `lib/coreBundle.js`, `strictModeViolationError`, internal).** Message: `strict mode violation: <locator as code> resolved to <n> elements:` followed by one line per match (`...` past the shown ones). ### 1. What belongs at the end-to-end level: journeys, cost and a strategy across levels · delta 850 (750 + 100 verification paragraph) · SEC-M30-01 (Opus)
- **Problem:** a team mirrors every component test in Playwright and the suite takes most of an hour; another has no browser test and ships a build whose lazy route 404s behind the production server (no unit test serves the built files); a third's single e2e test asserts twenty things and nobody can tell what broke.
- **Model:** an **end-to-end (e2e) test** drives the **built** app in a real browser against a running server and checks a **user journey** (a path through several pages that delivers one outcome); it is the only level that sees the production bundle, real routing on a real server, layout and the browser's own behavior. A strategy assigns each **risk** to the cheapest level that can catch it ([29 §1](../../modules/29-testing-angular.md#1-what-to-test-where-unit-integration-component-and-end-to-end-tests-the-pyramid-and-the-trophy) owns the levels); e2e gets the journeys whose failure costs most and that no lower level can see. Analogy: a dress rehearsal: you do not rehearse every line in costume, only the scene changes. Diagram: `flowchart LR`: risks (`"rule in a function"`, `"template wiring"`, `"page + service + HTTP"`, `"built app on a server"`) → levels (`unit`, `component`, `"integration (unit runner)"`, `"end-to-end"`), one arrow each. **What to notice:** each risk goes to the cheapest level that can see it; only the last needs a browser.
- **Mechanism:** what only e2e sees (the production build with hashed bundles and lazy chunks, a server's SPA fallback, real `fetch`, layout, focus and the browser's validation), shown by §1's tests; what it costs (build, server, browser start, network; F10's 30 s default timeout as a symptom of slower steps); one assertion focus per test; **read from the `playwright` 1.63.0 source**: `defaultTimeout = 3e4` and `defaultExpectTimeout = 5e3` (F10) as the reason e2e failures surface slowly. - **Verification:** `labs/e2e/tests/concepts/section-1-what-belongs.spec.ts`: `Section 1: the add-todo journey runs on the production build in a real browser` (navigates `/m30/todos`, adds a todo, reads it back; asserts a hashed `main-*.js` script in the served HTML), `Section 1: a deep link to a lazy route is served by the server fallback` (direct `goto('/m30/todos?q=milk')`); `labs/angular/src/app/modules/30-e2e-and-testing-strategy/concepts/section-1-component-level.spec.ts` (`ng test`): `Section 1: the empty-title rule is checked in a component test without a browser` (the same rule as Exercise 30.1's criterion, at the cheaper level).

### 2. Playwright and Cypress: architecture, `ng e2e` and the end of Protractor · delta 750 · SEC-M30-02 (Opus)
- **Problem:** `ng e2e` in a new v22 project prints "Cannot find "e2e" target"; an old project's `e2e/protractor.conf.js` no longer runs after an update; a team picks Cypress and then needs two browser tabs (a checkout that opens a payment window) or a cross-origin login.
- **Model:** **Playwright** runs test code in **Node** and drives browsers out of process; each test gets a fresh **browser context** (an isolated profile: cookies, storage, cache) in a shared browser, and tests run in parallel **worker processes**. **Cypress** runs test code **inside the browser** next to the app (F22), with Node reached through tasks, one browser at a time, one superdomain per test. Angular contributes only the `e2e` target and `ng e2e`, which runs whatever builder a package added (F5). Analogy: Playwright is a driving instructor in the passenger seat with dual controls (outside the car's software); Cypress is a co-pilot wired into the car's dashboard (sees everything inside, cannot leave the car). Diagram: `flowchart LR` with two subgraphs: Playwright (`"test runner (Node)"` → `"worker 1..n"` → `browser` → `"context per test"` → `page`) and Cypress (`"Node process"` ↔ `"browser: app iframe + spec iframe"`). **What to notice:** where the test code runs decides tabs, origins and what the test can reach in Node.
- **Mechanism:** F5 and F9 (the missing target and the five `ng add` choices; C8), F7 (docs order differs), F6 (Protractor history; `[Removed in v19.0]`, C5), F22-F24 (Cypress trade-offs, documented only, C7), F2 and F3 (what `@playwright/test` brings; Chromium only in this lab), Playwright's docs on how it drives each browser (read in the task; C3); **read from the `@angular/cli` 22.2.1 source**: `E2eCommandModule` and `onMissingTarget` (internal) as the reason `ng e2e` prompts instead of failing silently.
- **Callouts:** required *Framework vs platform* (C3).
- **First-use definitions:** Playwright, Cypress, Protractor, WebDriver (one clause), browser context, worker process, builder (link 12), `ng add`, superdomain.

### 3. Auto-waiting: actionability checks, web-first assertions and Cypress retry-ability · delta 700 · SEC-M30-03
- **Problem:** a test reads `textContent` right after a click and fails one run in five; a teammate adds `waitForTimeout(2000)` and the suite slows by minutes while still failing on a slow CI machine; a click lands on a button covered by a toast.
- **Model:** Playwright **waits for the page, not the clock**: every action first waits until its target is **actionable** (F16), and every web-first assertion **retries** until it passes or its timeout ends (F10: 5 s); a value read once is a snapshot that never retries. Cypress retries **queries and assertions**, not commands like `.click()` (F23, documented). Analogy: a waiter who waits until the table is free before serving, versus one who serves after counting to two. Diagram: `stateDiagram-v2` for `click()`: `resolve` → `"exactly one?"` → `visible` → `stable` → `"receives events"` → `enabled` → `act`, with a retry loop back to `resolve` and a `TimeoutError` exit. **What to notice:** every check is retried until the timeout; nothing waits a fixed time.
- **Mechanism:** F16 (the checks, the `TimeoutError`), F10 (timeouts), F15 (strictness as the first check, link §4), F23 (Cypress retry-ability; documented); **read from the `playwright` 1.63.0 source**: `defaultExpectTimeout` in `lib/matchers/expect.js` and where web-first matchers poll (the task names the function it finds; internal).
- **First-use definitions:** actionability, auto-waiting, web-first assertion, retry-ability, `TimeoutError`.

### 4. Locators, page objects and fixtures · delta 750 · SEC-M30-04
- **Problem:** a redesign renames CSS classes and 60 e2e tests fail with no behavior change; a "Delete" click deletes the wrong row; every spec repeats the same login and navigation, and a URL change means editing 40 files.

### 5. API mocking at the network layer, and where contract tests take over · delta 750 · SEC-M30-05
- **Problem:** an e2e suite against a shared staging backend fails whenever another team's data changes; a "500 from the server" state is never tested because the real server never fails on demand; a mocked suite stays green while the backend renamed a field.
- **Model:** **network-layer mocking** intercepts the browser's own requests (Playwright `page.route`, F17) and answers them, so the app runs unchanged with a backend you script; the alternatives are a **stub server** (a small fake backend over HTTP, this lab's `app-server.mjs`) and the **real backend** with seeded data. Analogy: a flight simulator scripting a storm (mock), a training airfield (stub server), real weather (real backend); none checks that the airport still exists (contract). Diagram: `sequenceDiagram`: Test, Browser page, `"route handlers"`, `"app-server"`: page fetch → handlers in reverse registration order → `fulfill` (mock) or `fallback` → earlier handler → `continue` → server. **What to notice:** the last registered handler sees the request first (F17).
- **Mechanism:** F17 (`route`, `fulfill`, `continue`, `fallback`, order; `routeFromHAR`), the contrast with `HttpTestingController` in one sentence (link [27 §11](../../modules/27-http-client.md#11-testing-and-the-backend-seam-providehttpclienttesting-httptestingcontroller-and-what-they-replace): it replaces the backend inside `HttpClient`, no browser), Cypress `cy.intercept` (F23, documented), MSW (F26, documented: same idea through a Service Worker, reusable across unit and e2e), contract tests (F26 Pact, one paragraph, pointer 41); **read from the `playwright-core` 1.63.0 source**: where route handlers are matched in reverse order (the task finds the function by `grep` for `fallback` in `lib/coreBundle.js`; internal) as the reason the last registration wins.
- **First-use definitions:** network-layer mocking, route handler, fulfill, HAR (HTTP Archive), stub server, contract test, consumer-driven contract, Service Worker (link 09 if it defines it, else one clause).
- **Verification:** `section-5-network-mocking.spec.ts`: `Section 5: page.route fulfills the list request without the server`, `Section 5: the last registered route handles the request first`, `Section 5: route.fallback hands the request to the earlier handler`, `Section 5: an unrouted request reaches the stub server` (tenant data from `__reset`), `Section 5: routeFromHAR replays a recorded response` (C4; `tests/concepts/hars/todos.har`, recorded once against the fixture app with `update: true`, then committed).
- **Questions drilled:** Q30.09, Q30.10; Exercise 30.2.
- **Misconceptions:** "mocked e2e tests are not real e2e tests" (cause: purity; they still run the real build in a real browser; they trade backend coverage for determinism, and the trade is explicit); "`HttpTestingController` and `page.route` are the same" (cause: both fake HTTP; one replaces Angular's backend in Node, the other intercepts the browser's request, 27 §11); "a green mocked suite proves the API works" (cause: the mock echoes what the frontend expects; contracts close that gap, 41); "HAR files are a full mock server" (cause: they replay; unmatched requests fall through or fail per `notFound`, which the task reads in the typings before stating).

### 7. Flaky tests: root causes, diagnosis and fixes · delta 700 · SEC-M30-07
- **Problem:** a test passes alone and fails in the full suite one run in ten; CI goes green on the second run and the team learns to press "re-run"; a date-dependent test fails every night at midnight UTC.
- **Model:** a **flaky test** gives different results on the same code; its causes are **non-determinism the test does not control**: timing (fixed waits, racing a response), shared state (data, accounts, order between tests), the environment (time, time zone, viewport, fonts, network) and the app's own races. The fix is to **remove the uncontrolled input**, not to wait longer: wait for the event (F16, F20 `waitForResponse`), own the clock (`page.clock`, F20), own the data (per-test or per-worker tenants, Lab decision 4), mock what you do not own (§5). Analogy: a smoke alarm that goes off at random: you do not move it further away, you find the toaster. Diagram: `flowchart LR`: `"flaky failure"` → causes `timing`, `"shared state"`, `environment`, `"app race"` → fixes `"wait for an event"`, `"own the data"`, `"own the clock and env"`, `"fix the app"`. **What to notice:** every fix removes an input the test did not control; none adds time.
- **Mechanism:** F13 (a failure discards the worker, so state that leaks inside a worker hides until a retry runs elsewhere; detailed in §9), F11 (the `flaky` outcome), F12 (`--repeat-each`, `--last-failed`), F14 (`on-first-retry` traces as the diagnosis artifact); quote F27's Google and Fowler sources only if read; **read from the `playwright` 1.63.0 source**: `outcome()` in `lib/common/index.js` (internal) as the reason a retry-pass is reported as `flaky`, not `passed`.
- **First-use definitions:** flaky test, non-determinism, quarantine, trace (Playwright), `--repeat-each`.
- **Verification:** `section-7-flaky.spec.ts`: `Section 7: waiting for the response replaces a fixed sleep` (the scenario endpoint delays 1,500 ms; `waitForResponse` then the assertion; no `waitForTimeout` in the file), `Section 7: page.clock makes a timer-driven message deterministic` (C4; `page.setContent` with a `setTimeout` message, `clock.install` and `fastForward`), `Section 7: tests in separate tenants do not see each other's data` (two tests in one file, `test.describe.configure({ mode: 'parallel' })`, each adds "Same title" and sees exactly one).
- **Questions drilled:** Q30.13, Q30.14.
- **Misconceptions:** "flaky tests are the tool's fault" (cause: the failure shows up in the tool; most causes are uncontrolled inputs in the test or races in the app); "retries fix flakiness" (cause: CI turns green; they hide it, and F11's `flaky` outcome exists so it can be counted, §8); "a longer timeout is a fix" (cause: the failure was a timeout; the race remains, only rarer); "flaky tests can be ignored if they usually pass" (cause: habit; a flaky test that is ignored stops guarding anything, and real regressions hide among its failures).

### 8. CI strategy for end-to-end tests: workers, sharding, retries policy and test data · delta 800 · SEC-M30-08 (Opus)
- **Problem:** the e2e stage takes 45 minutes on one machine; after sharding, one shard takes 20 minutes and three take 2; retries are set to 3 "to be safe" and a real regression ships because it passed on the third try; two shards log in as the same seeded user and delete each other's data.
- **Model:** CI speed comes from **parallelism at two levels**: workers inside a machine and **shards** across machines (F12); reliability comes from a **retries policy** that keeps a pass-on-retry visible (F11: `flaky`, `failOnFlakyTests`) plus traces on retry (F14) and a quarantine rule; isolation comes from **test data management**: every test creates or resets its own data (per-test reset, per-worker tenant from `parallelIndex`, F2), never shared mutable fixtures. Analogy: a kitchen at rush hour: more cooks (workers), more kitchens (shards), a rule that a dish sent back once is logged and inspected (retries policy), and each cook with their own ingredients (test data). Diagram: `flowchart TB`: `"CI job"` → `"shard 1/3"`, `"shard 2/3"`, `"shard 3/3"` → each `"workers 1..n"` → `"blob report"` → `"merge-reports"` → `"HTML report + traces"`; side note `"retries: 2 on CI, 0 locally; failOnFlakyTests or a flaky budget"`. **What to notice:** shards are independent machines; only the merged report shows the whole run.
- **Mechanism:** F12 (sharding by test count, `fullyParallel` for balance, blob reports and `merge-reports`; Cypress Cloud's duration-based balancing as the contrast, F23, documented), F10 and F11 (no retries by default, the `flaky` outcome, `--fail-on-flaky-tests`), F14 (trace modes), F13 (workers), `--only-changed` and `--last-failed` (F12) as local loops, the production build as the artifact under test (Lab decision 4); test data: reset endpoint per test, tenant per worker (`parallelIndex`), unique values, no order dependence; `storageState` login setup projects documented only (read `auth.md` in the task); **read from the `playwright` 1.63.0 source**: `filterForShard` (internal) as the reason file-level shards can be unbalanced (detailed in §9).
- **Callouts:** optional *Coming from the backend* (C3).
- **First-use definitions:** shard, worker (link §2), `parallelIndex`, blob report, retries policy, flaky budget, quarantine, test data management, tenant, seed.
- **Verification:** `section-8-ci.spec.ts`: `Section 8: each worker gets its own tenant from parallelIndex` (worker-scoped fixture; two parallel tests record tenant names; C4), `Section 8: a reset seeds a known state for each test`; runner-level runs are Q30.15 and Q30.18's tests and §9's (C12).
- **Questions drilled:** Q30.15, Q30.16, Q30.17; Exercise 30.3.
- **Misconceptions:** "more shards always mean a faster run" (cause: linear thinking; each shard pays build and browser start-up, and file-level shards can be unbalanced, F12); "retries are free reliability" (cause: CI turns green; a pass on retry is a signal, F11, and hides regressions that fail intermittently); "seed the database once for the whole run" (cause: it is fast; shared mutable data couples tests across workers and shards); "run every e2e test on every commit" (cause: safety; the task states only policies its sources support, for example `--only-changed` locally and the full suite before merge, and links 38 for pipeline staging).

### 9. Under the hood: how Playwright's runner groups, shards, retries and isolates tests · delta 600 · SEC-M30-09 (Opus)
- **Problem:** an interviewer asks "why did `--shard=2/3` run only one file?", "why did the test that failed not leak state into the next one?", "how does Playwright decide a test is flaky?".
- **Model:** the runner loads all test files, builds **test groups** (a file, or a single test with `fullyParallel`), filters them for the shard by test count (F12), dispatches groups to **worker processes** (one browser per worker, one context per test), **replaces a worker after a failure** (F13) and reruns a failed test up to `retries` times in a fresh worker; finally each test's attempts become one **outcome** (F11). Diagram: `sequenceDiagram`: Runner, `"Worker A"`, `"Worker B"`: load files → build groups → `filterForShard` → dispatch group to A → test fails → A is torn down → B starts with the retry → passes → outcome `flaky`. **What to notice:** a failure never shares a process with the next test, so a retry runs in a clean worker.
- **Mechanism:** F12 (the algorithm, read and quoted in a few lines of pseudo-code; `PWTEST_SHARD_WEIGHTS` internal), F11 (`outcome()`), F13 (worker replacement), F14; **read from the `playwright` 1.63.0 source**: `filterForShard` in `lib/runner/index.js` and the dispatcher's worker restart (the task finds it by `grep` and names it; internal; C9).
- **First-use definitions:** test group, dispatcher, outcome.
- **Verification:** `section-9-under-the-hood.spec.ts` (nested runs, C12): `Section 9: a failed test's worker is replaced before the next test` (worker-project: test 1 fails and records `process.pid`, test 2 records its pid; different), `Section 9: without fullyParallel a whole file goes to one shard` (shard-project, `--list --shard=1/3`), `Section 9: with fullyParallel tests are split one by one` (same project with `--fully-parallel`).
- **Questions drilled:** Q30.18.
- **Misconceptions:** "shards are balanced by duration" (cause: other tools do it, F23; Playwright counts tests, F12); "a retry runs in the same worker" (cause: retry sounds like "again, here"; it runs in a new worker, F13); "`fullyParallel` makes tests in a file share state" (cause: same file; each test still gets its own context, and parallel files already ran in different workers).
