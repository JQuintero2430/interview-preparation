### 1. Sessions versus tokens: what the server keeps, what each request carries, revocation and scaling · delta 500 (400 + 100 verification paragraph) · SEC-M42-01
- **Problem:** a support engineer disables a compromised account and the attacker keeps calling the API for an hour; a second Spring instance behind the load balancer logs every other request out; a team moves to "stateless JWTs" and discovers logout cannot end a session (24:1946's handoff).
- **Model:** **authentication** (who is calling) versus **authorization** (what they may do, §5); a **server session** keeps state on the server and the browser holds only an id in a cookie (an ambient credential, 33 §9), so revocation is deleting a row, and scaling needs a shared store (Spring Session, F1, C4) or sticky routing; a **self-contained token** (a JWT: header, claims, signature, base64url, 33 §8) carries its own claims, so any instance can check it with a public key and nothing is looked up, but it stays valid until `exp`: revocation needs short lifetimes, a deny list or introspection (§5, Q42.16). Analogy: a cloakroom ticket (session id) versus a signed boarding pass (JWT): the cloakroom can tear up your coat's record; the gate can only check the pass's date and signature. Diagram: `flowchart LR` two lanes: session (cookie id → any instance → shared session store → user) and JWT (`Authorization: Bearer` → any instance → verify with the issuer's public key → claims), with "revoke" pointing at the store in one lane and at "wait for `exp`" in the other.
- **Mechanism:** **read from Spring Security 7.1.1 `session-management.adoc`** (F2) to answer "why does a second instance not know my session?": the default `SessionRegistry` is an in-memory map, the HTTP session lives in the container, and clustering is Spring Session's job; `SessionCreationPolicy.STATELESS` is how a resource server avoids sessions; Boot's session timeout is 30 minutes (F2). JWT anatomy and why decoding is not verifying: our `jwt.ts` decodes any token without a key, and verification fails after one claim changes (tests).
- **Code:** (1) Java: `http.sessionManagement((s) -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))` for an API and `server.servlet.session.timeout: 30m` (YAML, F2; banner); (2) TypeScript: `decodeJwt` and `verifyJwt` (Excerpt of `labs/ts-js/.../concepts/jwt.ts`, our signer and verifier over WebCrypto ES256 or RS256); (3) the session-store model's `revoke` (Excerpt).
- **Callouts:** **Coming from the backend** (required: sessions versus JWT is the Spring developer's home ground): `HttpSession` and Spring Session versus a JWT checked by `BearerTokenAuthenticationFilter` (F17); **where it breaks**: in the browser the session id is an ambient credential, so cookie sessions bring CSRF (§6), while a bearer token is script-readable and brings exfiltration (33 §8).
- **First-use definitions:** authentication, authorization, server session, session id, self-contained token, JWT (link 33 §8), claim, signature, base64url, revocation, deny list, sticky session, Spring Session.
- **Verification:** `labs/ts-js/src/modules/42-fullstack-authentication/concepts/{jwt.ts,session-store.ts,section-1-sessions-tokens.test.ts}` (our models, C18; `now` passed in): `Section 1: anyone can decode a JWT's claims without the key`; `Section 1: changing one claim makes the signature check fail`; `Section 1: a revoked session id is refused on the next request`; `Section 1: a JWT still verifies after logout until its exp`.
- **Questions drilled:** Q42.01, Q42.02, Q42.03.
- **Misconceptions:** "JWTs are encrypted" (cause: they look opaque; they are signed base64url, 33 §8 and RFC 7519 §3, linked once); "stateless means logout works the same" (cause: logout is a server action for sessions; a JWT has no server record to delete, test); "sessions don't scale" (cause: the default registry is in memory, F2; a shared store such as Spring Session scales them, C4); "a JWT in a cookie is stateless and CSRF-free" (cause: the format changes, the transport does not; a cookie is ambient, 33 §9).

### 2. OAuth 2.0 and OpenID Connect for a single-page app: Authorization Code with PKCE, and why the implicit flow is gone · delta 420 · SEC-M42-02
- **Problem:** an old Angular app receives `#access_token=…` in its URL and the token shows up in browser history and a referrer log; a team adds "login with the company IdP" and cannot say why the code exchange needs a verifier when the app has no secret; someone validates the access token in the browser to "check the user".
- **Model:** **OAuth 2.0** delegates access (the **authorization server** issues an **access token** for a **resource server**); **OpenID Connect** adds identity (an **ID token** for the client, plus `userinfo`); a single-page app is a **public client** (no secret), so the **Authorization Code flow with PKCE** binds the code to the browser that started the flow: the client keeps a random **`code_verifier`**, sends `code_challenge = BASE64URL(SHA256(verifier))` with `S256`, and the token endpoint recomputes it (F4b); **`state`** ties the callback to the request (C13), **`nonce`** ties the ID token to the session (F7), `iss` in the response detects mix-up (RFC 9207, F5). The **implicit flow** returned tokens in the redirect URL and is out: RFC 9700 "SHOULD NOT", RFC 10017 "MUST NOT" (F5, F6). Analogy: a coat-check where you keep half of a torn ticket (verifier) and the counter shows the other half's fingerprint (challenge). Diagram: `sequenceDiagram`: Angular app → browser redirect to `/authorize` (`response_type=code`, `code_challenge`, `state`, `nonce`) → user logs in at the IdP → redirect back with `code`, `state`, `iss` → token endpoint with `code` + `code_verifier` → access token, ID token (and maybe a refresh token, §4) → API with `Authorization: Bearer`.
- **Mechanism:** **read from RFC 7636** (F4b) to answer "what stops a stolen authorization code?": an intercepted code is useless without the verifier, which never left the app; `plain` is rejected for new clients; **read from RFC 9700 §2.1.2** why the implicit flow leaks (tokens in the authorization response, no sender constraint). Which token the API accepts: the access token, never the ID token (its `aud` is the client, F7; Q42.06).
- **Code:** (1) TypeScript: `createPkcePair()` and `challengeFor(verifier)` (Complete from `labs/ts-js/.../concepts/pkce.ts`); (2) the authorization URL builder (Excerpt); (3) Java: `spring.security.oauth2.client.registration.<id>` properties for a public client (`client-authentication-method: none`) with PKCE on by default (F8; YAML, banner) as the bridge to §3.
- **Callouts:** **Coming from the backend**: a Spring `oauth2Login` app is a confidential client with a secret; **where it breaks**: a browser cannot keep a secret, so PKCE replaces client authentication on the code exchange, and Spring still sends PKCE for confidential clients by default (F8).
- **First-use definitions:** OAuth 2.0, OpenID Connect, authorization server (IdP), resource server, client, public and confidential client, authorization code, redirect URI, PKCE, `code_verifier`, `code_challenge`, `S256`, `state`, `nonce`, ID token, implicit flow, mix-up attack (one clause).
- **Verification:** `labs/ts-js/src/modules/42-fullstack-authentication/concepts/{pkce.ts,section-2-pkce.test.ts}`: `Section 2: the S256 challenge for RFC 7636's example verifier matches the RFC`; `Section 2: a generated verifier is 43 to 128 unreserved characters`; `Section 2: the authorization URL carries response_type code, S256, state and nonce`; `Section 2: a callback whose state differs from the stored one is rejected`.
- **Questions drilled:** Q42.04, Q42.05, Q42.06, Q42.07. Practised in Exercise 42.1.
- **Misconceptions:** "PKCE replaces `state`" (cause: both are random values in the request; PKCE protects the code exchange, `state` and `nonce` protect the session binding, C13 before stating more); "the SPA should validate the access token" (cause: it is a JWT the app can decode; it is the resource server's audience, the app's is the ID token, F7); "Once true: the implicit flow was the SPA flow" (until RFC 9700 (January 2025) and RFC 10017 (August 2026) discouraged and forbade it, F5, F6; the cause: browsers once could not make the cross-origin token request); "OIDC is a different protocol from OAuth" (cause: separate specs; OIDC is a layer on OAuth 2.0's code flow, F7).

### 3. Where the OAuth client runs: a browser-only client, a token-mediating backend or a backend-for-frontend with Spring · delta 400 · SEC-M42-03 (Opus)
- **Problem:** after 33 §8's lesson the team still keeps the refresh token in the browser; the security review asks "what can injected script take in each design?" and nobody answers per design; the BFF they build sets the session cookie on `.example.com` and answers XHRs with a 302 to the IdP (33:1575, 33:2055 handoffs).
- **Model:** RFC 10017 §6's three architectures (F6): **browser-based OAuth client** (tokens in the page), **token-mediating backend** (the server does the code exchange and hands the access token to the page), **backend-for-frontend** (the server is the OAuth client, keeps all tokens, and the browser holds only an `HttpOnly` session cookie; every API call goes through the BFF, which attaches the token). Spring builds a BFF from `oauth2Login()` (confidential client, PKCE by default, authorized clients in the HTTP session, F8) and **Spring Cloud Gateway's `TokenRelay`** (F9); the cookie follows RFC 10017 §6.1.3.2 (F6; attributes from Boot's `Cookie`, F2, C3). The page still needs CSRF defenses for the cookie (§6). Analogy: a hotel where guests carry master keys, the front desk hands out a key per request, or the concierge opens every door for you. Diagram: `flowchart LR` three lanes: browser → IdP and API with tokens; browser → token-mediating backend → access token back to the browser → API; browser → BFF (session cookie) → `TokenRelay` → API with the bearer token.
- **Mechanism:** **read from RFC 10017 §6.1-§6.2** what each architecture leaves to stolen script (F6; 33 §8's "none of these options can fully mitigate token exfiltration when the attacker can execute malicious code" linked, not re-quoted); **read from Spring Security 7.1.1** where the BFF keeps tokens (`HttpSessionOAuth2AuthorizedClientRepository`, F8) and why an XHR to a protected BFF endpoint gets a redirect unless an entry point answers 401 (C5); **read from Gateway 5.0.3 `tokenrelay.adoc`** what `TokenRelay` forwards (F9; refresh behavior only after C11). Angular's side: relative `/api` URLs on the BFF's origin (41 §1: no CORS), no `Authorization` header, a full-page navigation to start login.
- **Code:** (1) Java: a `SecurityFilterChain` with `oauth2Login(withDefaults())`, `csrf((csrf) -> csrf.spa())` (§6) and a 401 entry point for `/api/**` (only what F8, F16, F17 and C5 read; banner); (2) YAML: a Gateway route with `TokenRelay=` (F9) and the session cookie attributes (C3); (3) TypeScript: the BFF client and its login navigation (Complete from labs/angular `concepts/bff-client.ts`).
- **Callouts:** **Coming from the backend** (required: SYLLABUS names Spring Security's OAuth2 client and Gateway): the BFF is a classic server-side OAuth web app with an API proxy; **where it breaks**: the browser still sends the cookie by itself, so CSRF comes back (§6), and every API byte now flows through the BFF (cost and latency; 44 file-level for gateway versus BFF).
- **First-use definitions:** browser-based OAuth client, token-mediating backend, backend-for-frontend (link 33 §8), authorized client, token relay, session cookie (link 09 §6), authentication entry point.
- **Verification:** labs/angular `concepts/{bff-client.ts,section-3-bff.spec.ts}` (`HttpTestingController`; the navigation is an injected function, so no real page load): `Section 3: a BFF call goes to a relative /api URL with no Authorization header`; `Section 3: starting login navigates the whole page to /oauth2/authorization/<registration>` (the path as C5 reads; else the plan's registration path is labeled our BFF's); `Section 3: the token-mediating variant attaches the access token it was handed, the BFF variant never holds one`.
- **Questions drilled:** Q42.08, Q42.09.
- **Misconceptions:** "a BFF needs no CSRF protection" (cause: there is no token in the page; the cookie is ambient, 33 §8's bullet linked once); "the token-mediating backend is as safe as a BFF" (cause: refresh tokens stay on the server; the access token still reaches the page, F6 §6.2); "set the session cookie on the parent domain so all subdomains share it" (cause: convenience; RFC 10017 says SHOULD NOT set `Domain`, F6, and `__Host-` forbids it, 09 §6); "`TokenRelay` makes the gateway the resource server" (cause: it sits in front of the API; it forwards the user's token, and each service still validates it, §5).

### 4. Refresh tokens: rotation, reuse detection, silent renew and refreshing across tabs · delta 400 · SEC-M42-04 (Opus)
- **Problem:** a refresh token copied by XSS keeps working for weeks; two tabs refresh at the same moment and one is logged out; silent renew in a hidden iframe stopped working in a browser that blocks third-party cookies; a public client on Spring Authorization Server never receives a refresh token (F13).
- **Model:** a **refresh token** trades for new access tokens (27 §7 defines it; how the client uses it on 401 is 27's); **rotation** issues a new refresh token on every use and invalidates the old one; **reuse detection** remembers the family, so a replayed old token (attacker or a racing tab) revokes the active one and forces a new login (RFC 9700 §4.14, F5); public clients MUST rotate or sender-constrain (F5; DPoP, RFC 9449, one clause). **Silent renew** reran the authorization request in a hidden iframe using the IdP's session cookie, which is a third-party cookie inside the app's page, so blocking third-party cookies made refresh tokens "significantly more attractive" (F6). **Across tabs**, one tab's rotation invalidates the token another tab holds; serialize refreshes (the Web Locks API, as `angular-auth-oidc-client`'s `useRefreshTokenLock` does, F21; C14) or share the result. Spring Authorization Server: rotation is off by default (`reuseRefreshTokens(true)`, F11), it answers an unknown or inactive refresh token with `invalid_grant` (F12), the planner saw no family revocation (C6), and it issues no refresh token to a public client on the code grant (F13, C7). Analogy: a hotel key card that is re-coded each time you use it; if an old card is tried, the desk cancels all cards for the room. Diagram: `stateDiagram-v2`: `Active(RT1)` → refresh → `Active(RT2)` with RT1 `Used`; `Used` presented → `Revoked family` → login required.
- **Mechanism:** **read from Spring Authorization Server 7.1.1** (F11-F13) to answer "what does Spring do with a replayed refresh token?" (and what it does not, C6); our `token-family.ts` model implements RFC 9700 §4.14 and the tests show the difference; **read from `angular-auth-oidc-client` 22.0.2** the defaults (`useRefreshToken: false`, so silent renew is the default path; `allowUnsafeReuseRefreshToken: false`; `useRefreshTokenLock`, F21) and from `angular-oauth2-oidc` that code flow needs `useSilentRefresh` or `refreshToken()` (F20).
- **Code:** (1) TypeScript: our `TokenFamily` (`issue`, `refresh(token, now)` with rotation and reuse detection; Excerpt of `concepts/token-family.ts`); (2) the cross-tab refresh with `navigator.locks.request` (Excerpt of the §4 test's helper); (3) YAML: `reuse-refresh-tokens: false` for a client on Spring Authorization Server (F11; banner).
- **Callouts:** **Framework vs platform** (the line is blurred by the libraries): rotation and reuse detection are the authorization server's; the client library only stores, serializes and sends; the Web Locks API is the browser's. **Coming from the backend**: an optimistic lock on a version column; **where it breaks**: the server cannot tell the attacker from the legitimate client, so it revokes both (F5).
- **First-use definitions:** refresh token (link 27 §7), rotation, token family, reuse detection, sender-constrained token, DPoP (one clause), silent renew, third-party cookie (link 09 §6), Web Locks API.
- **Verification:** `labs/ts-js/src/modules/42-fullstack-authentication/concepts/{token-family.ts,section-4-refresh.test.ts}` (our model of RFC 9700 §4.14, C18; `now` passed in): `Section 4: each refresh returns a new refresh token and the old one stops working`; `Section 4: replaying a used refresh token revokes the whole family`; `Section 4: without rotation a stolen refresh token keeps working beside the real one`; `Section 4: two tabs refreshing under one Web Lock make one refresh call` (Node 24 `navigator.locks`, F25).
- **Questions drilled:** Q42.10, Q42.11, Q42.12. Practised in Exercise 42.2.
- **Misconceptions:** "refresh tokens are too dangerous for SPAs" (cause: early guidance; RFC 9700 allows them for public clients when rotated or sender-constrained, F5); "rotation alone stops theft" (cause: the old token dies; the attacker may use the new one first, and only reuse detection notices the second use, F5); "Spring Authorization Server rotates by default" (cause: rotation is the BCP; `reuseRefreshTokens` defaults to `true`, F11); "silent renew is just a background refresh" (cause: it looks like one; it is a full authorization request in an iframe that depends on the IdP's cookie, F6).

### 5. Spring Security as a resource server: validating JWTs and turning scopes into authorities · delta 400 · SEC-M42-05 (Opus)
- **Problem:** the API accepts a token issued for another service of the same IdP; tokens expired a few seconds ago are still accepted and someone files it as a bug; an IdP that sends `typ: at+jwt` is rejected after an upgrade; `hasRole('ADMIN')` never matches although the token says `roles: ["admin"]` (33:884 handoff).
