### 1. Measure first: the loop, lab versus field, and what each tool answers · delta 850 (750 + 100 verification paragraph) · SEC-M31-01 (Opus)
- **Problem:** a team adds OnPush to every component and `trackBy` to every list after a complaint that "the app is slow"; nothing changes, because the slow part was a 1.2 MB initial bundle on a phone; another team ships a "fix" whose Lighthouse score rose while real users' INP (link 08) got worse.
- **Model:** the **performance loop**: pick a user-visible symptom (a slow first view, a slow interaction, growing memory), **measure** it where it happens (field data for "who and how often", the lab for "why"), form a hypothesis, change one thing, measure again with the same instrument. Each tool answers one question: **field data** (CrUX, real user monitoring with `web-vitals`; 08 §6 owns the metrics) "how bad, for whom"; **Lighthouse** "what does one controlled load look like, and which audits fail"; the **Chrome Performance panel** "what did the main thread do, frame by frame"; the **Angular DevTools profiler** (21 §8 owns its mechanics; dev build only, 12 §5) "which components' change detection took the time"; the **Memory panel** (§8) "what is retained". Analogy: a doctor: the patient's history (field), a lab test (Lighthouse), an ECG during exercise (Performance panel), a specialist scan (Angular profiler). Diagram: `flowchart LR`: `symptom` → `"field data: how bad, for whom"` → `"lab: why (Lighthouse, Performance panel, Angular profiler)"` → `"one change"` → `"measure again (same tool)"` → back to `symptom`. **What to notice:** the loop starts and ends with the same measurement; a change without a before-and-after is a guess.
- **Mechanism:** F11 (the Angular docs' three groups and "profile your application first"), the dev-versus-production split (12 §5: DevTools needs a development build; production numbers come from the production build, which is why this module's browser tests run it, Lab decision 1), what a lab run cannot see (08 §6: no interaction means no INP; link Q08.17, not retold), what only field data has (devices, networks, the 75th percentile, 08); **read from the `@angular/build` 22.2.1 source**: the `statsJson` description in `schema.json` (F3) as the reason the build itself is the first measuring tool for load size (bridge to §6). ### 10. Rendering strategy as a performance decision: CSR, SSR and SSG · delta 450 · SEC-M31-10
- **Problem:** a marketing page built as a client-only SPA shows a blank screen until 400 KB of JavaScript runs (poor LCP on phones); a dashboard behind login gets server-rendered at high server cost for no visible gain.
- **Model:** where HTML is produced decides **when the first content can paint**: **CSR** (client-side rendering) waits for the JavaScript; **SSR** (server-side rendering) sends HTML per request, so content paints before the app boots, then hydration makes it interactive; **SSG** (static generation, prerendering) builds the HTML once at build time. Each moves cost between the user's device, the server and the build. Analogy: a kit to assemble at home (CSR), a meal cooked to order (SSR), and a ready meal from the shelf (SSG). Diagram: `timeline` or `flowchart LR` with three lanes: `CSR: HTML shell → JS → render → paint`, `SSR: render on server → HTML paints → JS → hydrate`, `SSG: prebuilt HTML paints → JS → hydrate`. **What to notice:** SSR and SSG move the first paint earlier; none of them removes the JavaScript the page needs to become interactive.
- **Mechanism:** the decision only (what each does to LCP and to INP during hydration, server cost, caching, personalization), with every mechanism (`@angular/ssr`, `RenderMode`, hydration, incremental hydration, event replay) a pointer to [32](../../modules/32-ssr-ssg-hydration.md) (C7); the Angular docs' SSR row in F11; **read from the `@angular/core` 22.2.1 typings or the docs**: one sentence the task can source on why hydration reuses server DOM instead of re-rendering (else drop, link 32).
- **First-use definitions:** CSR, SSR, SSG (prerendering), hydration (one clause, link 32), TTFB (time to first byte, one clause, link 08 if it defines it).
- **Verification:** no lab (this lab has no SSR; 32 owns it); every claim cited (docs, dated) or linked; the section says so in one sentence.
- **Questions drilled:** Q31.26.
- **Misconceptions:** "SSR always makes an app faster" (cause: earlier first paint; it adds server time per request and hydration work on the device, so a logged-in dashboard may gain nothing); "SSG is only for blogs" (cause: static sites; any page whose HTML is the same for everyone and changes rarely can be prerendered, 32); "SSR fixes a slow interaction" (cause: "fast page"; INP depends on the client's JavaScript, which SSR does not remove).

### 11. Under the hood: the CDK's rendered range, `NgOptimizedImage`'s `srcset` and the builder's chunks · delta 650 · SEC-M31-11 (Opus)
