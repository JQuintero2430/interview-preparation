### 1. CORS on both sides: Spring's `CorsConfigurationSource`, Spring Security, preflight caching, credentials and the dev proxy · delta 480 (380 + 100 verification paragraph) · SEC-M41-01 (Opus)
- **Problem:** the Angular app on `http://localhost:4200` calls `http://localhost:8080/api/orders`; curl works, the browser shows a CORS error; someone adds `@CrossOrigin` and the GET works but every POST's preflight gets 401 from Spring Security; in production a cookie session stops working when the API moves to `api.example.com`, and a download's file name reads `null`.
- **Model:** the browser enforces, the server declares (09 §5 owns the browser side; one sentence and a link). The Spring side has **one source of truth**, a `CorsConfigurationSource` (a `UrlBasedCorsConfigurationSource` mapping paths to `CorsConfiguration`s), which both Spring MVC and Spring Security read (F2, F4); the **preflight** must be answered before authentication because it carries no cookies or `Authorization` (F4 quote). **Credentials** forbid `"*"` origins (F2, F3: `validateAllowCredentials` throws); `allowedOriginPatterns` is the escape (F2). **Preflight caching**: `maxAge` (30 min with `@CrossOrigin` or the permit defaults, unset on a bare `CorsConfiguration`, F2, F3; browser default and caps are 09's, C4). **Exposed headers** (F6b): `Content-Disposition`, `ETag`, `Deprecation` need `Access-Control-Expose-Headers`. The **dev proxy** (F5) makes the browser see one origin, so there is no CORS at all in development; production uses a reverse proxy or gateway (44, file-level). Analogy: a club's guest list kept at the door (the browser checks it), written by the venue (the server); the proxy is walking in through the staff entrance of the same building. Diagram: `sequenceDiagram`: Browser → OPTIONS preflight → CORS processing (allowed?) → 200 with `Allow-*` and `Max-Age` → actual POST with cookie → CORS headers → Spring Security authentication → controller; an `alt` lane: dev server proxy forwards `/api/**` same-origin.
- **Mechanism:** **read from Spring Security 7.1.1 `cors.adoc`** to answer "why does the preflight get 401 when only `@CrossOrigin` is set?": the security filter chain runs before Spring MVC's handler mapping sees `@CrossOrigin`, the preflight has no credentials, and Spring Security handles CORS only when `.cors(…)` is configured, auto-configuring it "only if a `UrlBasedCorsConfigurationSource` instance is present" (F4; C1 for Boot's default chain); **read from `spring-web` 7.0.9 `CorsConfiguration`** why `"*"` plus credentials fails at startup rather than in the browser (F3). The proxy: Vite's `server.proxy` behind `proxyConfig`, path-matching rules (F5).
- **Code:** (1) Java: a `@Bean UrlBasedCorsConfigurationSource` with explicit origins (from configuration), methods, headers, `setAllowCredentials(true)`, `setExposedHeaders(List.of("Content-Disposition", "ETag"))`, `setMaxAge(3600L)` (Partial-equivalent banner; F2-F4); (2) Java: a `SecurityFilterChain` with `.cors(withDefaults())` (F4); (3) `proxy.conf.json` and the `angular.json` `proxyConfig` option (F5); (4) TypeScript: an `environment`-free relative base URL (`/api`) so the same build works behind the dev proxy and the production reverse proxy (Excerpt from the §1 spec's host file if one is created; else Partial).

- **First-use definitions:** origin and preflight (link 09 §5), credentialed request (link 09 §5), `CorsConfigurationSource`, origin pattern, exposed header, dev-server proxy, reverse proxy (one clause; 44).
- **Verification:** documented (F2-F5, F6b, dates) for the Spring and proxy claims; labs/angular `concepts/section-1-cors.spec.ts` (real fetch backend with `vi.stubGlobal('fetch', stub)`, F21): `Section 1: withCredentials makes the fetch backend send credentials include`; `Section 1: without withCredentials the request leaves the credentials mode to fetch's default` (exact value as the run shows: the task asserts the `init.credentials` the stub receives); `Section 1: a relative /api URL is sent as written, so a proxy can serve it from the same origin`.
- **Questions drilled:** Q41.01, Q41.02, Q41.03.
- **Misconceptions:** "add `@CrossOrigin` and CORS is done" (cause: it works for GETs without security; with Spring Security the preflight never reaches MVC unless `.cors()` is configured, F4); "`allowedOrigins("*")` with credentials is fine in dev" (cause: browsers' older leniency stories; Spring rejects it at configuration time, F3, and the browser rejects `*` with credentials, 09 §5); "CORS is a server security feature" (cause: it is configured on the server; the browser enforces it and curl ignores it, 09 §5); "the proxy works in production too" (cause: `ng serve` feels like a server; the dev server is not the production artifact, F5's "development server", and production needs a reverse proxy or gateway, 44).

### 2. DTO contracts: what crosses the wire, absent versus `null`, and checking responses at the boundary · delta 350 · SEC-M41-02
- **Problem:** a controller returns the JPA entity; a new `passwordHash` column ships to every browser, a lazy relation throws during serialization, and renaming a column breaks the Angular build three teams away; a PATCH that sends `{ "middleName": null }` and one that omits it both clear the field.
- **Model:** a **DTO** (data transfer object) is the contract type, separate from the entity, mapped at the controller edge; the JSON is the contract, not the Java or TypeScript class; **absent versus `null`** is a third state a PATCH must model (01 §7, 01:486's handoff); the client checks the shape at its edge because TypeScript types are erased (link 07 §8 and Q07.16 once; Q07.17 owns Zod's unknown-key modes). ### 4. Evolving the contract: compatible changes, API versioning in Spring Framework 7 and deprecation headers · delta 340 · SEC-M41-04
- **Problem:** the backend adds a `REFUNDED` status and an Angular `switch` with an exhaustive `never` check throws in production; a field becomes required and week-old tabs (37 §6) post bodies without it; the team copies controllers into `/v2` with no way to tell clients `/v1` is going away.
- **Model:** **compatible** changes (add an optional field, add an endpoint, widen what is accepted) versus **breaking** ones (remove or rename, make optional required, narrow a type, add an enum value a strict client rejects); a **tolerant reader** on both sides (Jackson's `FAIL_ON_UNKNOWN_PROPERTIES` off, F14; the client ignores unknown members and keeps a fallback branch for unknown enum values); **versioning** when a break is unavoidable: path, header, query parameter or media type, which Spring Framework 7 resolves through `ApiVersionStrategy` (F10); **retiring** a version with `Deprecation` (RFC 9745, F11) and `Sunset` headers. Analogy: a power socket standard: new appliances may add features, but a plug that changes shape needs an adapter period. Diagram: `flowchart TD`: change → compatible? → yes: ship, client ignores the unknown → no: new version → old version sends `Deprecation`/`Sunset` → clients migrate → remove.
- **Mechanism:** **read from Spring Framework 7.0.9's versioning docs** (F10) to answer "how does Spring pick the controller method for `X-Version: 1.3`?": the resolver extracts, the parser makes it comparable, validation rejects unsupported versions with 400, and mapping takes the highest `version` at or below the request among `"1.2+"`-style baselines; the deprecation handler adds the headers (F10, F11). Exact configurer method names only after C3. Angular side: a functional interceptor adds the version header to API URLs only and reports a `Deprecation` header once (reading it cross-origin needs it exposed, §1, F6b).
- **Code:** (1) Java: `@GetMapping(path = "/orders/{id}", version = "1.2+")` (F10) and `spring.mvc.apiversion.use.header: X-Version` (F8; YAML fence); (2) TypeScript: the version interceptor (Complete from labs/angular `concepts/api-version.interceptor.ts`); (3) the unknown-enum fallback (Excerpt).
- **Callouts:** **Coming from the backend**: semantic versioning of a Maven artifact versus an HTTP API (link Q38.17 once for library versioning); **where it breaks**: you cannot force deployed browsers to upgrade; old tabs keep sending old requests until reloaded (37 §6).
- **First-use definitions:** backward-compatible change, breaking change, tolerant reader (defined in §2; link back), API version, baseline version (Spring's `"1.2+"`), deprecation header, sunset.
- **Verification:** labs/angular `concepts/{api-version.interceptor.ts,section-4-versioning.spec.ts}` (`HttpTestingController`): `Section 4: the version interceptor sets the version header on API requests only`; `Section 4: a Deprecation response header is reported once per endpoint`; `Section 4: an unknown status value maps to the fallback label instead of throwing`. Spring: documented (F10, F11, C3).
- **Questions drilled:** Q41.08, Q41.09.
- **Misconceptions:** "adding an enum value is backward compatible" (cause: it is additive on the server; a client that switches exhaustively or validates with a closed enum breaks); "put `/v1` in every URL from day one" (cause: copying public APIs; versioning is a cost you pay when a break is unavoidable, and Spring 7 supports header and media-type schemes too, F10); "Once true: Spring had no built-in API versioning" (until Spring Framework 7.0, only after C16's `@since` read; otherwise phrase as "Spring Framework 7.0.9 documents built-in API versioning").

### 5. Error contracts with `ProblemDetail` (RFC 9457) and mapping them in Angular · delta 420 · SEC-M41-05 (Opus)
- **Problem:** every endpoint invents its own error JSON (`{ "error": … }`, `{ "message": … }`, an HTML page from the proxy); the Angular mapping layer (27 §5) grows a branch per endpoint; a validation 400 from Spring says only "Invalid request content." and the form cannot tell which field failed; a failed PDF download shows "[object Blob]".
- **Model:** a **problem detail** (RFC 9457, F9) is one JSON shape for errors: `type` (a URI naming the problem kind; `about:blank` when absent), `title`, `status`, `detail`, `instance`, plus **extension members** (for example `errors` with JSON Pointers); Spring renders it from `ProblemDetail`/`ErrorResponse` through `ResponseEntityExceptionHandler` (F6, F7); Angular receives it in `HttpErrorResponse.error`, **parsed according to the request's `responseType`** (F19), and maps the `type` (not the message) to UI errors (27 §5 owns the mapping layer). Lost updates and retried writes are part of the error contract: `If-Match` with an `ETag` → 412 (F16; 28:1084), and a client-generated key the server deduplicates (C15; 04:491, 27:1620). Analogy: a standard incident report form every department fills in the same way, with an appendix per incident kind. Diagram: `sequenceDiagram`: exception → `ResponseEntityExceptionHandler` → `ProblemDetail` (+ `errors`) → Jackson → `application/problem+json` → fetch backend `parseBody` by `responseType` → mapping layer → UI.
- **Mechanism:** **read from `spring-web` 7.0.9** (F7) to answer "why does the default validation 400 have no field list?": `MethodArgumentNotValidException`'s body is `forStatusAndDetail(BAD_REQUEST, "Invalid request content.")`, so field errors must be added as a property (`setProperty("errors", …)`, unwrapped to a top-level member by the Jackson mixin, F6); `type` is unset by default (F7), so clients fall back on `status`; Boot's `spring.mvc.problemdetails.enabled` is `false` by default (F8). **Read from `@angular/common` 22.2.1 `FetchBackend.parseBody`** (F19, internal) why a blob download's problem arrives as a `Blob`, and why a 502 HTML page arrives as a string on a JSON request. 27's `fields` placeholder is this contract's `errors` (one sentence, link Q27.16).
- **Code:** (1) Java: a `@RestControllerAdvice` extending `ResponseEntityExceptionHandler` overriding `handleMethodArgumentNotValid` to add `errors` with pointers and a `type` URI (banner; method signature read in `spring-webmvc` 7.0.9 before writing); (2) TypeScript: `isProblemDetail` and `readProblem(error: unknown): Promise<Problem | null>` handling object, string and `Blob` (Complete from labs/angular `concepts/problem-details.ts`); (3) the stubbed-fetch spec setup (Excerpt).

### 6. Pagination, sorting and filtering: offset versus cursor, and how Spring Data serializes a `Page` · delta 330 · SEC-M41-06
- **Problem:** an orders table shows a row twice when someone inserts while the user pages; page 5,000 takes seconds; after a Spring Data upgrade the client's `pageable.pageNumber` is gone and the paginator shows "page undefined".
- **Model:** **offset pagination** (`page`, `size`, `sort`; total count) is simple and supports jumping to page N, but shifts under inserts and costs more on deep pages; **cursor (keyset) pagination** returns a position after the last item (Spring Data's `Window` and `ScrollPosition`, F13) and is stable under inserts and cheap on deep pages, but cannot jump and usually has no total. **Sorting and filtering** are part of the contract: an allow-list of sort properties, a stable tiebreaker, and filters as named parameters. Spring Data's `Page` should cross the wire as **`PagedModel`** (`content` + `page` metadata, F12), not as `PageImpl`. Analogy: page numbers in a printed phone book (offset) versus a bookmark (cursor). Diagram: `flowchart TD` two lanes: offset request `?page=2&size=20&sort=createdAt,desc&sort=id,desc` → `Pageable` → `Page` → `PagedModel` JSON; cursor request `?after=<key>&size=20` → `ScrollPosition.forward(keys)` → `Window` → `{ items, next }` (our DTO).
- **Mechanism:** **read from `spring-data-commons` 4.1.1** (F12) to answer "why did the page JSON change on an upgrade?": returning `Page` serializes `PageImpl` directly (`DIRECT`, the default for backward compatibility), whose JSON is not a stable contract; `VIA_DTO` or returning `new PagedModel<>(page)` gives `{ content, page: { size, number, totalElements, totalPages } }`; Boot exposes `spring.data.web.pageable.serialization-mode` (default `DIRECT`) and the parameter names and limits (`max-page-size` 2000, F8). Cursor: the position is exclusive and needs a stable sort (F13). Angular side: one `PageRequest` to `HttpParams` with repeated `sort` (owner 27 §3 for immutable params), empty filters omitted.
- **Code:** (1) Java: `@EnableSpringDataWebSupport(pageSerializationMode = VIA_DTO)` and a controller returning `PagedModel<OrderDto>` (banner; F12); (2) TypeScript: `toPageParams()` (Complete from labs/angular `concepts/page-params.ts`); (3) the `PagedModel` and cursor response types with their mappers (Excerpt).
- **Callouts:** **Coming from the backend**: `Pageable` and `Page` versus the JSON the client sees; **where it breaks**: the client sees only the serialized form, so a Java type's getters become the contract unless a DTO fixes it.

- **Verification:** labs/angular `concepts/{page-params.ts,section-6-pagination.spec.ts}` (`HttpTestingController`): `Section 6: page, size and two sort orders become page, size and repeated sort params`; `Section 6: an empty filter is left out of the query`; `Section 6: a PagedModel response maps to items and page metadata`; `Section 6: a cursor response maps to items and the next cursor`. ### 8. Files: multipart and chunked uploads, progress, and downloads with `Content-Disposition` and streaming · delta 360 · SEC-M41-08
- **Problem:** a 5 MB upload fails with 413 on a default Boot app; a 2 GB video upload restarts from zero after a network blip; a CSV export downloads as `download` with no extension, or freezes the tab because the whole file sits in memory as a `Blob`.
- **Model:** **multipart/form-data** for files plus metadata (`@RequestPart`, `MultipartFile`; Boot's limits 1 MB per file and 10 MB per request by default, F8; exceeding them is a 413 `ProblemDetail`, F7); **chunked, resumable upload** for large files: the client slices the file and sends parts with their byte range, the server reports what it has, and a failed chunk is retried alone (C5: our protocol unless a standard is read); **progress** is 27 §9's (upload progress needs `withXhr()`, F19). **Downloads**: a link the browser follows (streams to disk, sends cookies, no `Authorization` header), a `Blob` through `HttpClient` (`responseType: 'blob'`, `observe: 'response'` to read headers; whole file in memory) or a streamed server response (`StreamingResponseBody`, F16); the file name comes from `Content-Disposition` (`filename*` wins, RFC 6266, F16), which must be exposed cross-origin (F6b). Analogy: moving house in one truck (multipart) versus numbered boxes you can resend (chunks). Diagram: `sequenceDiagram`: upload: client → POST chunk 1 (`Content-Range`) → server stores, answers offset → chunk 2 fails → client retries chunk 2 → complete; download: client → GET → `Content-Disposition` + exposed header → blob or browser download.
- **Mechanism:** **read from `@angular/common` 22.2.1** (F19) to answer "why can't Angular tell me the file name?": `HttpClient` has no `Content-Disposition` handling, and the header is not CORS-safelisted (F6b), so the server must expose it and the client must parse it; **read from `spring-web` 7.0.9 `ContentDisposition`** (F16) how the server writes `filename*` for non-Latin names. Streaming responses and server push are 43's for events (one sentence).
- **Code:** (1) Java: an upload endpoint with `@RequestPart("file") MultipartFile file` and a download returning `ResponseEntity<StreamingResponseBody>` with `ContentDisposition.attachment().filename(name, StandardCharsets.UTF_8)` (banner; signatures read in 7.0.9 before writing); (2) `application.yml` multipart limits (F8); (3) TypeScript: `parseContentDisposition()` (Complete from labs/angular `concepts/content-disposition.ts`); (4) the chunk planner (Excerpt).
- **Callouts:** **Framework vs platform** (required: `HttpClient` versus `fetch`): `fetch` can stream a response body as it arrives; `HttpClient`'s `Blob` arrives whole; a plain link lets the browser stream to disk.
- **First-use definitions:** multipart/form-data, part, chunked upload, resumable upload, `Content-Range`, `Content-Disposition`, `filename*`, streaming response.
- **Verification:** labs/angular `concepts/{content-disposition.ts,chunk-plan.ts,section-8-files.spec.ts}`: `Section 8: filename* wins over filename and is percent-decoded as UTF-8`; `Section 8: a header without a file name gives the fallback name`; `Section 8: a blob download reads Content-Disposition through observe response`; `Section 8: a file is planned into chunks whose byte ranges cover it exactly once`; `Section 8: a 413 problem from the upload limit maps to a file-too-large message`.
- **Questions drilled:** Q41.17, Q41.18 (and Q41.03's exposed header).
- **Misconceptions:** "set a larger limit and multipart handles any file" (cause: it works in tests; one request still restarts from zero on failure and holds a connection for minutes, so large files need chunks); "`responseType: 'blob'` is the way to download" (cause: it gives you the data; a link or a streamed response avoids holding the whole file in memory and keeps the browser's download UI); "the browser reads `Content-Disposition` for you in `HttpClient`" (cause: it does for navigations; for `HttpClient` the header is only data, and cross-origin it is hidden unless exposed, F6b, F19).

### 9. Dates, time zones, decimals and money across the wire · delta 340 · SEC-M41-09
- **Problem:** an order placed at 23:30 in Madrid shows the next day in New York; a delivery date `2026-10-20` shows as the 19th (34 §10's test, linked); a price of `19.90` arrives as `19.9`, a total of `12345678901234567.89` arrives rounded, and a 64-bit ID loses its last digits.
- **Model:** pick a wire type per meaning: an **instant** (`Instant`, `OffsetDateTime`) as an ISO 8601 string with `Z` or an offset; a **calendar date** (`LocalDate`) as `YYYY-MM-DD` with no zone, never turned into a `Date` at midnight; a **time zone** as an IANA name when the user's zone matters; **money** as a decimal string or integer minor units **plus** an ISO 4217 currency code (01 §2 and Q01.09 own the in-memory side; 34 §10 owns display); **64-bit IDs** as strings (01:704). Analogy: a meeting invite says "15:00 UTC" (instant) while a birthday card says "October 20" (calendar date); converting the card to a time in one zone moves the birthday. Diagram: `flowchart LR`: Java type → Jackson 3 JSON → `JSON.parse` result → client representation: `Instant` → `"…Z"` → string → `Date` or epoch ms; `LocalDate` → `"YYYY-MM-DD"` → string kept; `BigDecimal` → number or string → string → minor units; `Long` → number or string → string.
- **Mechanism:** **read from Jackson 3.1.5 `DateTimeFeature`** (F14) to answer "why do older Spring apps send dates as numbers?": `WRITE_DATES_AS_TIMESTAMPS` was enabled in Jackson 2 and is disabled in 3.0 ("Once true … until Jackson 3.0", from the source comment); `BigDecimal` and `Long` are JSON numbers by default (C7), and `JSON.parse` turns every number into a double (01 §2), so precision is lost before Angular code runs; the server can write them as strings (`@JsonFormat(shape = STRING)` only after C7). `Accept-Language`: one sentence through problem-detail message codes (F6, C12).
- **Code:** (1) Java: a DTO with `Instant placedAt`, `LocalDate deliveryDate`, `@JsonFormat(shape = JsonFormat.Shape.STRING) BigDecimal total` (banner, after C7) and a `currency` field; (2) TypeScript: the codecs `parseInstant`, `keepLocalDate`, `decimalToMinor` (Complete from `labs/ts-js/.../concepts/wire-codecs.ts`).
- **Callouts:** **Coming from the backend**: `java.time` types versus JavaScript's single `Date`; **where it breaks**: JavaScript has no `LocalDate` or `BigDecimal` in the language (Temporal at most one sentence, C6), so the client keeps strings and converts at the edge.
- **First-use definitions:** instant, calendar date, offset, IANA time zone, ISO 8601, ISO 4217 currency code, minor units (link 34 §10), decimal string.
- **Verification:** `labs/ts-js/src/modules/41-fullstack-api-contracts/concepts/{wire-codecs.ts,section-9-wire-codecs.test.ts}`: `Section 9: an instant string gives the same epoch milliseconds whatever offset it is written in`; `Section 9: a calendar date string is kept as a date and never shifted by a zone`; `Section 9: a decimal string converts to minor units without float drift`; `Section 9: a Long above 2^53 loses digits as a JSON number and keeps them as a string`. 34 §10's tests are linked for display, not re-run.
- **Questions drilled:** Q41.19, Q41.20.
- **Misconceptions:** "send dates as epoch numbers to avoid time-zone bugs" (cause: numbers look unambiguous; an epoch is an instant, and a calendar date has no instant, so the birthday still moves); "`BigDecimal` is safe because Java keeps it exact" (cause: the server is exact; `JSON.parse` on the client is not, 01 §2); "Once true: Spring Boot sends `java.time` values as numeric timestamps" (cause: Jackson 2's default; Jackson 3.0 disabled `WRITE_DATES_AS_TIMESTAMPS`, F14, and Boot 4 uses Jackson 3 by default).
