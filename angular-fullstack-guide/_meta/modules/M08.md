### 1. The critical rendering path: from bytes to pixels · ~600 words · SEC-M08-01
- **Problem:** a page shows a blank screen for two seconds on a slow phone although the HTML arrived quickly; the waterfall shows a stylesheet and a synchronous script in `<head>`.
- **Model:** a pipeline in which some stages wait for others: the parser builds the DOM, CSS builds the CSSOM, and nothing paints until both are ready enough.
- **Mechanism:** parsing and the preload scanner; DOM and CSSOM; why CSS is render-blocking and why a classic script is parser-blocking (and waits for pending CSS); render tree (`display: none` excluded); style → layout → paint → composite (link module 04 §1 for when the step runs); script loading attributes (`defer`, `async`, `type="module"` defers by default, `async` on modules) from the HTML Standard's script-loading figure and MDN; `blocking="render"` only if MDN/HTML Standard confirm its status.
- **Diagram:** Mermaid flowchart of the pipeline with the blocking edges, followed by "What to notice".
- **Verification:** documentation only (HTML Standard "scripting" and the script-attribute figure, web.dev critical rendering path articles, MDN `<script>`). SEC-M08-01 also installs jsdom in `labs/ts-js` (Facts above) and adds `section-1-setup.test.ts` with one `Section 1:` test that proves the jsdom environment runs (for example, `document.createElement` exists and a `DOMContentLoaded`-independent parse of a string with `DOMParser` builds the expected tree). No claim about load timing is made from jsdom.
- **Callout:** *Framework vs platform*: Angular CLI's output (module scripts, `defer`, inlined critical CSS) is decided by the build (link 12, 31); the rules here are the browser's.
- **Questions drilled:** Q08.01, Q08.02.

### 2. Layout, paint and composite: what each change costs · ~600 words · SEC-M08-02
- **Problem:** an animation stutters and a list renders slowly; the profiler shows purple "Layout" blocks repeated inside one task.
- **Model:** each style change re-enters the pipeline at some stage: geometry → layout (then paint and composite), visuals only → paint, `transform`/`opacity` on a composited layer → composite only.
- **Mechanism:** reflow (layout) and repaint triggers; forced synchronous layout: reading `offsetHeight`/`getBoundingClientRect()` after a write; layout thrashing as a read/write interleave in a loop, and the fix (batch reads, then writes; `requestAnimationFrame`); compositor-only properties; `will-change` (what it promises, memory cost, MDN's "last resort" advice); `content-visibility: auto` and `contain-intrinsic-size` (Baseline status from MDN). Link module 17 §4's `afterRenderEffect` phases as Angular's read/write split.
- **Verification:** documentation (web.dev "Avoid large, complex layouts and layout thrashing", "Stick to compositor-only properties", MDN `will-change`, `content-visibility`, CSSWG css-contain). The read-then-write batching code is compiled and run in jsdom only for its *order of operations* (a recorded call log), stated as such.
- **Questions drilled:** Q08.03, Q08.04, Q08.05; Exercise 08.2.

### 3. DOM APIs and observers · ~550 words · SEC-M08-03
- **Problem:** a component re-renders a 500-row table by appending rows one by one and polls the scroll position to lazy-load images.
- **Model:** the DOM is a live tree; batch changes off-tree (`DocumentFragment`), and let the browser tell you about changes instead of polling (observers).
- **Mechanism:** `DocumentFragment` (children move on append, the fragment is left empty); `template.content`; `MutationObserver` (records batched and delivered in a microtask, `takeRecords()`, `disconnect()`); `IntersectionObserver` (root, `rootMargin`, thresholds, asynchronous delivery); `ResizeObserver` (content box versus border box, the loop limit error); one sentence on DOM strings (`input.value`, `dataset`) for module 01's promise.
- **Verification:** `section-3-dom-observers.test.ts` (jsdom): fragment emptied after append, `MutationObserver` delivery after the synchronous code with all records in one callback, `takeRecords()`. `IntersectionObserver` and `ResizeObserver` from the W3C specs and MDN (jsdom lacks both; say so).
- **Questions drilled:** Q08.06, Q08.07.

### 4. Events: propagation, default actions, passive listeners and delegation · ~650 words · SEC-M08-04
- **Problem:** a click handler on a row also opens the row's parent panel; a "fix" with `stopPropagation()` breaks the analytics listener on `document`; a scroll handler makes scrolling janky.
- **Model:** an event travels down (capture), arrives (target), and travels back up (bubble), and every listener on the path can see it; the default action is separate from propagation.
- **Mechanism:** the propagation path computed before dispatch; `eventPhase`; `addEventListener` options (`capture`, `once`, `passive`, `signal` with `AbortController`); `stopPropagation` versus `stopImmediatePropagation` versus `preventDefault` (`cancelable`, `defaultPrevented`); passive listeners (ignored `preventDefault`; the DOM Standard's default-passive rule for `touchstart`/`touchmove`/`wheel` on window, document and body, read from the spec); delegation with `event.target.closest()`; events that do not bubble (`focus` versus `focusin`); `CustomEvent` with `detail`, `bubbles`, `composed`; synthetic `dispatchEvent` is synchronous (link Q04.06 for real clicks).
- **Diagram:** Mermaid sequence or flowchart of capture → target → bubble on a three-level tree.
- **Verification:** `section-4-events.test.ts` (jsdom): listener order, each stop method, `defaultPrevented` with and without `cancelable`, passive `preventDefault` ignored, `once`, `signal` removal, delegation through `closest`, `focus` not bubbling and `focusin` bubbling. The default-passive rule from the DOM Standard (jsdom does not apply it: test and say so if that is what the lab shows).
- **Callout:** *Coming from the backend*: a servlet filter chain also runs outer → inner → outer. **Where the analogy breaks:** every listener on the path runs unless one stops propagation, and stopping is the listener's decision, not the chain's.
- **Questions drilled:** Q08.08–Q08.12; Exercise 08.1.

### 5. Web Components: custom elements, shadow DOM and templates · ~650 words · SEC-M08-05
- **Problem:** a design system must ship a rating widget usable from Angular, React and plain HTML, whose styles do not leak in or out.
- **Model:** a custom element is a class the browser instantiates for a tag; a shadow root is a private subtree with its own style scope, and slots are holes the light DOM fills.
- **Mechanism:** `customElements.define`, naming rule (hyphen), upgrade; lifecycle (`constructor`, `connectedCallback`, `disconnectedCallback`, `attributeChangedCallback` with `observedAttributes`, `adoptedCallback`); attributes versus properties and reflection; `attachShadow` open versus closed (what closed does and does not protect); `<slot>` and named slots, `slotchange`; `:host`, `::slotted`, `::part` and `exportparts`; `<template>`; events crossing the boundary (retargeting, `composed`); declarative shadow DOM (`<template shadowrootmode>`, for server-rendered HTML; Baseline status from MDN).
- **Verification:** `section-5-web-components.test.ts` (jsdom): lifecycle order, `observedAttributes`, closed root gives `null`, slot assignment (`assignedNodes`/`assignedElements`), `slotchange` if jsdom fires it, a composed event retargeted to the host and a non-composed one stopped at the shadow root. Styling (`:host`, `::part`) and declarative shadow DOM from the HTML/CSS specs and MDN (jsdom does not compute these or attach DSD).
- **Callout:** *Framework vs platform*: Angular's default emulated encapsulation rewrites selectors with attributes; `ViewEncapsulation.ShadowDom` uses a real shadow root (owner: 13); Angular Elements wraps components as custom elements (owner: 37).
- **Questions drilled:** Q08.12–Q08.15; Exercise 08.3.

### 6. Core Web Vitals: LCP, INP and CLS · ~500 words · SEC-M08-06
- **Problem:** Lighthouse scores 98 in CI, yet Search Console flags the site's INP as poor.
- **Model:** three user-centred numbers: how soon the main content shows (LCP), how quickly the page responds to input (INP), how much it jumps (CLS), judged at the 75th percentile of real visits.
- **Mechanism:** each metric's definition and the good / needs-improvement / poor thresholds (quoted from web.dev); INP replaced FID (date from web.dev); what makes each one bad (late LCP resource, long tasks and heavy handlers, unsized media and late-inserted content); field data (CrUX, RUM with the `web-vitals` library) versus lab data (Lighthouse, DevTools; Lighthouse cannot measure INP without interaction, TBT as a proxy, verified from web.dev/Chrome docs).
- **Verification:** documentation only (web.dev vitals pages, Chrome for Developers Lighthouse docs). Any version or date claim cites its page.
- **Questions drilled:** Q08.16, Q08.17.

### 7. History API versus Navigation API · ~450 words · SEC-M08-07
- **Problem:** a hand-written router must intercept every link click, listen to `popstate`, and still misses navigations started by the browser's back button in some cases.
- **Model:** the History API changes the URL and stack but leaves interception to you; the Navigation API gives one `navigate` event for every same-document navigation, which you can intercept.
- **Mechanism:** `pushState`/`replaceState` (no event, no request), `popstate` on traversal only, state serialization limits; Navigation API: `navigation.addEventListener('navigate')`, `event.intercept({ handler })`, `navigation.entries()`, `navigation.currentEntry`, `canIntercept`; status marker from MDN (Baseline 2026 newly available, Facts above); what Angular's Router uses today (read from `@angular/router` 22.2.1 source or docs before claiming; owner of details: 24).
- **Verification:** `section-7-history.test.ts` (jsdom with a `url`): `pushState` fires no `popstate`, `back()` is asynchronous and fires `popstate` with the earlier state. Navigation API from the HTML Standard and MDN (jsdom lacks it).
- **Callout:** *Framework vs platform*: the Angular Router sits on top of one of these APIs; link 24.
- **Questions drilled:** Q08.18.

## Exercises (3, ceiling 3)

Each follows the full E1 anatomy, ≤ 480 prose words. Solutions in `labs/ts-js/src/modules/08-browser-rendering-dom-events/<name>.ts` with `<name>.test.ts` (jsdom), `describe('E08.N …')`, one `it` per criterion titled with its text, and mutation checks recorded in the LOG.

1. **Exercise 08.1 · Event delegation helper** (EX-M08-01; section 4). `delegate(root, type, selector, handler)` returns an unsubscribe function; `handler(event, matched)` receives the element that matched. Criteria:
   - a click on a descendant of a matching element calls the handler with that element;
   - clicks that match nothing inside `root` are ignored;
   - elements added after the call are handled;
   - a matching ancestor *outside* `root` does not count;
   - the returned function removes the listener (verified by dispatching after it).
2. **Exercise 08.2 · Batch DOM reads and writes per frame** (EX-M08-02; section 2). `createFrameScheduler(requestFrame = requestAnimationFrame)` with `measure(fn)` and `mutate(fn)`. Criteria:
   - all queued reads run before all queued writes in a frame;
   - many calls in one task request exactly one frame;
   - jobs keep their queue order;
   - a job queued during a flush runs in the next frame;
   - a throwing job does not drop the others (the error is reported after the flush).
   (Tests inject a fake `requestFrame`, so the claim is about order, not about real layout.)
3. **Exercise 08.3 · A `<rating-stars>` custom element** (EX-M08-03; sections 4 and 5; integrates both). Criteria:
   - renders `max` buttons in an open shadow root and exposes them as `part="star"`;
   - `value` and `max` are observed attributes, and the `value` property reflects to the attribute;
   - clicking a star sets `value` and dispatches a `rating-change` `CustomEvent` (`bubbles`, `composed`) with `detail.value`, which a `document` listener receives with the host as `target`;
   - a `value` outside `0…max` is clamped;
   - removing the element from the DOM removes its listeners (no event after removal).
