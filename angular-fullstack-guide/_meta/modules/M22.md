- F3. **Promise versus Observable.** A promise runs its executor at creation and its `then` handlers in a microtask; an observable runs its producer at `subscribe` and `next` synchronously: `["promise executor","both created","observable producer","o next","p then","p then 2"]` (R).

*Anatomy (R):*
- F8. **Teardown and the contract.** Teardown ran on complete, on error and on unsubscribe; `closed` is false before and true after; a second `unsubscribe()` is harmless: `["teardown-complete","error-handler","teardown-error","closed? false","teardown-none","closed after? true"]`. A synchronous complete runs the teardown **after the producer returns** (`["n","c","teardown"]`): `subscriber.add(teardown)` on a closed subscriber runs it at once (r, `Subscription.add`). Notifications after `complete` or `error` are dropped: `["n1","c"]` (R); source `Subscriber.next/error/complete` set `isStopped` and route stopped notifications to `handleStoppedNotification` (r); `config.onStoppedNotification` "noop by default" (r, `config.d.ts`).
- F9. **Synchronous sources.** `infinite.pipe(take(3))` with `while (!s.closed) s.next(i++)` delivered `[0,1,2,"c"]`, the loop exited at 3 and the teardown ran (R). `const sub = of(1).subscribe(() => sub.unsubscribe())` does not throw at subscribe: the temporal-dead-zone `ReferenceError` ("Cannot access 'sub' before initialization") is caught by the library and reported later (R); for an unbounded synchronous source the same mistake never stops it (observed as a hang in a first probe, then replaced by `take`).
- F10. **Handler errors are reported later.** An error thrown in a `next` handler and an `error` notification with no `error` handler did not throw from `subscribe`; with `config.onUnhandledError = fn` the function ran on a later job: `["sync-marker","no error handler","handler threw"]`; without it, Node reported an `uncaughtException` (R). - F11. **Producers and operators that throw.** `new Observable(() => { throw })` delivered an `error` notification (R); a throw inside `map`'s projection became `error` (`[1,"E:projection"]`, R); source `OperatorSubscriber` wraps `onNext`, `onComplete` in `try { … } catch (err) { destination.error(err) }` and `Observable._trySubscribe` catches the producer (r). *Subjects (R):*
- F20. **Four subjects.** Late subscriber to `Subject`: only later values. `BehaviorSubject(0)`: current value on subscribe (`a0 a1 b1`), `getValue()`/`value` 1, `getValue()` still works after `complete()` and throws the stored error after `error()`; a subscriber after complete gets only `complete`. `ReplaySubject(2)`: a late subscriber got `2,3` then `4`; after complete a new subscriber got `3,4` then `complete`; `new ReplaySubject()` is unbounded; `bufferSize` is `Math.max(1, …)` (r, `ReplaySubject.js`). `AsyncSubject`: nothing before `complete`, then the last value to early and late subscribers; after `error` only the error (the value is dropped) (R: `["before complete: 0","early:2","late:2","err x"]`).
- F21. **Edge cases.** `next` after `complete` is ignored (`isStopped` true, `closed` false); after `subject.unsubscribe()` both `next` and `subscribe` throw `ObjectUnsubscribedError` "object unsubscribed"; `asObservable()` returns an Observable that is not a `Subject` and has no `next`; a nested `next` inside a subscriber is delivered depth first (`["A1","A2","B2","B1"]`); a subscriber that unsubscribes another during delivery stops it from being called; an error in one subscriber's `next` does not stop the others and is reported later (F10); `observed` is true while subscribers exist (R). Source `Subject.next` iterates `currentObservers`, a copy of `observers` made lazily (`Array.from`), `_throwIfClosed`, `_checkFinalizedStatuses`, `_innerSubscribe`; `BehaviorSubject._subscribe` emits `_value` only if `!subscription.closed` (r).
- F22. **`EventEmitter` is a `Subject`.** `interface EventEmitter<T> extends Subject<T>, OutputRef<T>`, "Extends RxJS `Subject` for Angular by adding the `emit()` method", `@publicApi`; run under `ng test`: `emit(1)` and `next(2)` both reach the subscriber and `instanceof Subject` is true (r, R ng). `@angular/core/rxjs-interop` exports `outputFromObservable`, `outputToObservable` (`@publicApi 19.0`), `takeUntilDestroyed` (19.0), `toObservable`, `toSignal` and their option types (20.0), `pendingUntilEvent` (`@developerPreview 20.0`), `rxResource` (22.0 tag in the typings) (r). `@angular/core` 22.2.1 peer range `rxjs ^6.5.3 || ^7.4.0` (r).

*Operators (R, r, c):*
- F23. **`pipe`.** `o.pipe()` returns `o`; `pipe(f, g)(x)` is `g(f(x))`; the standalone `pipe` builds a reusable operator (`filter` then `map` gave `[4,8]` for `of(1,2,3,4)`); an operator returns a new Observable and leaves the source alone (R); source `pipeFromArray` returns `identity` for 0 functions, the function for 1, otherwise `fns.reduce((prev, fn) => fn(prev), input)`; `operate(init)` wraps `source.lift(function (liftedSource) { try { return init(liftedSource, this) } catch (err) { this.error(err) } })` and throws `TypeError('Unable to lift unknown Observable type')` for a non-liftable source (r, `util/pipe.js`, `util/lift.js`). ### 1. Push collections: Observables, Promises, iterators and laziness · delta 900 (800 + 100 verification paragraph) · SEC-M22-01
- **Problem:** a click, a socket message and a timer produce many values over time; a Promise delivers one; callbacks scatter the cleanup; a team lead asks why a `subscribe` call somewhere "starts everything again"; a backend developer asks "is this a `Flux`?".
- **Model:** an **Observable** is a lazily executed, push-based collection of zero to many values, delivered synchronously or later. The 2x2 table: **pull** (the consumer asks) versus **push** (the producer decides), **single** versus **multiple**: function, iterator, Promise, Observable (F1 docs). Analogy: a magazine subscription (nothing is printed until you subscribe, and you can stop) against a library trip (you pull) and a letter (one delivery). Diagram: `sequenceDiagram` of consumer, Observable, producer and subscription: `subscribe` starts the producer, `next` x3, `complete`, teardown; a second `subscribe` starts a second producer. **What to notice:** the producer is started by `subscribe`, not by creation, and each subscription has its own run.
- **Mechanism:** laziness and per-subscribe execution (F1, read `Observable.subscribe`); synchronous delivery (F2: "Observables are not async"); Promise contrast (F3: eager executor, microtask `then`, one value, no cancel, link [04 §3](../../modules/04-js-async-event-loop.md#3-promises-from-callbacks-to-a-state-machine) and [§7](../../modules/04-js-async-event-loop.md#7-cancellation-with-abortcontroller)); conversions (F4: `firstValueFrom`, `lastValueFrom`, `EmptyError`, `defaultValue`, they subscribe at once; `toPromise` legacy); what can become an Observable (F5: `from`); what an Observable is not (F6: not thenable, not iterable); an **entry-points table** (pointers, one line each: `HttpClient` 27, `Router.events` 24, `valueChanges` 25, `EventEmitter` §4, the `async` pipe 14 §8, `rxjs-interop` 17 §8 and 23, `outputFromObservable` 19), with the interop export list and statuses read from the typings (F22). ### 2. Anatomy: `Observable`, `Observer`, `Subscription` and teardown · delta 900 · SEC-M22-02
- **Problem:** a producer that opens an interval and a listener leaks both after the consumer leaves; a `subscribe` inside `next` throws a confusing `ReferenceError` later, not at the call; an error in a handler vanishes; a team asks what "complete" guarantees.
- **Model:** four parts. The **Observable** is the recipe (a function `subscribe(subscriber)`); the **Observer** is the consumer's three callbacks (`next`, `error`, `complete`, each optional); the **Subscriber** is the observer plus the guarantees RxJS adds (it stops after complete or error); the **Subscription** is the handle (`unsubscribe`, `closed`, `add`) that owns the **teardown** the producer returns. The **contract**: zero or more `next`, then at most one of `error` or `complete`, then nothing; teardown runs once. Analogy: a phone call: dialing starts the producer, either side can hang up, and hanging up runs the cleanup. Diagram: `stateDiagram-v2` of a subscriber (`active` → `stopped` on complete/error, `active` or `stopped` → `closed` on unsubscribe, with teardown on entering `closed`). **What to notice:** "stopped" and "closed" differ: after complete the subscriber ignores notifications at once, the teardown runs when it closes.

### 3. Cold and hot, unicast and multicast · delta 950 · SEC-M22-03
- **Problem:** two components subscribe to "the same" stream and the server is called twice; a late subscriber misses the value that matters; a `fromEvent` listener is added per consumer; a backend developer expects `Flux` behavior and asks about backpressure.

### 7. Combining streams: `combineLatest`, `withLatestFrom`, `forkJoin`, `zip`, `merge` and `concat` · delta 800 · SEC-M22-07
- **Problem:** a screen needs the latest filter and the latest results; a click should carry the latest price without firing when the price changes; three loaders must all finish before the page renders; a `forkJoin` of live streams never emits; a `zip` of a fast and a slow stream grows without limit.
- **Model:** combination operators differ on three questions: **when do they subscribe** (all at once or one after another), **what do they emit** (the latest of each, pairs by position, one final tuple, every value from any source), **when do they complete**. `merge` interleaves; `concat` queues sources; `combineLatest` re-emits the latest of each when any emits (after all have emitted once); `withLatestFrom` emits only when the **source** emits, with the latest of the others; `zip` pairs the n-th values; `forkJoin` waits for all to complete and emits the last of each; `race` follows the first to emit. Analogy: a conference call (`merge`), a queue at one window (`concat`), a pair of dancers (`zip`), a dashboard (`combineLatest`), and a group photo when everyone has arrived (`forkJoin`). ### 8. Timing operators: `debounceTime`, `throttleTime`, `auditTime` and `sampleTime` · delta 800 · SEC-M22-08
- **Problem:** a search box fires a request per keystroke; a scroll handler fires sixty times a second; a save button is double-clicked; a status panel needs the latest value every quarter second; each fix uses a different operator and each loses a different value.
- **Model:** four operators limit the rate of a burst and differ in **what they keep** and **when they emit**. `debounceTime(d)` waits for silence of `d` and emits the **last** value; `throttleTime(d)` emits the **first** value and ignores the rest for `d` (leading), optionally also the last (trailing); `auditTime(d)` starts a timer on the first value and emits the **last** value when it ends; `sampleTime(d)` emits the **latest** value at each tick, only if one arrived. Analogy: an elevator (`debounce`: leaves when nobody enters for `d`), a turnstile (`throttle`: lets the first through and shuts), a camera with a fixed shutter after the first motion (`audit`), a security guard glancing at the room every `d` (`sample`). Diagram: `flowchart LR` over one burst, one lane per operator showing which input becomes the output (F31 table). **What to notice:** debounce can starve under a steady stream, the others cannot; and what happens to the pending value at complete differs.
- **Mechanism:** the F31 frame tables for the same burst, as text marbles (reading aid, C9) with the rule under each; `throttleTime` config `{ leading, trailing }` (the four combinations run); completion rules (debounce flushes the pending value at complete, audit waits for its duration then completes, sample drops it, throttle with trailing off completes at once); `delay`, `timeout` (`TimeoutError` "Timeout has occurred"), `timer`, `interval`, `bufferTime` as the other time-based members (one run each in F31); which operator for which job (autosave: `auditTime` or `debounceTime` plus a flush; scroll: `throttleTime` leading and trailing or `auditTime`; double-click guard: `throttleTime` leading only; live search input: `debounceTime`, with the flattening half in 23; status panel: `sampleTime`); **read from the source**: `debounceTime.js` re-arms one scheduled task and compares `scheduler.now()` (`emitWhenIdle`), `audit.js` (`isComplete`, `endDuration`); the clock: `asyncScheduler` by default (the `scheduler` parameter is 23's) and why fake timers and `TestScheduler.run` both control it (F31). ### 9. Under the hood: `subscribe`, the subscriber chain and the subject's observer list · delta 800 · SEC-M22-09
- **Problem:** why does unsubscribing downstream stop the source three operators up; why does a throw in `map` reach `error` while a throw in the consumer's `next` is reported later; why does a nested `next` print in a surprising order; how does `share` know when to reset.
- **Model:** `subscribe` builds a **chain of subscribers**: the consumer's observer is wrapped in a `SafeSubscriber`; each operator adds an `OperatorSubscriber` whose destination is the subscriber downstream; the producer is called with the innermost one. Every subscriber is **added to its destination as a child**, so closing a subscriber closes everything upstream of it. A `Subject` is an observer list (`observers` copied to `currentObservers` before delivery); `share` is a reference counter around a `Subject` and a source subscription. Analogy: a string of paper cups on strings: pulling one cup's string releases all the cups behind it. Diagram: `flowchart TD`: `Observable.subscribe` → `new SafeSubscriber` → `errorContext` → `operator.call(subscriber, source)` → the next `OperatorSubscriber` → … → source `_subscribe(subscriber)` → teardown added back with `subscriber.add`; a side box for `Subject.next` copying observers. **What to notice:** every arrow between subscribers is a parent-child link, which is why one `unsubscribe` is enough.
