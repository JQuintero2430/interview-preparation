### 1. What a framework does, and Angular's philosophy · ~600 words · SEC-M12-01
- **Problem:** a team assembles a view library, a router, a form library, an HTTP client, a test runner and a bundler; each upgrade breaks a seam; two teams in the same company make different choices and cannot share code or people.
- **Model:** a library is code you call; a framework calls your code (inversion of control) and owns the program's shape: the entry point, the component model, the build. Angular is "batteries included" (router, forms, HTTP, i18n, testing, CLI, compiler from one team, released together) and opinionated (one way to declare components, DI everywhere, TypeScript first). Analogy: a fitted kitchen versus buying appliances one by one. Diagram: `flowchart LR` of who calls whom: your code calls a library; the framework (CLI build → compiler → runtime → change detection → your component) calls your code. **What to notice:** the framework is in charge of the entry point and the update loop.
- **Mechanism:** the parts Angular ships and that the rest of the module explains (compiler, runtime, CLI and builders, router, forms, HTTP, testing); the lock-step release of the framework packages (the `packageGroup` in `@angular/core`'s `ng-update` field, read: core, common, compiler, compiler-cli, forms, platform-browser, router, …) and the release cadence from angular.dev's releases page (a major every 12 months; deprecations kept for at least one major); what "opinionated" costs (learning curve, fewer choices) and buys (shared conventions, automated migrations, `ng update`).
- **First-use definitions:** framework, library, inversion of control, batteries included, opinionated, CLI (command-line interface), runtime, compiler.
- **Verification:** angular.dev releases page; `@angular/core/package.json` `ng-update.packageGroup` (read). No lab.
- **Callout:** *Coming from the backend* (`> [!TIP]`, optional): Spring Boot's starters and auto-configuration as the "batteries included" analogue; **where it breaks**: Angular's compiler rewrites your classes at build time, Spring proxies at run time.
- **Questions drilled:** Q12.01, Q12.02.
- **Misconception candidates:** "Angular is a library like React" (cause: both render components); "opinionated means you cannot opt out" (cause: early AngularJS and NgModule rigidity; standalone and signals show the current flexibility, link 15/17).

### 2. The CLI and the workspace: `angular.json`, projects, schematics and `ng update` · ~750 words · SEC-M12-02

### 5. The dev loop: `ng serve`, hot module replacement and Angular DevTools · ~550 words · SEC-M12-05

### 6. Bootstrapping: `bootstrapApplication`, the platform and initializers · ~900 words · SEC-M12-06
- **Problem:** a feature flag service is read before its config arrives and the first screen shows the wrong features; an `APP_INITIALIZER` that never resolves leaves a blank page with no error; a team cannot say where "the root injector" comes from.
- **Model:** bootstrap is a **startup sequence**: create (or reuse) the platform, create the application's root environment injector from `ApplicationConfig.providers`, run the initializers and wait for them, then create the root component into its host element and start rendering. ### 8. Under the hood: what the compiler emits and what the runtime does with it · ~1,050 words · SEC-M12-08
- **Problem:** interviewers ask "what is Ivy?", "what is in `ɵcmp`?", "why can Angular lazy-load a single component now?", "why do libraries need a linker?"; without the mechanism the answers are slogans.
- **Model:** each decorator becomes a **static definition on its own class** (`ɵcmp`, `ɵdir`, `ɵpipe`, `ɵprov`, `ɵfac`), and a template becomes **a function of instructions with a create pass and an update pass**; the runtime calls the create pass once per view to build DOM nodes and the update pass on each check to write only changed bindings into slots it remembers. **Locality**: compiling a component needs only that component and what it imports. Analogy: a player piano roll: the roll (template function) is punched once; playing it (create, then update) touches only the keys it lists. Diagram: `flowchart LR`: `counter.ts` → `ngc` → `static ɵfac`, `static ɵcmp = ɵɵdefineComponent({ selectors, inputs, decls, vars, consts, template, dependencies })` → runtime: first render `template(rf=1)` creates nodes in slots 0…decls-1 → later checks `template(rf=2)` with `ɵɵadvance` compares and writes changed bindings. **What to notice:** no virtual DOM tree is built or diffed; the template function itself knows which nodes have bindings.
