### 1. Folder structures that scale: by feature, domain slices, and core, shared and feature boundaries · delta 850 (750 + 100 verification paragraph) · SEC-M38-01
- **Problem:** a two-year-old app with `components/`, `services/`, `models/` folders of 200 files each: a change to "orders" touches seven folders, nobody knows which service a feature owns, and deleting a feature leaves orphans.
- **Model:** group by **feature area** (what the user does: orders, catalog, account), then by **role inside the feature**; three kinds of top-level areas: `core/` (app-wide singletons and setup: providers, interceptors, layout shell, configured once in `app.config.ts`), `shared/` (code with **no** feature knowledge: ui primitives, pipes, utilities) and `features/<name>/` (one lazy route each, 24 §4 link once). Domain slices: a larger feature (a bounded area such as "billing") becomes a folder with its own sub-features. Analogy: a department store: floors by department (features), a back office (core), and shared fittings (shared), never "all shelves on floor 2". Diagram: `flowchart TD`: `app` → `core`, `shared`, `features/orders`, `features/catalog`; arrows show allowed imports (features → shared, core → shared; no feature → feature).
- **Mechanism:** **read from angular.dev/style-guide** (F10) to answer "why does the guide forbid folders by type": the quoted "Organize your project by feature areas" and "Avoid creating subdirectories based on the type of code"; "Unit tests should live in the same directory as the code-under-test." What makes a folder a boundary: only what its `index.ts` (or the feature's route file) exports is used outside (link §4, §6); why standalone removed the need for `SharedModule` (link 15 §5 once; Q15.15 once).
- **First-use definitions:** feature area, domain slice, `core`, `shared`, boundary, lazy route (link 24 §4), barrel file.
- **Verification:** `labs/angular/src/app/modules/38-architecture-and-production-structure/concepts/section-1-folders.spec.ts` (`ng test`): `Section 1: each feature folder is reached only through its lazy route` (the sample app's router config loads `features/orders/routes.ts` and `features/catalog/routes.ts` with `loadChildren`; the spec navigates with `RouterTestingHarness` and asserts the rendered heading, probe first); `labs/ts-js/src/modules/38-architecture-and-production-structure/concepts/section-1-tree.test.ts` (Vitest): `Section 1: no file in one feature folder imports from another feature folder` (scans the `sample-app` tree's `.ts` files with the TypeScript compiler API's `preProcessFile`, read-only).
- **Questions drilled:** Q38.01, Q38.02, Q38.03.
- **Misconceptions:** "`shared/` is where anything used twice goes" (cause: the name; anything with feature knowledge in `shared/` makes every feature depend on every other, so it moves to the feature or to a `ui`/`util` library with no domain imports); "`core/` is a module you import once" (cause: the NgModule-era `CoreModule` with a `forRoot` guard, 15 §5; in a standalone app `core/` is a folder whose providers go into `app.config.ts`); "folders by type are easier to find things in" (cause: small apps; the style guide's reason is that a change touches one folder, F10).

### 2. Smart (container) and presentational components · delta 650 · SEC-M38-02
- **Problem:** an order table component injects the store, the router and `HttpClient`, so it cannot be reused on the dashboard, its test needs five providers, and a change in the API shape breaks a "dumb" table.
- **Model:** a **presentational** component knows nothing about where data comes from: signal inputs in, outputs out, no injected services except presentational helpers (19 §1 link once); a **container** (smart) component injects the facade (§3), reads its signals and passes them down, and turns outputs into facade calls. Analogy: a TV screen and the set-top box: the screen shows whatever arrives on its input; the box knows the channels. Diagram: `flowchart LR`: facade → container → (inputs) presentational list / filter → (outputs) container → facade.
- **Mechanism:** why the split helps under v22: with the OnPush default [Changed in v22.0] a component re-renders when an input changes identity, an event fires in it, or a signal it reads changes (link 21 §2 once, VERSIONS.md); presentational components that take immutable inputs fit that rule, so an in-place mutation is not shown (C4 probe, Q38.05). **Read from angular-eslint 22.6.0** (`prefer-on-push-component-change-detection` description, F11) to answer "why lint no longer asks for `OnPush`": it now flags opting **out** of the default. Testing: a presentational component is tested with `setInput` and output spies, no providers (link 29 §7 once). Base-class components versus composition (03:1032 handoff; link Q20.18 once).
- **First-use definitions:** presentational component, container component, signal input, output (link 19 §1), OnPush (link 21 §2).
- **Verification:** `concepts/section-2-roles.spec.ts` (`ng test`): `Section 2: the presentational list renders only from its inputs and has no injected services` (its `ɵcmp` is not inspected; the spec renders it with `TestBed` and an **empty** `providers` list and asserts rows); `Section 2: the presentational list emits select with the row id`; `Section 2: the container passes the facade's signals to the list and calls the facade on select` (fake facade through a provider); `Section 2: an in-place mutation of the input array is not rendered until the container passes a new array` (probe first, C4).
- **Questions drilled:** Q38.04, Q38.05, Q38.06.
- **Misconceptions:** "presentational components may not inject anything" (cause: the rule is stated too strictly; injecting a presentational helper such as `LiveAnnouncer` or `ElementRef` is fine; injecting state or data access is not); "smart/dumb is a React idea that signals made obsolete" (cause: hooks blurred it in React; the split is about **who knows the data source**, which signals do not change); "every component needs a container" (cause: overapplying the pattern; a leaf used once can read the facade directly when it will never be reused, Q38.06).

### 3. Facades and the data-access layer · delta 750 · SEC-M38-03 (Opus)
- **Problem:** five components each call `HttpClient` for orders with slightly different error handling; replacing the REST endpoint with a store or a cache means editing every component; tests mock `HttpClient` everywhere.
- **Model:** three layers inside a feature: **ui** (presentational), **feature** (containers, routes), **data-access** (HTTP services, the store, mapping DTOs to view models). The **facade** is one class in front of the store and the HTTP service (link 16 §9 once for the pattern): it exposes **read-only signals** (`orders`, `loading`, `error`) and **intent methods** (`load()`, `select(id)`, `cancel(id)`), and hides which store or endpoint sits behind. Analogy: a restaurant's waiter: you order from the menu, you never walk into the kitchen. Diagram: `flowchart LR`: container → facade → store (28 §2) and `OrdersApi` → `HttpClient`; a dashed arrow "test fake" replacing `OrdersApi`.
- **Mechanism:** **read from the lab** and 16 §9: the facade is provided in the feature's route `providers` (one instance per feature, link 24 §4 once) or `providedIn: 'root'`; the store is the 28 §2 service-with-signals (link once; Q28.04 linked, not retold); errors are mapped once at the data-access edge (link 27 §5 once and Q27.16 once); at most four injected dependencies per class (STYLE-GUIDE §7.1) is why a facade appears; an `InjectionToken` for the API port makes the adapter swappable (16 §7 link once). When a facade is overhead: one component, one call (say so). The **required Coming from the backend callout** (C3, with "Where the analogy breaks").
- **First-use definitions:** facade (link 16 §9), data-access layer, DTO, view model, port, adapter, service-with-signals store (link 28 §2).
- **Verification:** `concepts/section-3-facade.spec.ts` (`ng test`, `HttpTestingController`): `Section 3: the facade exposes orders loaded through the data-access service` ; `Section 3: the facade maps an HTTP error to an error state and keeps the previous orders` (probe first, C4); `Section 3: replacing the API token with a fake changes no component code` (the same container rendered with a fake `ORDERS_API` provider).
- **Questions drilled:** Q38.07, Q38.08, Q38.09.
- **Misconceptions:** "a facade is just a store wrapper with extra boilerplate" (cause: facades that forward every store method one-to-one; the value is the narrower, intent-shaped API and the swap point, so a pass-through facade is the anti-pattern); "the facade should expose Observables so components can compose" (cause: pre-signal habits; exposing read-only signals keeps OnPush templates simple, and `toSignal` belongs at the edge, link 28 §2); "data-access means only HTTP" (cause: the name; it also holds the store, caching and DTO mapping).

### 4. Layers, library types and dependency rules · delta 650 · SEC-M38-04
- **Problem:** a `ui` button imports a store selector; a utility imports a component; a feature imports another feature's internal file with `../../`; nothing fails until a refactor breaks three teams.
- **Model:** four **types** (`feature`, `ui`, `data-access`, `util`) and **scopes** (`orders`, `catalog`, `shared`); the rules are a direction: `feature` → `ui`, `data-access`, `util`; `ui` → `ui`, `util`; `data-access` → `data-access`, `util`; `util` → `util`; a scope depends only on itself and `shared`. Analogy: one-way streets: traffic flows downhill, never back. Diagram: `flowchart TD` of the four types with the allowed arrows, plus a crossed-out arrow `ui -.-> data-access`.
- **Mechanism:** how rules are enforced **without** Nx: folder conventions plus a lint rule (ESLint's `no-restricted-imports` with patterns, read from the ESLint docs, C2) or a custom checker (Exercise 38.3); with Nx: tags and `@nx/enforce-module-boundaries` (forward link to §7). **Read from `@nx/eslint-plugin` 23.3.0** (F12) to answer "why a relative `../../` import into another project is reported even if the tags allow it": the rule's first message, "Projects cannot be imported by a relative or absolute path, and must begin with a npm scope". Where `shared` directives and pipes go (14:2206 handoff: `shared/ui` or `shared/util` by whether they render).
- **First-use definitions:** library type, scope, tag, dependency rule, project graph (brief; §7 owns it), relative import.
- **Verification:** `labs/ts-js/src/modules/38-architecture-and-production-structure/concepts/section-4-rules.test.ts` (Vitest, a 30-line rule table in `concepts/rules.ts`): `Section 4: the rule table allows feature to ui, data-access and util`, `Section 4: the rule table rejects ui to data-access and util to ui`, `Section 4: the rule table rejects a scope importing another scope except shared`.
- **Questions drilled:** Q38.10, Q38.11.
- **Misconceptions:** "boundaries need Nx" (cause: Nx made tags popular; folder rules plus `no-restricted-imports` or a checker enforce the same direction in a CLI workspace, at the cost of hand-written patterns); "util may import anything as long as it is small" (cause: size feels harmless; a util that imports a component pulls Angular rendering into every consumer and makes cycles likely); "a cycle between two libraries only matters for the build" (cause: bundlers tolerate many cycles; ng-packagr refuses cycles between entry points (F8), and cycles make initialization order fragile).

### 5. Angular CLI libraries: `ng generate library`, ng-packagr and consuming the build · delta 750 · SEC-M38-05
- **Problem:** two apps copy the same 40 components; each fix lands in one copy; publishing to a private registry is a manual zip.
- **Model:** a **library project** (12 §2 link once; Q12.04 linked) is built by **ng-packagr** into the **Angular Package Format** folder: a `package.json` with `exports`, one FESM bundle per entry point and bundled typings, compiled in partial mode for publishing (12 §8 link once).
