### 1. `HttpClient` versus `fetch`: what the framework adds over the platform · delta 900 (800 + 100 verification paragraph) · SEC-M27-01
- **Problem:** a team calls `fetch` directly in components: every call repeats the `ok` check, JSON parsing and the auth header; a 404 resolves instead of failing ([Q09.03](../../modules/09-web-networking-storage-security.md#q09-03)); requests are not cancelled when the user leaves; tests stub `globalThis.fetch` per file; nobody can add a header to every request in one place.
- **Model:** `HttpClient` is a **pipeline in front of the platform**: a typed request object goes through a chain of interceptors to a pluggable **backend** (`FetchBackend` by default in v22, `HttpXhrBackend` on request) that finally calls `fetch` or `XMLHttpRequest`; the result comes back as a cold `Observable` of events, so unsubscribing aborts, and errors (including 4xx/5xx) arrive on the error channel as `HttpErrorResponse`. Analogy: a company mail room: you hand in a typed form, the mail room stamps, logs and routes it (interceptors), the courier (backend) is replaceable, and a returned parcel with a problem comes back as a complaint slip, not as a normal parcel. Diagram: `flowchart LR`: `component` → `HttpClient` → `"interceptors (chain)"` → `"HttpBackend"` → `"fetch / XHR (platform)"` → `server`, with a dashed box `"platform: CORS, cookies, HTTP cache"` around the last two nodes. **What to notice:** everything left of the backend is Angular; the request on the wire is still the browser's.
- **Mechanism:** F6 (docs: typed responses, cold Observables, unsubscribe aborts, status 0 for network errors; quoted with path, branch `main`, date), F11 (type assertion only; cold, one sentence plus [22 §3](../../modules/22-rxjs-foundations.md#3-cold-and-hot-unicast-and-multicast)), F16 (a 404 is an error, contrast with `fetch`), F18 (the fetch backend calls `fetch` with an `AbortSignal`; the init keys show which options are forwarded), F7 (fetch backend by default, with the `[Changed in v22.0: …]` marker; §2 owns setup); **read from the `@angular/common` 22.2.1 source**: `FetchBackend.handle` (`fesm2022/_module-chunk.mjs`: one `AbortController` per request, abort in the teardown) as the reason "unsubscribe" means "abort" (one paragraph; §6 owns the details).
- ***Framework vs platform* callout (required, C2):** what Angular adds (Observables, interceptors, typed options and parsing, XSRF, the testing seam, `httpResource`) against what the platform does ([09 §2](../../modules/09-web-networking-storage-security.md#2-fetch-xhr-and-the-request-lifecycle): the request, CORS, cookies, the HTTP cache) and what TypeScript adds (the generic is an assertion, F6).

### 2. Setting up `HttpClient`: `provideHttpClient`, its features and the fetch backend default · delta 800 · SEC-M27-02
- **Problem:** after `ng update` to v22 the upload progress bar still works in one app and throws `NG02824` in a new one; a lazy feature adds `provideHttpClient(withInterceptors([audit]))` and the global auth header disappears from its requests; a test passes `provideHttpClientTesting()` first and the requests go to the real network; someone adds `provideHttpClient()` "because the docs say so" though nothing needed it.
- **Model:** `provideHttpClient(...features)` is a **configuration recipe**: it registers the client, the interceptor handler, the backend (`FetchBackend` unless `withXhr()`) and the XSRF interceptor, then appends each feature's providers (`withInterceptors`, `withInterceptorsFromDi`, `withXsrfConfiguration`, `withNoXsrfProtection`, `withRequestsMadeViaParent`, `withXhr`, deprecated `withFetch` and `withJsonpSupport`). Analogy: a phone plan: the base plan includes calls and a default carrier; add-ons change the carrier or add services; a second SIM in a sub-department is a separate plan unless it forwards to the main line. - **Model:** `httpResource(() => urlOrRequest)` is a **`resource` whose loader is `HttpClient`**: it reads signals in the request function, issues the request **eagerly** whenever they change (cancelling the previous one), skips the request when the function returns `undefined`, and exposes `value`, `status`, `error`, `isLoading`, `hasValue`, plus `headers`, `statusCode` and `progress`. It goes through the same interceptors and testing backend. It is for **reads**; writes stay `HttpClient` calls. Analogy: a live departure board bound to a station selector, versus a ticket counter you walk up to. Diagram: `stateDiagram-v2`: `idle` (request `undefined`) → `loading` → `resolved` / `error`; params change → `loading` (previous request cancelled); `reload()` → `reloading`; `set()` → `local`. **What to notice:** a params change starts over at `loading` without the old value; `reload()` keeps it as `reloading`.
- **Mechanism:** F26 (the lifecycle run: statuses, cancellation, `value()` throwing in error with the message, `statusCode`/`headers`), F27 (request object, `defaultValue`, `parse` failure, `text`, interceptors, `NG0203`), F6 (docs: global `HttpClient`, eager, cancels the outstanding request, `parse` with Zod/Valibot named, the testing example with `whenStable()`), F2/F4 (`[Stable since v22.0]`, experimental since 19.2.0); `resource` statuses and reads: one sentence plus [17 §6](../../modules/17-signals.md#6-resources-async-data-as-signals) and [Q17.22](../../modules/17-signals.md#q17-22); the three-way choice: [Q17.26](../../modules/17-signals.md#q17-26); `rxResource`: [23 §7](../../modules/23-rxjs-in-depth.md#7-rxjs-and-signals-decision-rules-tosignal-toobservable-and-rxresource); `validateHttp` builds on it: one sentence plus [26 §6](../../modules/26-signal-forms.md#6-async-validation-and-debounce-validateasync-validatehttp-pending-and-cancellation); router resources: one clause plus [24 §6](../../modules/24-routing.md#6-resolvers-and-route-data-resolvefn-failures-and-router-resources); **read from the `@angular/common` 22.2.1 source**: the `httpResource` factory in `fesm2022/http.mjs` (how the request function becomes the resource params and how the loader subscribes to `HttpClient` and maps events; grep first and name only what is found).

### 11. Testing and the backend seam: `provideHttpClientTesting`, `HttpTestingController` and what they replace · delta 750 · SEC-M27-11
- **Problem:** a test with interceptors passes on one machine and calls the real network on another; a timeout test waits forever; a test of `httpResource` reads `value()` too early; a forgotten request goes unnoticed until production.
- **Model:** `provideHttpClientTesting()` swaps the **`HttpBackend` token** for an in-memory backend and gives you its controller: everything above the backend (the client, every interceptor, XSRF, `httpResource`) runs for real, and you answer each request by hand (`expectOne` → `flush`/`error`/`event`), then `verify()` that nothing is left open. Analogy: a flight simulator: the cockpit and the crew procedure are real; the sky is a screen you control.    - a request with the NO_CACHE token always reaches the backend.
4. **Exercise 27.4 · Refresh on 401: one refresh for many requests and no refresh loop** (EX-M27-04; section 7, with 3 and 4; `exercise-4-refresh/` with `auth-store.ts` (`AuthStore` root service: `accessToken` signal, `refresh(): Observable<string>` single flight, `logout()`, `refreshCalls` counter for tests), `auth.interceptor.ts` (`authInterceptor`, `SKIP_AUTH` context token, `API_ORIGIN` injection token), `refresh.spec.ts`). Constraints: add `Authorization` only to requests whose URL is relative or starts with `API_ORIGIN`; one retry per original request; the refresh request carries `SKIP_AUTH`; a failed refresh calls `logout()` and errors every waiting request; at most 3 injected dependencies; not covered: token storage (33), proactive refresh before expiry (an Interviewer follow-up). Criteria:
   - API requests carry the current bearer token;
   - requests to other origins carry no token;
   - three concurrent 401s trigger exactly one refresh;
   - every queued request is retried once with the new token;
   - a 401 from the refresh call logs out and fails the waiting requests;
   - a request that fails with 401 again after the refresh is not retried a second time.
5. **Exercise 27.5 · An upload with progress and cancel on the XHR backend** (EX-M27-05; sections 9, 6 and 2; `exercise-5-upload/` with `upload.service.ts` (`UploadService`: `upload(file: Blob): Observable<UploadState>` mapping events to `{ kind: 'progress', percent } | { kind: 'done', id } | { kind: 'failed', error }`), `upload-panel.ts` (`lab-m27-upload-panel`: a progress text, a cancel button, `takeUntilDestroyed` or an explicit `Subscription`), `upload.spec.ts`). Constraints: the spec configures `provideHttpClient(withXhr())` then `provideHttpClientTesting()` and drives progress with `TestRequest.event(...)`; `reportUploadProgress: true` and `observe: 'events'`; percentages rounded down; cancel unsubscribes; one test documents with a stubbed `fetch` that the same service on the default backend fails with `NG02824` (F25); not covered: real XHR (jsdom, C3), resumable uploads. Criteria:
   - the request asks for upload progress events;
   - upload progress events become rounded percentages;
   - the response becomes a done state with the server id;
   - cancel aborts the request;
   - an error response becomes a failed state;
   - on the default fetch backend the upload fails with NG02824.
6. **Exercise 27.6 · A search page with `httpResource`: loading, error and empty states, tested with `HttpTestingController`** (EX-M27-06; sections 10, 11, 3 and 5; `exercise-6-search-page/` with `search-result.ts` (type and guard), `search-page.ts` (`lab-m27-search-page`: an input bound to a `query` signal, `httpResource` with a request object (`params: { q }`), `undefined` when the query is shorter than 2 characters, `parse` with the guard, `defaultValue: []`, templates for idle, loading, error (mapped message), empty and results states), `search-page.spec.ts`). Constraints: the DOM tests use `fixture.autoDetectChanges()` and `await fixture.whenStable()` (no fake timers with `autoDetectChanges`, the module-26 lab rule); no `subscribe` in the component; no `HttpClient` injection in the component; not covered: debouncing (one Interviewer follow-up linking [17 §6](../../modules/17-signals.md#6-resources-async-data-as-signals)'s `debounced` and 22's timing operators). Criteria:
   - a query shorter than two characters sends no request and shows the hint;
   - typing a query sends one request with q as a parameter;
   - while the request runs the page shows loading;
   - results render as a list;
   - an empty result shows the empty state;
   - a server error shows the mapped error message;
   - a new query cancels the previous request.
