### 1. What to test where: unit, integration, component and end-to-end tests, the pyramid and the trophy · delta 900 (800 + 100 verification paragraph) · SEC-M29-01 (Opus)
- **Problem:** a team with 2,000 unit tests of services ships a login page whose button is never wired, because no test rendered the template; another team tests everything through the browser and waits 40 minutes per run, with flaky failures nobody trusts; a test suite mocks every collaborator and passes while the real HTTP mapping is broken. (Numbers are illustrative; the text says so or uses none.)
- **Model:** a test's **level** is set by **how much real code it runs and what it fakes**: a **unit test** runs one function or class with its collaborators replaced; a **component test** renders one component's template in `TestBed` (Angular's testing module, §4) with a DOM; an **integration test** runs several real units together (a routed page with its store and service, only the network faked); an **end-to-end test** drives the built app in a real browser against a running server (module 30). The **testing pyramid** (Mike Cohn, 2009, via Fowler, F27) says many fast unit tests, fewer integration tests, few UI tests; the **testing trophy** (Kent C. Dodds, F27) adds static analysis at the base and puts most effort in integration tests ("Write tests. Not too many. Mostly integration."). Analogy: testing a car: bench-test the alternator (unit), start the engine on a stand (integration), drive it round the test track (end-to-end); a compiler and linter are the factory inspection before anything turns (static). Diagram: `flowchart TB` with two stacks side by side: pyramid (`"UI / e2e: few"` over `"service / integration"` over `"unit: many"`) and trophy (`"e2e"` over `"integration: most"` over `"unit"` over `"static: types, lint"`). **What to notice:** both shapes put e2e at the top and few of them; they disagree on where the middle of the effort goes, which is a cost/confidence trade-off, not a rule.
- **Mechanism:** what each level costs in Angular: a unit test of a pure function needs no `TestBed` (§8); a component test pays for `TestBed` and jsdom (§2); an integration test in the unit runner fakes only HTTP (`HttpTestingController`, 27 §11) and uses `RouterTestingHarness` (24); **shallow versus deep** component tests: replacing a child with a stub through `overrideComponent(…, { set: { imports: [Stub] } })` isolates the parent but tests a fake contract (the run below); the confidence argument is Testing Library's guiding principle (F25 quote) and Fowler's "Practical Test Pyramid" (F27); **read from the `@angular/build` 22.2.1 source**: the unit-test builder compiles each spec with the application's Angular compiler (`getVitestBuildOptions` reuses the build target's options, F4), which is why a component test exercises the real AOT template while a plain unit test does not touch it.
