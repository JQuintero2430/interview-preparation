### 1. Why accessibility, and what the standards require · ~650 words · SEC-M11-01
- **Problem:** a checkout works with a mouse and not with a keyboard; a contract or a regulator asks for "WCAG 2.2 AA"; a team treats accessibility as a final polish pass and rebuilds components twice.
- **Model:** accessibility is a **contract between the page and every way of using it** (keyboard, switch, voice, screen reader, magnifier, captions, a bright street). WCAG organises it as four principles (perceivable, operable, understandable, robust: POUR), testable success criteria, and three levels; laws and procurement point at the standard. Analogy: a building ramp designed in versus bolted on afterwards. Diagram: `flowchart LR` of principles, guidelines, success criteria, levels A/AA/AAA, a conformance claim, and a law or contract that cites the standard. **What to notice:** the law points at the standard and the standard points at criteria you can test.
- **Mechanism:** users and situations (permanent, temporary, situational); POUR; levels (A minimum, AA the usual target, AAA not required as a blanket policy: the WCAG sentence quoted); what WCAG 2.2 added (nine criteria, 4.1.1 removed; the dates as read); which success criteria land in CSS and units: contrast 1.4.3 (4.5:1 normal, 3:1 large) and 1.4.11, resize 1.4.4, reflow 1.4.10, text spacing 1.4.12, target size 2.5.8, focus 2.4.7 and 2.4.11 (forward link to 4), motion 2.2.2 and 2.3.3 with `prefers-reduced-motion` (35 owns animation), `forced-colors`; links to 10 §5 and §6; the **contrast ratio formula** (relative luminance, `(L1 + 0.05) / (L2 + 0.05)`) with a Complete snippet; the European Accessibility Act (EAA, Directive (EU) 2019/882): what it covers, dates and exemptions **only as read from the primary text**; harmonised standard EN 301 549 and its WCAG reference **only if read**; the business case (reach, search and SEO overlap with semantics, litigation and procurement, cost of retrofit) stated as reasoning, with a figure only from a dated source read in the task.
- **First-use definitions:** accessibility, assistive technology (AT), WCAG and W3C/WAI, success criterion, conformance level, POUR, EAA, EN 301 549 (if read), contrast ratio and relative luminance.

### 2. Semantic HTML, landmarks and headings · ~650 words · SEC-M11-02
- **Problem:** a "card" built from `div`s and a click handler cannot be reached with Tab; a screen reader user hears "group, group, group"; headings picked for font size make the page outline useless; no `main` means no way to jump to the content.
- **Model:** the browser turns DOM, ARIA and some CSS into an **accessibility tree**: every node has a role, a name, a state and sometimes a description; assistive technology reads that tree through the platform's accessibility API, not the pixels. Native elements fill the tree correctly for free. Analogy: the page has a second, text-only interface and the markup is its source code. Diagram: `flowchart LR` of HTML elements, ARIA attributes and CSS (`display: none`) into the accessibility tree, then the platform accessibility API, then screen reader, voice control, switch. **What to notice:** CSS and ARIA can both change the tree, which is why they can also break it.
- **Mechanism:** what a native element gives (role, focusability, keyboard activation, state: `button` activates on Enter and Space, `a[href]` on Enter; `disabled`; form submission; `label`); element-to-role mapping (HTML-AAM); `button` for actions versus `a` for navigation; landmark elements (`header`, `nav`, `main`, `aside`, `footer`, `form`, `section`) with the conditions under which they map to a landmark role (page-level `header`/`footer` versus inside sectioning content, `section` and `form` only when they have an accessible name), one `main`, naming repeated landmarks; headings as structure (levels as an outline, no skipped levels, size is CSS; the HTML outline algorithm: what the spec says now and that no browser implemented it, from the spec text); lists and tables with real markup; `alt` text decision (informative, decorative `alt=""`, functional); link text that stands alone (2.4.4); `lang` (3.1.1) and `<title>` (2.4.2); visually hidden text pattern versus `hidden`/`display: none` (forward link to 3); `<details>`/`<summary>`.
- **First-use definitions:** accessibility tree, role, accessible name (defined fully in 6, linked), landmark, heading level, semantic HTML, platform accessibility API, visually hidden.
- **Verification:** HTML-AAM, ARIA in HTML and the HTML standard read in the task; MDN pages quoted. ### 3. ARIA: roles, states, properties and its rules · ~700 words · SEC-M11-03
- **Problem:** a custom dropdown rebuilt from `div`s with fourteen `aria-*` attributes still cannot be opened with the keyboard; `aria-label` on a plain `div` is ignored; `aria-hidden="true"` on a focused button leaves the user typing into nothing.

A role says what something is, a state says what it is doing now, a property says how it relates to the rest. Analogy: subtitles change what you read about the film, never the film. Diagram: `flowchart TD` decision: does a native element exist? yes: use it; no: choose the APG pattern, then add role, name, state, keyboard handling and focus management, then test with a screen reader. **What to notice:** three of the four steps in the "no" branch are behavior ARIA does not provide.

### 4. Keyboard, focus order, roving tabindex and focus traps · ~800 words · SEC-M11-04
- **Problem:** a menu opens only on hover; a modal lets Tab walk into the page behind it; `outline: none` leaves the keyboard user blind; a toolbar of twelve buttons takes twelve Tab presses; a CSS `order` rewrite makes focus jump around the screen.
- **Model:** the keyboard moves a cursor (focus) through a list of **focusable areas**; **Tab moves between widgets, arrow keys move inside one**. Analogy: Tab walks the corridor between rooms, arrows move around inside a room. ### 5. Focus management in SPAs and live regions · ~700 words · SEC-M11-05
