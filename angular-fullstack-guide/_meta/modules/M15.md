### 1. What NgModules did: compilation scope, injector and lazy-loading unit · ~850 words · SEC-M15-01
- **Problem:** a component works in one feature and is "not a known element" in another; a service provided in a shared module exists twice; a lazy module is the only way to split a chunk; a newcomer asks why `imports` in `@NgModule` and `import` at the top of the file are different things.
- **Model:** an NgModule was **three things in one class**: a compilation scope (which selectors and pipes a declared component's template may use), a provider list (which services its injector gets) and a lazy-loading unit (what `loadChildren` loaded). A standalone component takes the first job itself (`imports`), environment injectors and `provide*` functions take the second, and a route array or a component takes the third. Analogy: a club membership card that also decides which rooms you may enter and which lockers you get; standalone gives each person their own key list. Diagram: `flowchart LR`: `@NgModule` → (1) `declarations`/`imports`/`exports` → template scope of each declared component; (2) `providers` → the injector the module creates; (3) `loadChildren` → a lazy chunk with its own injector; dashed arrows to the standalone replacements (`imports` on the component, `ApplicationConfig`/route `providers`, `loadComponent`/route arrays). **What to notice:** the three jobs have three separate replacements, which is why a migration can be done one job at a time.
- **Mechanism:** the metadata (F1); "Declarables must belong to exactly one module" and `NG6007` (F14); "Declarations are private by default" and `NG8001` for an unexported declaration (F14); `NG6004` (F14); module providers reach every module that imports it and, for the root module, the whole app (F12); a lazy module gets its own injector (F1, F24); why it confused people, argued from the observations, not asserted: the scope lives in another file, the same class decides scope and providers so importing for a component also imports providers (F18), a provider in a widely imported module is duplicated per lazy injector (F18), the module constructor runs eagerly (F16); **NgModules are not deprecated** (F1: no tag) and the docs recommend standalone for new code (F12). Code: one small NgModule feature from `legacy/catalog/` and the same feature standalone (each a Complete/Excerpt snippet of a lab file).
- **First-use definitions:** NgModule, declarable (component, directive or pipe), compilation scope (template scope), `declarations`, `exports`, root module, feature module, lazy-loaded module, standalone component (link §2), environment injector (link 16 §5).
- **Verification:** `section-1-what-ngmodules-did.spec.ts` + `legacy/catalog/` (`catalog.module.ts`, `catalog-list.ts`, `price-pipe.ts`, read-only afterwards): `Section 1: a declared component renders what its module imports`, `Section 1: a module's providers are created in the injector that imports the module`, `Section 1: the module constructor runs when its injector is created`, `Section 1: the standalone version renders the same DOM without a module`. `NG6007`, `NG6004` and `NG8001` (unexported) are dated `ngc` blocks.
- **Callouts:** *Framework vs platform* (`> [!NOTE]`, required: the `imports` array of `@NgModule`/`@Component` versus the ES `import` statement; the ES module system is module 05's ([Q05.01](../../modules/05-js-modules-memory-modern-features.md#q05-01)): one decides what the TypeScript file can reference, the other what a template can use). Optional *Coming from the backend* (`> [!TIP]`): an NgModule resembles a Java module's `exports` plus a Spring `@Configuration` in one class. **Where the analogy breaks:** a JPMS module is a compile and runtime boundary for packages, while an NgModule's scope applies only to templates and its providers land in a shared injector.
- **Questions drilled:** Q15.01, Q15.02; Exercise 15.4.
- **Misconception candidates:** "NgModules are deprecated" (cause: the docs recommend standalone for new code, F12; no `@deprecated` tag, F1); "`imports: [X]` in `@NgModule` is the same as `import { X }`" (cause: the same word; one is a TypeScript reference, the other template scope plus providers); "a module's providers are private to the module" (cause: declarations are private by default; providers are not: they join the importing injector, F16, F18).

### 4. Lazy loading without modules: `loadComponent` and `loadChildren` with route arrays · ~700 words · SEC-M15-04
- **Problem:** the only reason a feature had an NgModule was `loadChildren`; a lazy feature's service must be shared by its pages but not by the rest of the app; a team writes `.then(m => m.AdminPage)` everywhere; a route loads an NgModule with `loadComponent`.
- **Model:** **the lazy unit is now a file**: `loadComponent` loads one standalone component, `loadChildren` loads a `Routes` array, and the route's `providers` give the feature its own environment injector, which is all the lazy NgModule used to provide. Analogy: you used to order a whole crate (module) to get a chair; now you order the chair or the room plan. A standalone `GreetingBanner` component, a `GREETING_CONFIG` token, `provideGreeting(config)` returning `EnvironmentProviders`, and a `GreetingModule` that imports and re-exports the banner with `forRoot(config)` delegating to `provideGreeting` and `forChild()` carrying no providers. Constraints: the module adds no logic of its own; no `providedIn: NgModule`; at most 3 injected dependencies per class; no network. Criteria:
   - a standalone app configured with `provideGreeting` renders the banner with the configured text;
   - an NgModule app importing `GreetingModule.forRoot(config)` renders the same banner through a declared component;
   - `importProvidersFrom(GreetingModule.forRoot(config))` in an environment injector gives the same configuration as `provideGreeting(config)`;
   - `forChild()` exports the banner but provides no configuration (the banner falls back to its default);
   - `provideGreeting` cannot be listed in a component's `providers` (a `// @ts-expect-error` line in the spec that fails the typecheck if the error disappears);
   - a second `forRoot` inside a child injector throws a named error (a guard in the module constructor, as in §5).
3. **Exercise 15.3 · A lazy feature without modules** (EX-M15-03; section 4; `exercise-3-lazy-feature/admin.routes.ts`, `admin-shell.ts`, `user-list.ts`, `settings-page.ts`, `admin-store.ts` + `lazy-feature.spec.ts`). An `admin` route that `loadChildren` a default-exported routes array with `providers: [AdminStore]`, a child list, a `loadComponent` settings page (default export), next to the old lazy NgModule route kept for comparison under `legacy/`. Constraints: no NgModule in the solution; `RouterTestingHarness` only; no guards or resolvers (24's). Criteria:
   - `/admin` renders the user list through the lazy routes array;
   - `/admin/settings` renders the default-exported component;
   - the list and the settings page share one `AdminStore`;
   - the root cannot inject `AdminStore`;
   - leaving and re-entering `/admin` keeps the same store;
   - the legacy NgModule route still works next to it and has its own store instance.
4. **Exercise 15.4 · A model of NgModule compilation scope** (EX-M15-04; sections 1, 5 and 8; `labs/ts-js/src/modules/15-standalone-and-ngmodules/scope-model.ts` + `scope-model.test.ts`). `computeScopes(units)` takes plain descriptions of modules (`declarations`, `imports`, `exports`) and standalone components (`imports`), returns each component's template scope and a list of diagnostics shaped like Angular's: declared twice (`NG6007`), a standalone class declared (`NG6008`), a non-standalone class imported by a standalone component (`NG2011`), an export neither declared nor imported (`NG6004`), and an unknown selector in a template (`NG8001`). A **model of the rules read and observed in Angular 22.2.1, not Angular's compiler**; the Constraints list what it leaves out (no pipes versus directives distinction beyond names, no `schemas`, no providers, no `forwardRef`, no JIT). Criteria:
   - a declared component sees its module's declarations and the exports of imported modules;
   - exports are transitive through re-exported modules;
   - a declaration not exported is invisible to importers;
   - a standalone component sees only its own `imports` (and the exports of imported modules);
   - each of the five diagnostics is reported with the class names involved;
   - a cycle of module imports terminates and is reported once.
