**Read from angular.dev (the Markdown sources of the `v22.2.1` tag of `angular/angular`, `adev/src/content/guide/di/`; pages DI overview, creating and using services, defining dependency providers, hierarchical DI, injection context, DI in action, lazy loading services, lightweight injection tokens, debugging DI, migrations `inject-function` and `injectable-to-service`, and error pages NG0200, NG0201, NG0203, NG0204, NG0205, NG0207, NG0209):**
- F1. Creating and using services: `@Service()` is described as "a modern, ergonomic shorthand for the traditional `@Injectable({ providedIn: 'root' })`"; its three guarantees for a root service are a singleton, global availability and tree-shakability ("excluded from the final production bundle if your code never explicitly uses it": see F27 for what was observed); the comparison table: `@Service` has no constructor DI, no `useClass`/`useValue`/`useExisting`/`useFactory` keys, no non-root scopes (`platform`); it has `inject()` and a `factory` option; `@Service({ autoProvided: false })` leaves registration to a `providers` array; "Reach for `@Service` when you are creating a new singleton class that uses `inject()`"; the `factory` runs in an injection context. `ng generate service` is the first example.
- F2. Migration page `injectable-to-service`: "available as of v22.1"; `ng generate @angular/core:service`; `@Injectable({providedIn: 'root'})` becomes `@Service()`, `@Injectable()` becomes `@Service({autoProvided: false})`; it skips a class that injects through its constructor, an `@Injectable` with any option but `providedIn`, and `providedIn` other than `'root'`; the `inject-function` migration is the suggested first step.
- F3. Hierarchical DI: two hierarchies, the `EnvironmentInjector` tree and the `ElementInjector` tree; "An `ElementInjector` is empty by default unless you configure it in the `providers` property"; above `root` sit an additional environment injector (the platform one: "`providedIn` 'platform'") and the `NullInjector`, which "returns an error or, in the case of `@Optional()`, `null`"; routes create child environment injectors; **resolution rules**: first the parents in the `ElementInjector` hierarchy, then the `EnvironmentInjector` hierarchy "back to the element where the request originated"; modifiers `optional`, `self`, `skipSelf`, `host`.
- F4. Injection context: valid places are a constructor, a field initializer, a provider factory and code run by `runInInjectionContext`; `assertInInjectionContext(fn)` throws a clearer message naming the helper; outside a context `inject` and `assertInInjectionContext` throw NG0203. The page uses `runInInjectionContext(this.environmentInjector, …)` (the free function, F10).
- F5. Error pages: NG0200 circular dependency, NG0201 no provider, NG0203 not in injection context, NG0204 can't resolve all parameters (JIT/legacy), NG0205 injector already destroyed, NG0207 `EnvironmentProviders` in a non-environment injector, NG0209 invalid multi provider ("a non-Array was found"). **The docs' NG0200/NG0201 texts differ from the 22.2.1 runtime texts (F20): quote runtime texts.**
- F6. Defining dependency providers: `providedIn: 'root'`, `'platform'`, and the NgModule-scoped forms; `useClass`, `useValue`, `useFactory`, `useExisting`; tokens; "multi"; `provideX()` functions.

### 1. Why dependency injection: containers, constructor injection and `inject()` · ~700 words · SEC-M16-01
- **Problem:** a class builds its own `HttpClient`-like collaborator with `new`, so a test cannot replace it, a second environment needs an `if`, and two components that should share state create two copies; a reviewer asks why Angular needs a container at all when constructors already take arguments; a team debates `constructor(private x: X)` versus `x = inject(X)`.
- **Model:** dependency injection is **a class declaring what it needs and something else deciding what it gets**. Analogy: a restaurant kitchen where the cook asks for "a knife", and the pass decides which knife; the cook never walks to the supplier. Diagram: `flowchart LR`: consumer (declares a token) → injector (looks up a provider for the token) → provider (recipe) → instance (cached per injector). **What to notice:** the consumer holds a token, not a class it constructs; the injector owns the cache that makes a singleton.
- **Mechanism:** inversion of control and what a container adds over hand-written constructors (lookup by token, caching per scope, lifetime hooks, hierarchy): argued from the probes (F18: one root instance; a component-level provider gives another) and the DI overview (F6), not from a doc claim; **constructor injection versus `inject()`**: both resolve through the same injector; `inject()` works in field initializers, needs no constructor, works in inherited classes without `super(...)` plumbing and in functions (F4); constructor parameters work in 22.2.1 with `@Inject`/`@Optional` (F29) and **`@Service` forbids them** (F15, → §3); the inject-function migration (F2); the **token** idea: a class, an `InjectionToken`, an abstract class or a string (F21); a first look at the three-step pipeline; a class with no decorator and a constructor parameter has no provider (F29); `NG2003` when a constructor parameter cannot be a token (F16). Coming-from-the-backend callout: Spring's container is the nearest relative (F30); the full comparison is §9.
- **First-use definitions:** dependency, injector, provider, token, inversion of control, singleton, injection context (link §4), `inject()`.
- **Verification:** `section-1-why-di.spec.ts`: `Section 1: a root service is one instance across consumers`, `Section 1: a component-level provider gives that component its own instance`, `Section 1: inject() works in a field initializer and a constructor parameter resolves the same instance`, `Section 1: a class without a provider fails with NG0201 naming the token`, `Section 1: an undecorated class with a constructor parameter has no provider`. `NG2003` (F16) is a dated `ngc` block.
- **Callout:** *Coming from the backend* (`> [!TIP]`, required): a Spring `@Autowired` constructor is resolved from one container at startup; Angular resolves from a tree of injectors that grows and shrinks with the UI. **Where the analogy breaks:** an Angular injector can be created and destroyed at any time (a route, a component) and its lookup climbs a parent chain; a Spring `ApplicationContext` is normally one per application.
- **Questions drilled:** Q16.01, Q16.02, Q16.03; Exercise 16.6 (the model injector).
- **Misconception candidates:** "DI is just the constructor syntax" (cause: Java tutorials show constructors; the injector and its cache are the point, F18); "`inject()` is a new, unsafe shortcut" (cause: it looks like a service locator; it is restricted to an injection context and typed, F4, F19); "a service is a special class" (cause: the word; any class or token with a provider is injectable, F21, F29).

### 2. Providers and tokens: `useClass`, `useValue`, `useFactory` and `useExisting` · ~850 words · SEC-M16-02
- **Problem:** a team swaps a real payment client for a fake in tests by editing production code; a logger interface needs two implementations behind one token; an alias `Logger` → `ConsoleLogger` creates two console loggers; a list of two providers for one token silently drops one.
- **Model:** a **provider is a recipe attached to a token in one injector**. Analogy: recipe cards in a binder: the same card name can exist in another binder (another injector), and the nearest binder wins. Diagram: `flowchart TD`: `provide` token → recipe (`useClass` new instance of class; `useValue` this exact value; `useFactory` call a function in an injection context; `useExisting` another token's instance) → instance cached per injector. **What to notice:** only `useExisting` points at another token; the other three create or hold a value themselves.
- **Mechanism:** the shorthand `providers: [Svc]` equals `{ provide: Svc, useClass: Svc }` (F6; the equality asserted in a test); the four recipes and their identity consequences: `useClass` creates a separate instance even of the same class (F21: `A2` via `useClass: A1` is not `A1`), `useExisting` returns the same instance as the target (F21), `useValue` gives the value as is (no cloning), `useFactory` with `deps`-free `inject()` in the factory (F4: the factory runs in an injection context; the `deps` array is the legacy form: C2 for its version); **last provider wins** for one token within one injector (F21); **multi** is §7; `EnvironmentProviders` and `makeEnvironmentProviders` are §7; the `provideX()` convention is §9; abstract class as a token: injection by an abstract class works like an interface token (stated from F29 only if the test asserts it); string tokens exist and lose type safety (F21); `NG0201` from a missing provider with the **`Source:` line naming where lookup started** (F18, F20); `useClass` of an `@Service` class is not allowed (F1: no provider keys).
- **First-use definitions:** provider, recipe, token, `InjectionToken` (link §7 and Q07.18), alias, factory function, last-wins.
- **Verification:** `section-2-providers.spec.ts`: `Section 2: a class shorthand equals useClass of itself`, `Section 2: useClass creates its own instance while useExisting returns the target instance`, `Section 2: useValue returns the same object every time`, `Section 2: useFactory runs once per injector and can inject`, `Section 2: the last provider for a token wins`, `Section 2: a missing provider is NG0201 with the source named`.
- **Callout:** none required.
- **Questions drilled:** Q16.04, Q16.05, Q16.06; Exercise 16.1.
- **Misconception candidates:** "`useExisting` and `useClass` are interchangeable aliases" (cause: both map one token to a class; one reuses the instance, one makes a new one, F21); "providing a token twice merges them" (cause: Spring `List<T>` injection; the last wins unless `multi`, F21); "`useValue` copies the object" (cause: the word 'value'; it stores the reference, to assert).

### 3. `providedIn`, `@Service`, scopes and tree-shaking · ~850 words · SEC-M16-03

- **Model:** **where a provider is registered decides how many instances exist and when the code can be dropped**: `providedIn` registers the recipe on the token itself ("provided where it is defined"), `providers` registers it where it is used. ### 4. The injection context: `inject()`, `runInInjectionContext` and `injectAsync` · ~800 words · SEC-M16-04

### 5. The injector tree: platform, root, route and element injectors, and the modifiers · ~1,000 words · SEC-M16-05
- **Problem:** a service provided in a lazy route is not found from the root; a service provided on a parent component is found by a directive on a projected node but not as expected; `optional` returns `null` where `self` was meant; a team cannot tell why two sibling routes have two instances of "the same" service.
- **Model:** there are **two trees of injectors**: element injectors (one per element that has providers, following the DOM) and environment injectors (platform → root → one per route that provides something). A lookup walks the element tree first, then the environment tree from the element where the request started. Analogy: asking a colleague for a stapler: first desks along your row, then the department supplies, then the building store, then no one. Diagram: `flowchart TD`: element injectors (child → parent → … → app root element) → environment: route injector → … → root environment → platform → `NullInjector` error/`null`; `self`/`host` arrows that stop early. **What to notice:** modifiers cut the walk: `self` stops at the start, `skipSelf` begins at the parent, `host` stops at the host element and never reaches the environment tree.
- **Mechanism:** the two hierarchies (F3); the **resolution rules** (F3: element tree, then environment tree "from the element where the request originated"); the platform injector and `NullInjector` (F3, F25); route environment injectors: a route with `providers` creates one; siblings get different instances, the same route revisited reuses its injector; children's providers override parents' for their subtree; root does not see route tokens (F25); **modifiers** as the options object of `inject()` (F12) and the older decorators (`@Optional`, `@Self`, `@SkipSelf`, `@Host`: F29 for constructor use); what each returns on the probed cases (F24, C7); `host` and projected content (F24: a projected directive sees the parent's `viewProviders`: → §6); the `NG0201` message's `Source:` shows where the walk started (F18, F20); `EnvironmentInjector` is a `get`-able injector with `runInContext`-style helpers via the free function (F4, F10); `Injector.get(Injector)` returns the injector asked from (F21); "a service in `providers` of a component is an element-tree lookup" and why component-level providers give per-instance state (§6).
- **First-use definitions:** element injector, environment injector, platform injector, `NullInjector`, resolution, modifier, route injector (link 24), host element (link 13 §7), projection (link 19).
- **Verification:** `section-5-injector-tree.spec.ts`: `Section 5: the element tree is searched before the environment tree`, `Section 5: a route with providers creates its own injector and sibling routes get different instances`, `Section 5: revisiting a route reuses its injector`, `Section 5: a parent route's provider is overridden by a child route's`, `Section 5: the root injector does not see route providers`, `Section 5: self, skipSelf, host and optional change where the walk starts and stops`, `Section 5: the platform injector shares platform services with root and does not see root services`. Docs (F3) quoted dated.
- **Callout:** *Framework vs platform* is not required; the Spring row of the comparison table is in §9.
- **Questions drilled:** Q16.15, Q16.16, Q16.17, Q16.18; Exercise 16.6.

### 8. Lifetime and dynamic injectors: `DestroyRef`, `EnvironmentInjector`, `Injector.create`, forward references and cycles · ~900 words · SEC-M16-08
- **Problem:** a feature loaded at run time needs its own services and must clean up; a utility must register cleanup without owning a component; a class is referenced before its declaration; two services need each other and the app dies with `NG0200`.
- **Model:** **an injector owns the lifetime of what it creates**: destroy the injector and its instances' `ngOnDestroy` run; `DestroyRef` is the handle that lets code register cleanup for "whatever I live inside". Analogy: a rented room: when the lease ends (the injector is destroyed) everything inside is cleared, and `DestroyRef` is the checkout checklist. Diagram: `stateDiagram-v2`: `Created` → `Active` (instances created lazily on first `get`) → `Destroyed` (`ngOnDestroy` called, `destroyed = true`, later `get` is `NG0205`); an arrow to cycles detection `Resolving → NG0200`. **What to notice:** instances are created on first request and destroyed with their injector, not with the code that asked.

### 9. DI patterns, testing and the Spring container · ~850 words · SEC-M16-09
- **Problem:** feature flags and payment providers differ per environment; a library must expose a stable API without leaking providers; a test must replace a service that is provided on a component; a backend developer asks whether this is Spring.
- **Model:** **swap behavior by swapping what a token resolves to**: strategy (token → implementation), facade (one class in front of several), adapter (map a foreign API to your token's interface), configuration (token with a typed object), feature flag (token → boolean or implementation). Analogy: a power strip with labelled sockets: appliances ask for "mains", the room decides which circuit. Diagram: `flowchart LR`: consumer → `PAYMENT` token → provider chosen by environment/route/test (`StripeAdapter` | `FakePayment`); beside it `provideBilling(config)` returning `EnvironmentProviders` for apps. **What to notice:** the consumer is unchanged in all three environments.
- **Mechanism:** strategy by token (F21 `useClass`/`useFactory`/`useExisting`); a facade as a root service; an adapter; configuration objects with defaults (`InjectionToken` with `factory`: F18); **feature flags** with a token and factory reading another token; **`provideX()` API design**: a function returning `EnvironmentProviders` via `makeEnvironmentProviders`, optional `withFeature()` arguments, one registered initializer (F20, F22; Angular's own `provideRouter` pattern named only as an example, no behavior claim); **testing**: `TestBed` providers replace root services and **not** component-level ones, `overrideComponent` does (F28), `TestBed.runInInjectionContext` (F12), creating fakes as `useValue`/`useClass`; **Spring comparison** (F30, C6): scopes (singleton default versus Angular's per-injector instances), scoped proxies (Angular has none: a shorter-lived dependency in a longer-lived consumer is a lookup in a different injector, not a proxy), `@ComponentScan` versus **no scanning** (a provider must be reachable by registration or `providedIn`), constructor injection preferred in Spring versus `inject()` plus `@Service`'s constructor ban in Angular.
- **First-use definitions:** strategy, facade, adapter, feature flag, configuration object, `provide*` function, test double (link 29), scoped proxy (Spring term), component scan (Spring term).
- **Verification:** `section-9-patterns-and-testing.spec.ts`: `Section 9: a token resolves to a different strategy per injector`, `Section 9: a provide function returns environment providers that configure a service`, `Section 9: a feature-flag token chooses an implementation through a factory`, `Section 9: module-level providers replace a root service but not a component-level one`, `Section 9: overrideComponent replaces a component-level provider`. Spring facts are quoted dated from the reference (F30, C6).
