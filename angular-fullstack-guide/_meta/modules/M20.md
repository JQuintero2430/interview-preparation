## Facts established while planning (re-check in the task that uses them)

All dated 2026-10-08. **R** = ran under `ng test` (Node 24.21.0, Angular 22.2.1), **r** = read (installed `labs/angular/node_modules/@angular/core` 22.2.1, the `v22.2.1` tag of `angular/angular` `adev/src/content/…`, or the `main` branch `CHANGELOG.md` fetched the same day), **c** = CHANGELOG line (attributed by the version heading it sits under). A "tree" below is: `Root` (`@if (on()) { <p-parent /> } {{ r() }}`) holds `Parent` (template `<p-child [v]="v()"><p-sib /></p-child>{{ w() }}`, signals `v`, `w`) holds `Child` (template `<ng-content /><p-leaf [v]="v()" />`) and projected `Sib`; all components use the v22 default (OnPush); each logs its constructor and every hook.

*Hook order (R):*
- F1. **First render**, as logged: constructors first, in creation order, before any hook: `parent.ctor, child.ctor, sib.ctor, leaf.ctor`. Then, in one pass: `parent.onInit, parent.doCheck, parent.effect, parent.afterContentInit, parent.afterContentChecked, child.onChanges, child.onInit, child.doCheck, sib.onInit, sib.doCheck, child.effect, sib.afterContentInit, child.afterContentInit, child.afterContentChecked, leaf.onChanges, leaf.onInit, leaf.doCheck, leaf.afterContentInit, leaf.afterContentChecked, leaf.afterViewInit, leaf.afterViewChecked, sib.afterViewInit, child.afterViewInit, child.afterViewChecked, parent.afterViewInit, parent.afterViewChecked`, then the render hooks `child.afterNextRender, child.afterEveryRender`. Reading it: the three "pre-order" hooks (`onChanges`, `onInit`, `doCheck`) go parent before child, and the projected `sib` runs right after `child` (it is a node of the parent's template, after the `p-child` node); the "after" hooks go **deepest first** (leaf, then sib, then child, then parent: post-order), so a child's `afterViewInit` precedes its parent's; `afterContentInit` of sib precedes child's. The component effects (`parent.effect`, `child.effect`) ran **after that view's `ngDoCheck` and before its `ngAfterContentInit`**. (A root fixture component's own hooks sit in the host view and, in this zoneless TestBed, did not re-run on a second `fixture.detectChanges()` with nothing dirty: wrap the component under test in a host so every hook is observed. A plan probe without the wrapper showed this.)
- F2. **Updates** (tree above, after the first render): `Parent.w.set(1)` (read only by the parent's template) logged `child.doCheck, sib.doCheck, child.afterContentChecked, child.afterViewChecked, child.afterEveryRender`: the parent's **own** `ngDoCheck`/`afterContentChecked`/`afterViewChecked` did **not** run (they belong to the view that declares the parent, `Root`'s, which was not refreshed), the child's view was not refreshed (no `leaf` hooks), and no `onChanges` ran. `Root.r.set(1)` (read by the root template) logged `parent.doCheck, parent.afterContentChecked, parent.afterViewChecked, child.afterEveryRender`: the parent's hooks ran, its view did not. `Parent.v.set(2)` (the bound input) logged `child.onChanges, child.doCheck, sib.doCheck, child.afterContentChecked, leaf.onChanges, leaf.doCheck, leaf.afterContentChecked, leaf.afterViewChecked, child.afterViewChecked, child.afterEveryRender`. **Hooks run in the view that declares the component, not in the component's own view** (also F11).
- F3. **Destroy** (`@if` turned false): `leaf.onDestroy, sib.onDestroy, child.onDestroy, parent.onDestroy` (deepest first, post-order).
- F4. `ngOnChanges` before `ngOnInit`: `onChanges` first, then `onInit`; the keys of the `SimpleChanges` for a component with a bound `[n]="5"` and a static `r="static"` were `r,n` (attribute order is the template's order: asserted by the task, not assumed); the unbound sibling instance of the same component **never** had `ngOnChanges` called but did get `onInit`. A later bound change reported `n: 1 -> 2 first=false`; the first reported `undefined -> 1 first=true`. `SimpleChanges<C>` (the generic form) typed `c.n?.previousValue` against the class (compiled). The docs' summary table lists `ngOnInit` **before** `ngOnChanges`; the docs text ("During initialization, the first `ngOnChanges` runs before `ngOnInit`") and the run agree with each other, not with the table: state the observation against the table (C10).
- F5. **Constructor versus `ngOnInit` (R).** In the constructor: a signal input with a default reads it (`n=0`); a required input read there throws `NG0950: Input "r" is required but no value is available yet.` (followed by a link note); `inject(Injector)` works; in `ngOnInit`: `n=5 r=static`, and `inject(Injector)` throws `NG0203: The \`Injector\` token injection failed. \`inject()\` function must be called from an injection context such as a constructor, a factory function, a field initializer, or a function used with \`runInInjectionContext\`.` The compiler already rejects a required-input read in a constructor (`NG8118`, Q17.28; the probe needed a cast to run it). docs `reference/errors/NG0950.md`: "Inputs are guaranteed to be available in the `ngOnInit` lifecycle hook and afterwards"; "Access the required input in reactive contexts".
- F6. **Hooks run untracked (r).** `callHookInternal` in `_debug_node-chunk.mjs` wraps each hook in `setActiveConsumer(null)` (so a signal read in a hook is not a dependency of anything), and `cleanUpView` does the same for destroy work. Not run: the claim is "read from `callHookInternal`".

*Render hooks (R unless stated):*
- F7. **Phases.** Components `A` (an `afterEveryRender` with all four phases passing values `A-E`, `A-W`, `A-M`, an `afterNextRender(cb)` and an `afterNextRender({ read })`) and `B` (created before `A`; `afterEveryRender({ read })` and `afterEveryRender({ write })`) logged, in one render: `A.earlyRead, B.write, A.write got A-E, A.mixed got A-W, A.nextRender(mixedReadWrite), B.read, A.read got A-M, A.nextRender read`. So **phase by phase across all components** (all `earlyRead`, then all `write`, then all `mixedReadWrite`, then all `read`), inside a phase in registration order, a plain callback is a `mixedReadWrite`, and each phase receives the return value of the previous phase of its own spec (the first receives nothing). Source: `AfterRenderImpl.execute` loops `for (const phase of AFTER_RENDER_PHASES) for (const sequence of this.sequences)` and runs each callback in `ngZone.runOutsideAngular`; `getHooks` maps a plain callback to the third slot (r).
- F8. **Registration.** A callback registered in a constructor (`afterNextRender(cb)`) or in `ngOnInit` **with `{ injector }`** ran after the first render, **after** `ngAfterViewInit` (`afterViewInit, from ctor, from ngOnInit (field injector)`), and inside `fixture.detectChanges()` (it returned after them); `afterNextRender` in `ngOnInit` **without** an injector threw `NG0203: afterNextRender() can only be used within an injection context such as a constructor, a factory function, a field initializer, or a function used with …`. A hook registered from inside a running render hook (`afterNextRender` inside an `afterNextRender`, with an `injector`) ran in the same tick (`outer`, `inner`, then the tick returned): read in `AfterRenderImpl.register`/`deferredRegistrations`.
- F9. **When they run.** A hook runs after a **render**, not after every tick: in the lab an `ApplicationRef.tick()` with nothing dirty ran no `afterEveryRender` callback, and a `Parent` signal change that refreshed a view ran it once. Source: `ApplicationRef.synchronizeOnce` sets the "after render" flag when change detection ran and calls `afterRenderManager.execute()` only when that flag (8) is set; registering a hook notifies the scheduler (`scheduler.notify(7)`). **Cleanup:** a hook registered in a component constructor stopped running once the component was removed (`D every` stopped; the one registered with `{ manualCleanup: true }` kept running after removal: `M every` repeated on every later render). `AfterRenderOptions` = `{ injector?, manualCleanup? }` (typings, `@publicApi 20.0`); `AfterRenderRef.destroy()`.
- F10. **Writing state in a hook.** A callback that does `this.s.update(v => v + 1)` while `s() < 2` rendered `hook s=0, hook s=1, hook s=2`, text `2` (another render per write; CHANGELOG 17.x "afterRender hooks should allow updating state"); one that writes every time threw `NG0103: Infinite change detection while refreshing application views. Ensure views are not calling \`markForCheck\` on every template execution or that afterRender hooks always mark views for check.` after **10** runs (`n=10`; `MAXIMUM_REFRESH_RERUNS = 10`, r in `_debug_node-chunk.mjs`).
- F11. **Server.** `afterEveryRender`/`afterNextRender` return a no-op ref when `ngServerMode` is set (r: `NOOP_AFTER_RENDER_REF`); typings and docs: "Callbacks run on browser platforms only"; "Render callbacks do not run during server-side rendering or during build-time pre-rendering" (docs `lifecycle.md`). Not run (see Lab decision).

### 1. The lifecycle map: phases and the order of the hooks · delta 1,050 (950 section + 100 verification paragraph) · SEC-M20-01
- **Problem:** a developer puts a measurement in the constructor, a subscription in `ngAfterViewInit` and an `@Input` read in the wrong hook; a child's hook "runs before the parent's" and breaks an assumption; a parent changes and its child's `ngDoCheck` fires while its template does not; the docs' table and the real order disagree on one pair.
- **Model:** a component has four stages: **created** (constructor), **checked** (the hooks that run while Angular walks the tree top-down: `ngOnChanges`, `ngOnInit`, `ngDoCheck`, then content hooks, then view hooks), **rendered** (render callbacks after every component is in the DOM) and **destroyed** (`ngOnDestroy`). Diagram: `sequenceDiagram` of `Parent`, `Child`, `Leaf` through the first render: three constructors, then the pre-order hooks going down, then the "after" hooks coming back up, then the render hooks. **What to notice:** pre-order hooks go down the tree, "after" hooks come back up, so a child's `afterViewInit` precedes its parent's.

### 2. Constructor, `ngOnInit` and inputs: what exists when · delta 800 · SEC-M20-02
- **Problem:** a constructor that reads an input sees its default (or throws for a required input); a constructor that calls a service with a bound id sends a wrong request; `inject()` in `ngOnInit` throws; the same logic is copied into both places "to be safe".
- **Model:** the **constructor** is plain construction: the injection context is open, nothing is bound yet; `ngOnInit` is the first moment the inputs hold their bound values, and the injection context is closed. Analogy: arriving at a hotel: the constructor is the booking (you can choose services), `ngOnInit` is check-in (your room number now exists). Diagram: `flowchart LR` of the timeline `constructor (injection context open, inputs default)` → `ngOnChanges` → `ngOnInit (inputs bound, no injection context)`, with a note box per stage listing what is usable. **What to notice:** each stage has exactly one thing the other lacks.
- **Mechanism:** the constructor holds the injection context so `inject()`, `effect()`, `afterNextRender()` and field initializers work there (F5; owner [§4](../../modules/16-dependency-injection.md#4-the-injection-context-inject-runininjectioncontext-and-injectasync) and [Q16.12](../../modules/16-dependency-injection.md#q16-12): one sentence and a link); inputs: a signal input holds its default in the constructor and a required input throws `NG0950` (F5; the compiler's `NG8118` is [Q17.28](../../modules/17-signals.md#q17-28)); the value is guaranteed from `ngOnInit` (docs `NG0950.md`); `ngOnChanges` and `SimpleChanges` including the generic form `[Added in v21.0]` (F4, F19) and the alias note (docs: the record uses the property name); the first `ngOnChanges` carries `firstChange` true; an unbound input component never gets `ngOnChanges` but gets `ngOnInit` (F4); constructor emits and query reads are 19's ([Q19.03](../../modules/19-component-communication-and-projection.md#q19-03), [Q19.20](../../modules/19-component-communication-and-projection.md#q19-20)). Guidance: keep constructors to wiring (fields, `inject`, `effect`, render-hook registration); put work that needs bound values in `ngOnInit`, or better in a `computed`/`effect` (§3); never copy logic into both. ### 3. Which hooks still matter with signals · delta 850 · SEC-M20-03
- **Problem:** a team migrates to signal inputs and asks which hooks to delete; an `ngOnChanges` that recomputes derived state duplicates a `computed`; an `ngDoCheck` written for in-place mutation never fires in a zoneless app; a view hook is used for DOM work that now has a render hook.
- **Model:** each classic hook has a **reason** it exists; signals take over the reasons that are "derive a value from inputs" and "react to a change", and leave the reasons that are "run once at a moment" and "touch the real DOM". Analogy: sorting a toolbox: some tools are replaced by a power tool (the signal graph), some stay because the job is still manual. Diagram: `flowchart TD` of the hooks on the left and their signal-era destination on the right (`ngOnChanges` → `computed`/`linkedSignal`/`effect`; `ngOnInit` → stays; `ngDoCheck` → a signal or immutable data; `ngAfterViewInit` → signal query or `afterNextRender`; `ngOnDestroy` → `DestroyRef`). **What to notice:** nothing is deleted from the framework; the reasons move.
- **Mechanism:** the map above with the evidence: `ngOnChanges` still runs for signal inputs (F4, [Q19.22](../../modules/19-component-communication-and-projection.md#q19-22) for setters), a `computed` over an input replaces derived-state code (F17), an `effect` runs once at first render and again per change (F17, owner [17 §4](../../modules/17-signals.md#4-effects)); **the order of a bound-input update** (F2, F17, C14): `onChanges`, `doCheck`, then the component effect, then the template; `ngDoCheck` is for custom change detection and is invoked even when the component's own check is skipped (typings, F19), but only when its declaring view is checked, so an in-place mutation nobody announces never reaches it in a zoneless app (F18, C3) and writing a plain field in it does not refresh an OnPush template (F18): the fix is immutable data or a signal; `ngAfterViewInit`/`ngAfterContentInit` for queries become signal queries read in `computed` or `effect` ([§5 of 19](../../modules/19-component-communication-and-projection.md#5-queries-view-and-content-queries-with-signal-queries)) and DOM work becomes `afterNextRender` (§4); **hooks run untracked** (F6, read from `callHookInternal`): a signal read in `ngOnInit` is a one-time read, not a dependency; `ngOnInit`, `ngOnDestroy` and the render hooks remain. ### 4. Render hooks: `afterNextRender`, `afterEveryRender` and their phases · delta 1,000 · SEC-M20-04
- **Problem:** a chart library needs the real DOM element and its size; `ngAfterViewInit` runs before layout is guaranteed and on the server; code that reads layout and writes styles in one callback forces the browser to relayout repeatedly; a hook registered in `ngOnInit` throws `NG0203`; a hook that writes state on every render loops.

Analogy: the stage crew's walk-through after all scenery is set: nobody walks through while scenery is still moving; reads happen in one sweep and writes in another. Diagram: `flowchart LR` of `change detection` → `earlyRead` → `write` → `mixedReadWrite` → `read` with the registered callbacks of components A and B placed under each phase. **What to notice:** the phases run across all components, one phase at a time.

### 5. Teardown: `ngOnDestroy`, `DestroyRef` and `takeUntilDestroyed` · delta 850 · SEC-M20-05
- **Problem:** an interval keeps ticking after the component is gone; a `subscribe` in `ngOnInit` holds the component alive; a `window` listener adds a copy per instantiation; late async work touches a destroyed view and throws `NG0911`.
