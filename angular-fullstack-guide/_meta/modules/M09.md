**Run (Node 24.21.0, `fetch` is undici):**
- `fetch` resolves on a 404: `status 404`, `ok false`, `statusText 'Not Found'`; a refused connection rejects with `TypeError: fetch failed` (the underlying code is not on `error.cause.code` here; read `cause` before claiming anything about it).
- Redirects with a `POST` body: 301, 302 and 303 are followed as `GET` with no body; 307 and 308 keep `POST` and the body (server echoed `GET:""` ×3 and `POST:"x"` ×2). `redirect: 'manual'` gives `status 302`, `type 'basic'`, readable `Location` (in Node; a browser returns an opaque-redirect response, documented, not run).
- `Headers`: names are case-insensitive (`get('CONTENT-TYPE')`), duplicate `append` joins with `, ` (`'1, 2'`), `Set-Cookie` is the exception, `getSetCookie()` returns the two cookies as an array while `get('set-cookie')` joins them with `, `.
- A second body read throws `TypeError: Body is unusable: Body has already been read` and `bodyUsed` is `true`; `clone()` before reading gives two readable copies.
- Conditional GET: a handler that sets `ETag: "v1"` and answers `304` with an empty body when `If-None-Match: "v1"` matches; `fetch` surfaced the `304` and `""` because the lab sends the header by hand (Node's `fetch` keeps no HTTP cache, so no automatic revalidation happens).
- Abort: manual `abort()` rejects with `AbortError` (`This operation was aborted`), `AbortSignal.timeout(100)` with `TimeoutError`, `abort(new Error('user left'))` rejects with that error, `AbortSignal.any([timeout, other])` reports the timeout. (Module 04 owns the detail; module 09 only uses it.)
- `fetch` with a `ReadableStream` body and no `duplex` throws `TypeError: RequestInit: duplex option is required when sending a body.`; with `duplex: 'half'` it works. `keepalive: true` is accepted (it has no visible effect in Node). `response.body.getReader().read()` yields `Uint8Array` chunks.
- `new Request(url)` defaults: `credentials 'same-origin'`, `mode 'cors'`, `cache 'default'`.
- **Node has no CORS enforcement**: a server that sends no `Access-Control-Allow-Origin` is read normally by `fetch` in Node (so "works in curl/Postman/Node" proves nothing about the browser).
- HTTP/1.1 versus HTTP/2: six concurrent 100 ms requests through an `http.Agent({ keepAlive: true, maxSockets: 2 })` opened 2 sockets and had at most 2 in flight (server side, ≥ 300 ms in total); the same six requests through one `http2.connect()` (cleartext h2c) used 1 session with 6 concurrent streams (< 250 ms). Browsers speak HTTP/2 over TLS only (documented, not run); HTTP/3 cannot be run in Node 24 (documented).
- CSP hash sources: `crypto.subtle.digest('SHA-256', bytes)` base64 equals `createHash('sha256')…digest('base64')`, and one added space in the script text changes the hash (`false`). (Basis for "the hash covers the exact text".)
- Globals: Node 24 has `fetch`, `Request`, `Response`, `Headers`, `AbortSignal.any`, `structuredClone`, `BroadcastChannel`, `WebSocket`, `CompressionStream`; it has **no** `XMLHttpRequest`, `localStorage`, `indexedDB`, `caches`, `EventSource`, `navigator.sendBeacon`.

### 1. HTTP semantics: methods, status codes and headers · ~450 words · SEC-M09-01
- **Problem:** a retry layer resends a `POST /payments` after a timeout and charges twice; a dashboard treats `301` and `307` alike and loses a request body; an API returns `200` with `{ "error": … }` and every cache and monitor believes it worked.
- **Model:** a request is a sentence (method + target + headers + optional body), a response is the reply (status + headers + body); the method tells intermediaries what they may do (cache, retry, prefetch) without understanding the payload. Diagram: flowchart "request failed or got a status → safe to resend?" (idempotent method or idempotency key; 5xx/network error vs 4xx).
- **Mechanism:** safe / idempotent / cacheable as RFC 9110 defines them and which methods have which (GET, HEAD, OPTIONS safe; PUT, DELETE idempotent; POST and PATCH not by default); status classes and the codes front ends meet (200/201/204, 301/302/303/307/308 and what each does to method and body, 304, 400/401/403/404/409/422/429, 500/502/503/504, `Retry-After`); headers that matter to a browser app (`Content-Type`, `Accept`, `Authorization`, `Location`, `Set-Cookie`, `Vary`, `Content-Disposition`, `Retry-After`), header names case-insensitive, `Headers` joins duplicates and exempts `Set-Cookie`; HTTP is stateless. First-use definitions: origin server, idempotent, safe, intermediary/proxy, idempotency key.
- **Verification:** RFC 9110 (read the method-properties section and the redirect section before writing). `section-1-http-semantics.test.ts` (Node, local server from `support/http-server.ts`): `fetch` resolves on 404 (`ok false`), POST through 301/302/303 becomes `GET` without a body while 307/308 keep method and body, `Headers` case-insensitivity, duplicate joining and `getSetCookie()`. A browser's redirect rewriting for 301/302 is the Fetch Standard's, quoted; the lab shows undici's behavior.
- **Callout:** *Coming from the backend* (Spring `ResponseEntity`/`HttpStatus` choose these codes; **where the analogy breaks:** the browser and every proxy interpret them, so a wrong code changes caching and retry behavior outside your code).
- **Questions drilled:** Q09.01, Q09.02, Q09.03, Q09.05.

### 2. `fetch`, XHR and the request lifecycle · ~480 words · SEC-M09-02
- **Problem:** a form posts with `fetch`, the server answers 500, and the UI shows "saved" because the promise resolved; a page sends analytics in `unload` and the last events are lost; an upload needs a progress bar and `fetch` cannot give one.
- **Model:** `fetch` returns a promise for the *response head*; the body is a separate one-shot stream you read afterwards. XHR is the older event-based object with progress events. Diagram: `sequenceDiagram` page → network → page with the three settle points (request fails → rejection; headers arrive → promise resolves with `Response`; body read → second promise), and where `abort()` cuts in.
- **Mechanism:** what rejects (network failure, abort, malformed request) and what does not (any HTTP status); `Response.ok`, `.json()`/`.text()`/`.blob()`, `bodyUsed` and `clone()`; `Request`/`Response`/`Headers` as platform classes shared with service workers; `credentials` (`omit`/`same-origin`/`include`; default `same-origin`), `mode`, `redirect`, `cache`, `signal`; streaming a response with `response.body.getReader()`; streaming a request body needs `duplex: 'half'` and (documented) HTTP/2+ in browsers; upload progress is XHR-only (`xhr.upload.onprogress`); download progress by counting chunks of the stream; `keepalive` and `sendBeacon` for page-hide delivery (limits read from the Fetch Standard / MDN before stating); cancellation is [module 04 §7](../../modules/04-js-async-event-loop.md#7-cancellation-with-abortcontroller) (link) plus: the rejection carries `signal.reason`, and aborting during a body read rejects that read. First-use definitions: one-shot stream, opaque response (only if used).
- **Verification:** `section-2-fetch.test.ts` (Node + local server): body can be read once (`TypeError`, `bodyUsed`), `clone()` gives two reads, `ok`/`status` handling, streamed body arrives as `Uint8Array` chunks, request stream without `duplex` throws, abort during a body read rejects the read, `Request` defaults (`credentials`, `mode`). XHR upload progress, `keepalive` size limit, browser-only behaviors: MDN and the Fetch Standard (jsdom has `XMLHttpRequest` but no `fetch`; not used).
- **Callout:** *Framework vs platform*: `HttpClient` (v22 uses fetch by default; owner 27) wraps these; the rules here are the platform's.
- **Questions drilled:** Q09.03, Q09.04, Q09.05, Q09.06; Exercise 09.2.

### 3. HTTP/1.1, HTTP/2 and HTTP/3 · ~400 words · SEC-M09-03
- **Problem:** a build ships 300 tiny modules and loads slowly over HTTP/1.1, while "bundle everything" over HTTP/2 invalidates the whole cache on every deploy; on a lossy mobile network HTTP/2 stalls all assets on one lost packet.
- **Model:** a road with lanes. HTTP/1.1: one lane per connection, a request waits behind the one ahead (HOL blocking at the HTTP layer), so browsers open several connections. HTTP/2: many streams interleaved on one TCP connection, but a lost TCP segment stalls all of them (HOL blocking at the TCP layer). HTTP/3: streams on QUIC (over UDP) with independent loss recovery. Diagram: three-column flowchart.
- **Mechanism:** persistent connections and pipelining's failure in 1.1; HTTP/2 framing, streams, HPACK header compression, stream priorities (state read before claiming), why Server Push is gone (read from Chrome/MDN before stating), TLS in practice (ALPN); HTTP/3 over QUIC: per-stream recovery, 0-RTT/1-RTT handshake, connection migration, `Alt-Svc` discovery (read before writing); what this changes for bundling (fewer reasons for sprites/domain sharding/one giant bundle; still reasons to bundle: compression ratio, per-request overhead, module waterfalls; cache granularity favors hashed chunks): Angular's chunking is owned by 12 and 31. First-use definitions: multiplexing, HOL blocking, QUIC, ALPN, stream.
- **Verification:** RFC 9113 and RFC 9114 (read the HOL paragraphs), MDN HTTP/2 and HTTP/3 pages, Chrome Server Push removal post. `section-3-http-versions.test.ts` (Node `http`/`http2`, h2c): six concurrent requests need as many connections as the agent allows under HTTP/1.1 (2 sockets with `maxSockets: 2`, in-flight ≤ 2) and one session with six concurrent streams under HTTP/2. States that browsers use HTTP/2 over TLS only and that HTTP/3 was not run. Do not time-assert on absolute milliseconds; assert socket/session/in-flight counts.
- **Callout:** *Coming from the backend*: the Backend guide §5.2 (link) for multiplexing; **where the analogy breaks:** the front-end consequence is bundling and caching strategy, not server thread or connection-pool sizing.
- **Questions drilled:** Q09.07, Q09.08.

### 4. HTTP caching · ~460 words · SEC-M09-04
- **Problem:** a deploy ships a fixed bug, yet users run the old bundle for a day; or `index.html` is cached for a year and points at deleted files; or private account data lands in a shared proxy cache.
- **Model:** a cache answers from memory while the stored response is *fresh*; when it is *stale* it asks the origin "has this changed?" with a validator and gets either `304` (reuse) or a new `200`. Diagram: flowchart (stored? → fresh? → serve; stale + validator → conditional request → 304/200; none → full request).
- **Mechanism:** freshness (`max-age`, `Expires`, heuristic freshness when absent), validators (`ETag` strong/weak, `Last-Modified`) and conditional requests (`If-None-Match`, `If-Modified-Since`), `Cache-Control` directives (`no-cache`, `no-store`, `must-revalidate`, `max-age=0`, `private`/`public`, `s-maxage`, `immutable`, `stale-while-revalidate`), `Vary`, browser reload behavior (normal reload revalidates; read from MDN/web.dev before claiming); the hashed-asset strategy: content-hashed file names + `max-age=31536000, immutable`, and `index.html` with `no-cache` so a deploy is picked up; a single sentence linking LCP/CWV ([Q08.16](../../modules/08-browser-rendering-dom-events.md#q08-16)) and the CLI's output hashing (12). First-use definitions: fresh/stale, validator, shared vs private cache, CDN.
- **Verification:** MDN `Cache-Control` and HTTP caching, RFC 9111 (read the freshness and validation sections). `section-4-caching.test.ts` (Node + local server): a small `etag-handler.ts` (content-hash `ETag`, `304` on `If-None-Match`, new `ETag` on changed content) and a content-hash file-name helper, asserting 200 → 304 (empty body) → 200 after a change. **Node's `fetch` has no HTTP cache**, so what a browser does with `max-age`/`immutable` is documented, not run; say so.
- **Callout:** *Framework vs platform*: Angular's `ng build` emits hashed file names and `index.html`; the headers come from the server/CDN (owner 44); `HttpClient` has no cache of its own (owner 27).
- **Questions drilled:** Q09.09, Q09.10, Q09.11.

### 5. The same-origin policy and CORS · ~480 words · SEC-M09-05
- **Problem:** the SPA at `https://app.example.com` calls `https://api.example.com` and the console shows a CORS error, while the same call works in Postman; someone "fixes" it with `Access-Control-Allow-Origin: *` and then credentials stop working, or reflects any `Origin` and opens the API to every site.
- **Model:** the browser is a guard at the door of each *origin*: scripts may *send* many cross-origin requests, but may *read* the response only if the other server opts in with headers. Diagram: `sequenceDiagram` browser ↔ API for a preflighted request (`OPTIONS` + `Origin`/`Access-Control-Request-*` → `Access-Control-Allow-*` → the real request → `Access-Control-Allow-Origin` on the response) and the "block the read" step.
- **Mechanism:** origin = scheme + host + port, same-origin vs same-site (defined here, used again in §6); what the same-origin policy blocks (reading cross-origin responses, not sending, not embedding images/scripts/forms); CORS request kinds: simple versus preflighted (MDN's exact conditions), the preflight and its cache (`Access-Control-Max-Age`, browser caps), response headers (`Allow-Origin`, `Allow-Methods`, `Allow-Headers`, `Expose-Headers`, `Allow-Credentials`), credentials (`fetch(..., { credentials: 'include' })`; wildcard not allowed with credentials; `Vary: Origin` for dynamic origin), what the browser enforces (the response is hidden from script; the request is **not** stopped for simple requests, so CORS is no protection against CSRF or a server-side client); redirects and error responses need the headers too (read the Fetch Standard before claiming); dev proxy / same-origin reverse proxy as the alternative (pointer to 41 and 44). First-use definitions: origin, preflight, safelisted header, credentialed request.
- **Verification:** MDN CORS (quoted, Facts above) and the Fetch Standard CORS protocol (read). `section-5-cors.test.ts` (Node + local server): a server with no CORS headers is read normally by Node `fetch` (CORS is enforced by browsers, not by HTTP or Node); the lab does not claim any browser behavior. Exercise 09.1's model is checked against MDN's rules, not against a browser.
- **Callout:** *Coming from the backend*: Spring `CorsConfigurationSource` (owner 41) is where these headers come from; **where the analogy breaks:** a server-side CORS filter does not *block* anything for non-browser clients; the browser alone decides whether script may read the answer. No Spring snippet in this module.
- **Questions drilled:** Q09.12, Q09.13, Q09.14; Exercise 09.1.

### 6. Cookies · ~460 words · SEC-M09-06
- **Problem:** a session cookie readable by an injected script is stolen; a "remember me" cookie leaks to every subdomain; a cookie is sent on a forged cross-site `POST` and money moves; after a browser update an embedded widget loses its cookie.
- **Model:** a cookie is a small note the server asks the browser to hold and attach to later requests to a matching host and path; attributes are the rules on the note. Diagram: flowchart "`Set-Cookie` → accepted? (prefix, Secure, Domain rules) → stored → on each request: Domain/Path match? Secure? SameSite context? → `Cookie` header".
- **Mechanism:** `Set-Cookie` and `Cookie` headers; `Domain` (host-only by default, subdomains when set), `Path` (default = the URL's directory, which surprises), `Expires`/`Max-Age` (Max-Age wins), `Secure`, `HttpOnly` (hidden from `document.cookie`; stops theft by script, not abuse from script), `SameSite` (`Strict`, `Lax`, `None` needs `Secure`; what each sends on cross-site subrequests and top-level navigations), the **site** concept (registrable domain; scheme-aware "schemeful same-site" read before stating), `__Host-` and `__Secure-` prefixes, `Partitioned` (CHIPS: one jar per top-level site) and the state of third-party cookies (as MDN states it on the day read), cookies versus CSRF (SameSite is defense in depth; the SPA-specific treatment is 33/42). First-use definitions: site (registrable domain), host-only cookie, third-party cookie, CSRF (one clause, owner 33).
- **Verification:** MDN `Set-Cookie`, RFC 6265bis (read the SameSite and prefix sections), dated source for the Lax default (see Facts). `section-6-cookies.test.ts` (jsdom, `// @vitest-environment jsdom`, `url` option): HttpOnly via script ignored, server-side HttpOnly cookie hidden from `document.cookie` but sent by the jar, `__Host-` rejected without `Secure`/`Path=/`, `Secure` rejected on `http:`, `Domain` of another site rejected, `Max-Age=0` deletes, default path. These are jsdom (tough-cookie) results; SameSite behavior, `Partitioned` and third-party blocking are documented, not run.
- **Callout:** *Coming from the backend*: Spring's `ResponseCookie` / `server.servlet.session.cookie.*` set these attributes (owner 42; no snippet here); **where the analogy breaks:** the server sets the note, but the browser decides whether to store it and when to send it.

### 7. Browser storage: what each is safe for · ~380 words · SEC-M09-07
- **Problem:** an app keeps a JWT and a shopping cart in `localStorage`; one XSS bug reads both; an offline editor stores 200 MB in `localStorage` and crashes on a quota error; a user's data vanishes because the browser evicted the origin.
- **Model:** a set of cupboards with different sizes, lifetimes and visibility: cookies travel with requests; Web Storage is a small synchronous string map per origin (`sessionStorage` per tab); IndexedDB is an asynchronous transactional object database; Cache Storage holds `Request`/`Response` pairs for service workers. Diagram: decision flowchart (needs to go to the server? → cookie; small string setting? → Web Storage; structured/large/offline? → IndexedDB; HTTP responses for offline? → Cache Storage), with "never secrets in script-readable storage" noted as the deciding question.
- **Mechanism:** same-origin scoping; Web Storage is synchronous (blocks the main thread), string-only (`'1'`, `'[object Object]'`, `JSON` round trip loses `Date`, `undefined`, functions), `storage` event fires in *other* documents; IndexedDB (object stores, indexes, transactions, structured clone, async via requests/promises-wrapper libraries; `structuredClone` is the same algorithm, verified here by running it in Node); Cache Storage; quotas and eviction (MDN numbers as read, best-effort vs persistent, `navigator.storage.estimate()`/`persist()`, Safari's 7-day rule, `QuotaExceededError` handling); storage can throw or be unavailable (private modes, blocked cookies): wrap access; storage is readable by any script on the origin, hence XSS equals storage theft (token trade-off matrix: owner 33, link). First-use definitions: Web Storage, structured clone, quota.
- **Verification:** `section-7-storage.test.ts` (jsdom): string coercion, JSON round trip losses, `sessionStorage` separate from `localStorage`, jsdom's `QuotaExceededError`, plus `structuredClone` (Node) keeping `Date`/`Map` that JSON loses. IndexedDB, Cache Storage, real quotas and eviction: MDN pages (jsdom has neither API; the quota numbers are MDN's, dated by the read).
- **Questions drilled:** Q09.18.

### 8. Content Security Policy and Trusted Types · ~440 words · SEC-M09-08
- **Problem:** an XSS bug lands a `<script>` tag in a comment field; the framework's escaping missed one path; a third-party tag manager loads a second script from an unexpected host; an allowlist CSP of 40 hosts is bypassed through one JSONP endpoint.
- **Model:** CSP is a second lock: even if hostile markup gets into the page, the browser refuses to run script that the server did not mark as its own; Trusted Types guards the DOM sinks from the inside. Diagram: `sequenceDiagram` server generates a nonce per response → header + HTML with the nonce → browser runs only scripts with a matching nonce → `'strict-dynamic'` lets those scripts load others → violation → report (report-only variant).
- **Mechanism:** delivery by `Content-Security-Policy` header (and `Content-Security-Policy-Report-Only`; `<meta>` limits read before stating); directives (`default-src`, `script-src`, `style-src`, `connect-src`, `img-src`, `frame-ancestors`, `object-src`, `base-uri`, `form-action`, `report-to`/`report-uri` as read), source expressions (`'self'`, hosts, `'nonce-…'`, `'sha256-…'`, `'strict-dynamic'`, `'unsafe-inline'`, `'unsafe-eval'`); why allowlists fail and nonce/hash + `strict-dynamic` policies work (web.dev, quoted); a nonce is ≥ 128 bits of randomness, fresh per response (so a static `index.html` cannot carry a fixed nonce: hashes or server rendering; Angular's treatment is 33); hash = base64 SHA-256 of the exact script text; rollout with report-only; Trusted Types [Baseline 2026, newly available since February 2026] (`require-trusted-types-for 'script'`, `trusted-types` allowlist, policies that sanitize; sinks such as `innerHTML`), what they do not cover. First-use definitions: nonce, sink, XSS (one clause, owner 33), violation report.
- **Verification:** web.dev strict CSP, MDN CSP and Trusted Types pages, CSP Level 3 (read for `strict-dynamic`). `section-8-csp.test.ts` (Node): a nonce helper yields ≥ 128 bits, base64, different each call; a `strictCsp(nonce)` builder returns the web.dev policy string; a hash source equals the SHA-256 of the exact text and changes with one extra space (Facts above). Enforcement is browser behavior: documented only.
- **Callout:** *Framework vs platform*: CSP and Trusted Types are platform features; Angular's sanitizer, nonce support and Trusted Types integration are module 33.

## Exercises (3, ceiling 3)

Each follows the full E1 anatomy, ≤ 400 prose words. Solutions in `labs/ts-js/src/modules/09-web-networking-storage-security/<name>.ts` with `<name>.test.ts`, `describe('E09.N …')`, one `it` per criterion titled with its text. **The module text never claims "mutation checks"** (REVIEW lesson): a criterion's test is what the reader can run.

1. **Exercise 09.1 · A CORS decision model** (EX-M09-01; section 5; `cors-model.ts`). `needsPreflight(request)` and `checkCors({ request, preflight?, response })` implement the rules MDN states, as a pure model (not a browser). Criteria:
   - a `GET`, `HEAD` or `POST` with only safelisted headers and a safelisted `Content-Type` is simple (no preflight);
   - another method, a custom header or `Content-Type: application/json` needs a preflight;
   - the response is readable only if `Access-Control-Allow-Origin` is `*` or exactly the request origin;
   - with credentials, `*` is rejected and `Access-Control-Allow-Credentials: true` is required;
   - a preflight answer must allow the method and every non-safelisted header (names case-insensitive), otherwise the real request is not sent.
2. **Exercise 09.2 · A resilient `fetch` wrapper** (EX-M09-02; sections 1 and 2, links 04 §7; `resilient-fetch.ts`). `fetchJson(url, { method, timeoutMs, retries, signal, sleep, jitter })` over a local server. Criteria:
   - a non-2xx status rejects with an `HttpError` that carries the status (plain `fetch` resolves);
   - a request slower than `timeoutMs` is aborted and rejects with a `TimeoutError`;
   - aborting the caller's `signal` rejects with its reason and sends no retry;
   - only idempotent methods are retried, and only on network errors and 502/503/504; a `POST` is never retried;
   - waits between attempts come from the injected `sleep`, grow exponentially from the injected `jitter`, and stop once the signal is aborted.
3. **Exercise 09.3 · A cookie jar that follows the browser's rules** (EX-M09-03; sections 1, 5 and 6; integrates the module; `cookie-jar.ts`). `jar.set(setCookieHeader, url)`, `jar.cookieHeader(url, { crossSite, topLevelNavigation, method })`, `jar.scriptView(url)`. Criteria:
   - `Set-Cookie` attributes are parsed (`Domain`, `Path`, `Max-Age`, `Secure`, `HttpOnly`, `SameSite`), a cookie is host-only unless `Domain` is given, and the default `Path` is the URL's directory;
   - a `__Host-` cookie is accepted only with `Secure`, `Path=/` and no `Domain`, and `__Secure-` needs `Secure` (agreeing with jsdom's jar on the table of cases the test shares with it);
   - `Domain`, `Path` and `Secure` decide which cookies the `Cookie` header carries for a URL;
   - `SameSite=Strict` is never sent cross-site, `Lax` only on a top-level `GET` navigation, `None` requires `Secure`, and same-site requests send everything;
   - `HttpOnly` cookies are sent but absent from `scriptView`, and `Max-Age=0` deletes a cookie.
