### 1. AngularJS: scopes, watchers and the digest cycle · delta 850 (750 + 100 verification paragraph) · SEC-M39-01
- **Problem:** an AngularJS 1.x screen with 3,000 bindings feels slow on every keystroke, a value set in a `setTimeout` never shows, and a page sometimes dies with "10 $digest() iterations reached. Aborting!"; teams still maintain such code, and interviewers ask why Angular left this model.
- **Model:** a **scope** is a plain object that holds the model for a part of the page; templates bind to it; each binding registers a **watcher** (a function that reads a value and the last value seen). `$apply(fn)` runs your code and then `$digest`, which walks every watcher and calls the listener of each one whose value changed, then loops again until a full pass changes nothing (dirty checking), at most 10 loops. Analogy: a night guard who walks every door in the building after any noise, and walks again if he finds one open, until a full round finds every door closed. Diagram: `flowchart TD`: event → `$apply(fn)` → run `fn` → `$digest` → for each watcher compare → any dirty? yes → loop (TTL count) / no → render done; a side path "count > 10 → infdig error".
- **Mechanism:** **read from `angular.js` 1.8.3** (F16): `TTL = 10`, `$digest`'s loop, `$evalAsync` drained inside the loop, `$$postDigest` after it (internal, C8), the `infdig` message; the scope guide quotes (code outside "the AngularJS execution context" needs `$apply`; the delay coalesces updates into one notification). Two-way binding (`ng-model`) is two watchers plus a DOM listener that calls `$apply`. Prototypal scope inheritance and isolate scopes (F16). Contrast once with Angular: a template is compiled to code that is checked from the root on a tick, and since v22 OnPush-by-default views are skipped unless marked (link 21 §2 and §3 once; zone.js played the "noise detector" role, 21 §3).
- **First-use definitions:** AngularJS (the 1.x framework, end of support January 2022), scope, `$rootScope`, watcher, digest, dirty checking, `$apply`, two-way binding, isolate scope, TTL (here: the loop limit).
- **Verification:** `labs/ts-js/src/modules/39-version-history-and-migrations/concepts/mini-digest.ts` (≈40 lines: `watch`, `apply`, `digest` with a loop limit of 10, stated as our model of the 1.8.3 loop, C9) and `concepts/section-1-digest.test.ts`: `Section 1: our model runs a second loop when a listener changes another watched value`; `Section 1: our model stops after 10 unstable loops with an infdig-style error`; `Section 1: our model does not see a change made outside apply until the next digest`.
- **Questions drilled:** Q39.01, Q39.02. Practised in Exercise 39.1.
- **Misconceptions:** "AngularJS re-renders the whole page on every change" (cause: "it checks everything" is heard as "it repaints everything"; it compares watcher values and touches only the DOM of changed bindings, F16); "dirty checking is the same as Angular's change detection" (cause: both are called change detection; AngularJS loops until stable and lets watchers write the model, Angular checks top-down once per tick and throws `ExpressionChangedAfterItHasBeenChecked` in dev mode when a check changes a bound value, link 21 once); "`$scope.$apply()` everywhere fixes missing updates" (cause: it does fix code outside the context; called inside a digest it throws "$digest already in progress", the task reads `beginPhase`'s message from 1.8.3 and quotes it, or drops the clause).
- **The verification paragraph** (placeholder before §1, 80-110 words): `ng test` (jsdom 30.1.1) for the legacy and migrated features and the strangler routing; Vitest in Node for our digest model, the hop planner, the program scheduler and the installed migration files read from `labs/angular/node_modules`; the v22 core migrations run in memory through `@angular-devkit/schematics` 22.2.1's `SchematicTestRunner` (or "read, not run" under `PLAN-M39-B`); source reads of `@angular/cli`, `@angular/core` and `@schematics/angular` 22.2.1, of `angular` 1.8.3 and `@angular/upgrade` 22.2.1 from npm tarballs; the Angular, CLI and Components changelogs and angular.dev sources on the stated dates; AngularJS and ngUpgrade documented only.

### 2. Why Angular was rewritten, and what carried over · delta 650 · SEC-M39-02 (Opus)
- **Problem:** "Why did Google rewrite AngularJS instead of evolving it?" is a staple question, and most answers repeat folklore ("it was slow", "it had no mobile support") with no source; a team deciding whether to migrate a 1.x app needs the actual differences that make a direct upgrade impossible.
- **Model:** AngularJS and Angular share a name, the idea of declarative templates with DI, and little code: Angular 2 (2016-09-14, F11) changed the language (TypeScript), the change detection model (a compiler and one-way data flow by default, then zone.js triggers; link 21 §3), DI (class tokens and hierarchical injectors; link 16), templates (property and event bindings instead of directive-specific attributes; link 13), modules (ES modules plus NgModules, later standalone) and tooling (the CLI from 1.0.0, 2017-03-24, F15). - **First-use definitions:** rewrite (no in-place upgrade path), one-way data flow, minification-safe DI annotation, ES module.

### 3. How Angular ships: semantic versioning, the release cadence, support windows and the deprecation policy · delta 700 · SEC-M39-03
- **Problem:** a team plans its year around Angular releases and asks "how long can we stay on v20?", "will a minor break us?", "is a developer preview API safe?"; wrong answers lead to running unsupported versions or building on APIs that change in a patch.
- **Model:** a **major** (breaking changes allowed, with migrations), **minor** (features, no breaking changes) and **patch** (fixes) follow semantic versioning; since v22 a major comes **every 12 months** with 4-6 minors, before v22 every 6 months with 1-3 minors (F9); each major is **active** then **LTS** (long-term support: critical fixes and security only), about 24 months in all (F9, table with the v20-v22 rows); a deprecated API stays for at least the next major; developer preview and experimental APIs are outside the policy. Analogy: a lease with a fixed term, a renewal notice one term ahead, and a "beta" room that can be rearranged any day. Diagram: `timeline` of v20, v21, v22 with released, active ends and LTS ends (F9 values).
- **Mechanism:** **read from angular.dev `reference/releases.md`** (F9) to answer "why can't I jump from v19 to v22": the update-path rule (within one major) and the deprecation period; the compiler ABI note ("across patch versions of the same minor"; why independently built bundles must match the minor; link 38 §8 once); how a deprecation is announced (changelog, strikethrough in API docs) and how it reaches you (the `@deprecated` JSDoc tag in the typings, F18, lint and IDE strikethrough). Status vocabulary: stable, developer preview, experimental, deprecated (STYLE-GUIDE §3.2 markers, link to the guide's own use).
- **First-use definitions:** semantic versioning, major/minor/patch, active support, LTS, deprecation period, developer preview, experimental, compiler ABI.
- **Verification:** `labs/ts-js/…/concepts/section-3-support.test.ts` (Vitest): `Section 3: the installed @angular/core 22.2.1 marks ChangeDetectionStrategy.Default as deprecated in its typings` (reads `types/*.d.ts` from `labs/angular/node_modules`, C10); `Section 3: our support table puts v22 in active support and v20 and v21 in LTS on 2026-10-18` (a fixture from F9 with its source line; the date is a parameter, not the clock).
- **Questions drilled:** Q39.04, Q39.05.
- **Misconceptions:** "Angular releases a major every six months" (cause: true until v22; "Once true: … until v22.
