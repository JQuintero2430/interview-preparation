### 1. What TypeScript is: erased types, `tsc` and transpile-only tools · ~600 words · SEC-M06-01
- Problem: a value typed `User` arrives from an API as `{ name: null }` and crashes three screens later; "but it compiled".
- Model: types are a proof checked before the program runs, then deleted; analogy: a building inspector's sign-off, not a load-bearing wall. **Diagram** (flowchart): `.ts` → type checker (whole program) and, separately, the emitter or a per-file transpiler (esbuild, Vitest, Node type stripping) → `.js`. "What to notice": only the checker sees types; every transpiler just removes them.
- Mechanism: erasure (no run-time types, no overloads by type); the checker is whole-program, transpilers are per-file, hence `isolatedModules`; Node 24 strip-only mode and the syntax it refuses (enum, namespaces with values, parameter properties) → `erasableSyntaxOnly` [Added in TypeScript 5.8]; TypeScript 7 is the Go port of the same checker (faster, same language), TypeScript 6.0 is the bridge release whose deprecations 7.0 removes; Angular 22 requires `>=6.0 <6.1`.
- Claims and verification: erased annotations (`transpileModule` output); Node strip-only success and the enum error (run `node` on two `.ts` fixtures through `run-node.ts`); version facts from npm/VERSIONS.md and the TypeScript 6.0 notes.
- Also builds the shared helper `labs/ts-js/src/modules/06-ts-type-system-essentials/typecheck.ts`: `typecheck(code, options?) → { code: number; line: number; message: string }[]`, with its own test, and the tsconfig `exclude` for fixtures. Read-only to every later task.
- Callout: *Coming from the backend*: Java generics are erased too, but Java keeps classes and `instanceof` checks at run time; TypeScript erases interfaces and type aliases entirely, so nothing is left to check against.
- Questions drilled: Q06.01–Q06.03.

### 2. Structural typing, assignability and `readonly` · ~550 words · SEC-M06-02
- Problem: a `UserId` and an `OrderId`, both `string`, swapped in a call that compiles; and an object literal with a typo in an optional property that is silently accepted through a variable but rejected inline.
- Model: compatibility by shape ("if it has the members, it fits"), like a socket that accepts any plug with the right pins.
- Mechanism: assignability by members; excess property checks apply only to fresh object literals (`TS2353`); optional properties and weak types (`TS2559`); classes compare structurally too, except that `private`/`protected` members make a class nominal-ish; TypeScript modifiers (`private`, `protected`, `public`, `readonly`) are erased, unlike `#private` (link Q02.09, Q03.09); `readonly` properties and `ReadonlyArray`: shallow, compile-time only, bypassed by aliasing and casts (link Q03.18); branded IDs → 07.
- Claims and verification: `typecheck` codes for each assignability case; `transpileModule` output showing `private` erased.
- Callout: *Coming from the backend* (Java/C# are nominal: two classes with the same fields are not interchangeable).
- Questions drilled: Q06.04–Q06.06.

### 3. Narrowing and control-flow analysis · ~600 words · SEC-M06-03
- Problem: `if (value)` drops the valid `0` and `''`; a check in one function does not help the caller.
- Model: the checker walks your code like a reader with a highlighter, shrinking each variable's type at every test and widening it again at assignments and joins.
- Mechanism: `typeof` (including `typeof null === 'object'`, link 01 §1), `instanceof`, `in`, equality and `switch`, truthiness and its traps, assignments; type predicates (`value is T`) and assertion functions (`asserts value is T`); CFA limits: narrowing is lost in callbacks for `let` variables and after awaits on mutable properties; inferred type predicates from `filter` [Added in TypeScript 5.5]; `this` parameters and `noImplicitThis` (keeps 02's promise).
- Claims and verification: `typecheck` snippets that compile only if narrowing happened; one Vitest run-time test for the truthiness trap.
- Questions drilled: Q06.07–Q06.09; Exercise 06.2.

### 4. Unions, intersections and discriminated unions · ~500 words · SEC-M06-04
- Problem: `{ loading: boolean; data?: T; error?: string }` allows `loading: true` with an `error`, and nobody can tell which combinations are legal.
- Model: a union is "one of these shapes", a tag field is the label on the box, and `never` is the empty box that proves you opened every label.
- Mechanism: union members' common properties; intersections combine requirements (conflicting primitives → `never`); discriminants (literal-typed tag), narrowing by `switch`, exhaustiveness with a `never` check (`TS2322`/`TS2366` when a case is missing); `noFallthroughCasesInSwitch`.
- Claims and verification: `typecheck` codes for the missing-case error and the conflicting intersection.
- Questions drilled: Q06.10–Q06.12; Exercise 06.1.

### 5. `any`, `unknown`, `never`, `void`, and `object` versus `{}` · ~450 words · SEC-M06-05
- Problem: one `any` from a JSON parse spreads through a codebase and disables checking far away.
- Model: `unknown` is a sealed parcel (check before opening), `any` is a parcel with the "inspected" sticker forged; `never` is the type of no value; `void` is "ignore the result".
- Mechanism: `any` is both top and bottom and is contagious; `unknown` requires narrowing; `never` from exhaustive checks and throwing functions; `void` return types accept functions that return values (callback assignability) but a `void` function declaration cannot return a value; `useUnknownInCatchVariables` (keeps 05's promise); `object` (non-primitive), `{}` (anything but `null`/`undefined`), `Object` (the interface; avoid).
- Claims and verification: `typecheck` codes for each assignment; `JSON.parse` return type read from `lib.es5.d.ts` in typescript@6.0.3.
- Questions drilled: Q06.13, Q06.14.

### 6. Enums, literal unions, `as const` and `satisfies` · ~600 words · SEC-M06-06
- Problem: a numeric enum accepts any number; a `const enum` breaks under `isolatedModules`; Node strip-only refuses enums; an annotated config object loses its literal keys.
- Model: a literal union is a list of allowed words; an `as const` object is a dictionary whose words are also values at run time; `satisfies` is a spell-check that leaves your text unchanged.
- Mechanism: numeric enum emit and reverse mapping, string enums, `const enum` (inlined by `tsc`, not by per-file tools; `isolatedModules` rules); literal unions and `as const` objects with `(typeof X)[keyof typeof X]`; why Angular's style guide and many codebases prefer unions (cite the current Angular style guide only if it says so; otherwise state the engineering reasons: erasable, no emit, works with strip-only); `as const` [Added in TypeScript 3.4] readonly literals; `satisfies` [Added in TypeScript 4.9] checks without widening; type assertions (`as`, double assertion through `unknown`) and why they are unchecked.
- Claims and verification: `transpileModule` emits for numeric/string/const enums; `typecheck` codes for a numeric enum assignment and for `satisfies` catching a typo while keeping literal types; Node strip-only enum error (from section 1's fixture).
- Questions drilled: Q06.15–Q06.18; Exercise 06.3.

### 7. `tsconfig`: the `strict` family, module settings and TypeScript 6.0 defaults · ~650 words · SEC-M06-07
- Problem: two projects with "the same" TypeScript disagree on whether `arr[0].name` compiles; an upgrade to 6.0 suddenly includes no `@types` packages.
- Model: `tsconfig` is the contract that decides what "type-correct" means for this codebase; `strict` is a bundle, not one rule.
- Mechanism: what `strict` enables in 6.0 (list read from the 6.0.3 `--help --all` output or the docs: `noImplicitAny`, `strictNullChecks`, `strictFunctionTypes`, `strictBindCallApply`, `strictPropertyInitialization`, `noImplicitThis`, `useUnknownInCatchVariables`, `alwaysStrict`, `strictBuiltinIteratorReturn` – verify the exact list); flags outside `strict`: `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `noPropertyAccessFromIndexSignature`, `noImplicitOverride`; `module`/`moduleResolution` (`bundler` for Angular/Vite apps, `nodenext` for Node packages, `preserve`); `isolatedModules`, `verbatimModuleSyntax` and `import type`; the 6.0 default and deprecation list (Facts above) and `ignoreDeprecations`; `"use strict"` vs `strict` (keeps 02's promise).
- Claims and verification: `typecheck` for each flag's effect (`TS2532`/`TS18048`, `TS2375`/`TS2379` for `exactOptionalPropertyTypes`, `TS1484` for `verbatimModuleSyntax`), the default-`strict` probe, and the `types: []` default (a global from an `@types` package is not visible without `types`).
- Questions drilled: Q06.19–Q06.22; Exercise 06.4.

### 8. Declaration files, `@types` and augmentation · ~450 words · SEC-M06-08
- Problem: a JavaScript library has no types; `window.appConfig` is an error; a plugin adds a method to a library's interface.
- Model: a `.d.ts` file is a contract written next to code you cannot change.
- Mechanism: `.d.ts` files, `declare`, ambient modules (`declare module 'x'`), DefinitelyTyped `@types/*` and the 6.0 `types: []` default, `skipLibCheck`; module augmentation (interface merging inside `declare module 'lib'`) and `declare global` (requires the file to be a module); `typesVersions`/`exports` `types` conditions briefly (link 05 §2 for `exports`).
- Claims and verification: `typecheck` with a second virtual `.d.ts` file (the helper accepts extra files) for augmentation and `declare global`; one npm package's real `package.json` `types` field read from `node_modules`.
- Questions drilled: Q06.23, Q06.24.

## Exercises (4, ceiling 4)

Each lives in `labs/ts-js/src/modules/06-ts-type-system-essentials/` with one `describe` per exercise (`E06.n …`) and one `it` per criterion, titled with the criterion's wording, in checklist order. Compile-time criteria are tested with the `typecheck` helper (the code under test is imported as source text with Node's `fs` through a variable specifier, or the test snippet imports the solution's types from a virtual file).

1. **Exercise 06.1 · An exhaustive reducer** (EX-M06-01; section 4). A discriminated `Action` union and `reduce(state, action)` with an `assertNever` default. Criteria: each action produces the expected state; an unknown action at run time throws with its `type`; adding a variant without a case is a compile error (`typecheck` on a variant of the source); the state type forbids `loading` with `error`.
2. **Exercise 06.2 · A guard for API data** (EX-M06-02; sections 3, 5). `isUser(value: unknown): value is User` and `assertUser(value: unknown): asserts value is User`, with nested `address` and optional `phone`. Criteria: accepts a valid payload; rejects each malformed field (table of cases); `null`, arrays and primitives are rejected; after the guard, property access compiles without assertions; the assertion form throws a `TypeError` naming the first bad field. Follow-up links Zod in 07.
3. **Exercise 06.3 · A typed configuration table** (EX-M06-03; section 6). A feature-flag table declared `as const satisfies Record<string, FlagConfig>`; derive `FlagName` from its keys; `isEnabled(name: FlagName)`. Criteria: a misspelled flag name is a compile error; a misspelled config property is a compile error (`satisfies`); the literal values survive (a test reads the exact union); no `enum` and no run-time cost beyond the object (emit checked with `transpileModule`).
4. **Exercise 06.4 · Make a loose module strict** (EX-M06-04; sections 3, 5, 7; integrates). A provided `legacy-cart.ts` source (a string fixture) that compiles under `strict: false` only; write `cart.ts` with the same run-time behavior that has zero diagnostics under `strict`, `noUncheckedIndexedAccess` and `exactOptionalPropertyTypes`. Criteria: the legacy source has the listed diagnostics under strict (asserted codes); the new source has none; the same run-time tests pass for both behaviors; no `any`, no non-null `!`, no `as` (checked by a source scan).
