*Server-Sent Events and long polling, the standards (w, d):*
- F9. **WHATWG HTML §9.2** (fetched 2026-10-21): the constructor takes a URL and only `{ withCredentials }`, no headers; requests use cache mode `no-store` and send `Accept: text/event-stream`; **a 200 with `Content-Type: text/event-stream` opens the stream; a 204 makes the user agent stop reconnecting; any other status or content type "fails the connection" (no reconnection); a network error, or the body ending, "reestablishes the connection"**: fire `error`, wait the reconnection time (user agents may add backoff), then reconnect sending `Last-Event-ID` when the last event ID is not empty; `close()` aborts and sets `CLOSED`. - F10. **WHATWG event-stream parsing**: UTF-8 only, an optional leading BOM is skipped; lines end with CRLF, LF or CR; a line starting with `:` is a comment; `field:value` strips exactly **one** leading space from the value; `data` appends the value plus LF to the data buffer; `event` sets the type; `id` sets the last event ID unless the value contains NUL, and a bare `id` resets it to empty; `retry` sets the reconnection time only if the value is all ASCII digits; unknown fields are ignored; **a blank line dispatches**: an empty data buffer dispatches nothing, a trailing LF is removed, the type defaults to `message`; the last event ID persists across events and is copied onto each event's `lastEventId`; **an incomplete event at the end of the stream is discarded**. Spec examples quoted by Q43.04 and Exercise 43.1: the four-block stream with `: test stream`, `data: first event` / `id: 1`, `data:second event` / `id`, `data:  third event`; the stream `data`, blank, `data`, `data`, blank, `data`, `data:` (the first block fires an event with empty data, the middle one an event whose data is a single newline, and the last is discarded because no blank line follows it); `data:test` and `data: test` are the same.
- F11. **RFC 6455**: §1.3 the opening handshake is an HTTP/1.1 `GET` with `Upgrade: websocket`, `Sec-WebSocket-Key`, and the server answers `101 Switching Protocols` with `Sec-WebSocket-Accept` (the key plus the GUID `258EAFA5-E914-47DA-95CA-C5AB0DC85B11`, SHA-1, base64); §5.1 a client MUST mask every frame it sends and a server MUST NOT mask; §5.5.2 a Ping "may serve as a keepalive"; §7.4.1 1000 normal closure, 1001 going away, "1006 is a reserved value and MUST NOT be set as a status code in a Close control frame by an endpoint" (the user agent reports it when the connection closed abnormally); §10.2 servers "SHOULD verify the |Origin| field" and may answer 403; §10.5 "This protocol doesn't prescribe any particular way that servers can authenticate clients".
- F12. **STOMP 1.2** (stomp.github.io): a frame is a command line, `header:value` lines, a blank line, the body and a NULL octet; `content-length` is needed when the body contains NULL octets; `CONNECT`/`STOMP` with `accept-version`, `host`, `heart-beat`; `CONNECTED`; `SEND`, `SUBSCRIBE` (with `id`), `UNSUBSCRIBE`, `MESSAGE` (with `subscription`, `message-id`), `RECEIPT`, `ERROR`, `DISCONNECT` with `receipt`; heart-beating: `heart-beat:<cx>,<cy>` and the sender's interval is "MAX(<cx>,<sy>)", 0 means none, the heart-beat is an EOL, and the receiver "SHOULD" be tolerant of timing.

### 1. Choosing a transport: polling, long polling, Server-Sent Events, WebSockets, and Web Push when no tab is open · delta 480 (380 + 100 verification paragraph) · SEC-M43-01
- **Problem:** a notification badge polls every two seconds and the API's access log is 90% empty answers; a team picks WebSockets for a one-way price feed and then has to build reconnection, authentication and proxy support by hand; a user with no tab open never sees an alert (37's handoff); long polling in Spring holds a request thread per waiting client (41:931's "pushed events").
- **Model:** four ways to get news from the server, by what stays open and who may send: **polling** (a new request every N seconds; nothing stays open; 23 §8 and Q23.29 own the Angular pattern), **long polling** (the server holds the request until there is news or a timeout, then the client re-requests at once; RFC 6202, F13; `DeferredResult` in Spring, F17), **Server-Sent Events** (one long HTTP response the server keeps writing text events into; server to client only; automatic reconnection with resume, F9), **WebSockets** (an HTTP request upgraded to a two-way frame channel, F11; no reconnection, no message format, no resume built in). **Web Push** reaches a browser with no tab open through the browser vendor's push service (37 §7 owns the client side): the backend POSTs an encrypted payload with a `TTL` to the subscription's endpoint and signs a VAPID JWT (RFC 8030 §5, 8291, 8292; F14); no Spring API exists, so a library or a direct HTTP call does it (read, not run). Cost per message: polling pays a request per interval whether or not there is news; long polling pays a request per message plus up to three network transits of latency (F13); SSE and WebSockets pay one connection, then only the bytes of each event. Under HTTP/1.1 each SSE connection holds one of about six per-host connections (F15, 09 §3 for HTTP/2's multiplexing). Analogy: calling the shop every hour, staying on hold until they have news, a radio that only the shop speaks into, a phone line both can speak on; and a letter when you are not home. Diagram: `flowchart TD` decision tree: "server to client only?" → yes: "many events, tab open?" → SSE; "rare news" → polling; no: "both directions often?" → WebSocket (STOMP on top); side branch "no tab open?" → Web Push; "proxy or old infrastructure kills long connections?" → long polling.
- **Mechanism:** **read from RFC 6202 §2.2** (F13) to answer "why is long polling slower than it looks?": every message costs a full request and response, and a message that arrives while the client is re-requesting waits for the new request; **read from the WHATWG spec and RFC 6455** what each protocol gives for free (SSE: reconnection, `Last-Event-ID`; WebSocket: nothing above frames, F9, F11). Our `transport-model.ts` counts requests, bytes of headers and worst-case latency for N events under each transport (tests).
- **Code:** (1) TypeScript: `costOf(transport, events, interval)` in our model (Excerpt of `concepts/transport-model.ts`), which counts one request per poll or per long-poll answer, because that is where the header overhead of F13 comes from; (2) Java: a long-poll endpoint returning `DeferredResult<List<Notification>>` with an explicit timeout and `onTimeout` setting an empty result, so a timed-out request answers 200 with nothing instead of an error (F17; banner); (3) the Web Push request as `text`: `POST` to the endpoint with `TTL`, `Content-Encoding: aes128gcm`, `Authorization: vapid t=…, k=…` (F14; lines from RFC 8030 and 8292 only).
- **Callouts:** none required; the Coming from the backend view is §3's.
- **First-use definitions:** polling, long polling, Server-Sent Events (SSE), WebSocket, Web Push (link 37 §7), push service, VAPID, `TTL` header, per-host connection limit, full duplex.
- **Verification:** `labs/ts-js/src/modules/43-fullstack-realtime/concepts/{transport-model.ts,section-1-transports.test.ts}` (our model, C16): `Section 1: polling every 2 s for an hour makes 1800 requests whatever the number of events`; `Section 1: long polling makes one request per delivered event plus one per timeout`; `Section 1: an event that arrives while a long poll is re-requesting waits for the next request`; `Section 1: a stream pays one request for any number of events`.
- **Questions drilled:** Q43.01, Q43.02, Q43.03.
- **Misconceptions:** "WebSockets are always the modern choice" (cause: they are the best-known push technology, so they look like the default; for one-way feeds SSE gives reconnection and resume that a WebSocket app must build, F9, F11); "SSE is limited to six connections, so it does not scale" (cause: MDN's warning is prominent; the limit is per browser and host under HTTP/1.1 and HTTP/2 multiplexes, F15, 09 §3); "long polling is just slow polling" (cause: both re-request; long polling answers as soon as there is news, so latency is near a stream's except after each message, F13); "Web Push can replace a live connection" (cause: it reaches closed tabs, so it seems more powerful; it needs a subscription with user permission, goes through a third party with a `TTL`, and is meant for notifications, F14, 37 §7).

### 2. Server-Sent Events on the wire: the `text/event-stream` format and how `EventSource` reconnects · delta 380 · SEC-M43-02 (Opus)
- **Problem:** events arrive twice after a reconnect, or are lost; a server sends `data: {"a":1}` without a blank line and the client never fires; a 500 during a deploy stops all clients for good while a dropped connection reconnects by itself; someone sets `retry: 5s` and it is ignored.
- **Model:** an event stream is UTF-8 text of `field: value` lines; a **blank line dispatches** the event built so far; `data` lines join with LF; `event` names the type (`message` by default); `id` sets the **last event ID**, which persists and is sent back as `Last-Event-ID` on reconnect; `retry` sets the **reconnection time** (digits only); `:` lines are comments (heartbeats) (F10). Reconnection: a network error or the end of the body → wait the reconnection time → reconnect with `Last-Event-ID`; 204 → stop; any other status or a wrong content type → fail for good (F9). Analogy: a ticker tape where each message ends with a blank gap, and each numbered message lets the operator resume from the last number you read. Diagram: `sequenceDiagram`: EventSource → server `GET` `Accept: text/event-stream` → 200 `text/event-stream` → `id: 41` event → `id: 42` event → connection drops → `error` event, wait `retry` → `GET` with `Last-Event-ID: 42` → server resumes at 43; a note: 204 stops, 500 fails without retry.
- **Mechanism:** **read from WHATWG HTML §9.2** (F9, F10; lesson 16: re-read which responses stop reconnecting before writing) to answer "why does a 500 stop `EventSource` but a dropped connection does not?": a failed response "fails the connection" while a network error or end of body "reestablishes" it; the server signals "stop" with 204. Our `sse-parser.ts` implements the parsing algorithm, and `sse-reconnect.ts` the reconnect decision, both labeled ours (C16).
- **Code:** (1) the WHATWG four-block example stream (`text` fence, F10); (2) TypeScript: `createSseParser(onEvent)` (Excerpt of `concepts/sse-parser.ts`), which keeps the partial line across chunks and remembers a trailing CR, because a chunk may end between CR and LF and a CRLF must count once; (3) `nextStep(response | networkError, state)` returning `reconnect(after, lastEventId)` or `stop` (Excerpt of `concepts/sse-reconnect.ts`), because the decision depends only on the status, content type and stored state, so it is testable without a socket.
- **Callouts:** none required (§3 has the backend view).
- **First-use definitions:** event stream, field, dispatch, data buffer, event type, last event ID, `Last-Event-ID`, reconnection time, `retry` field, comment line, heartbeat, `readyState`.
- **Verification:** `labs/ts-js/src/modules/43-fullstack-realtime/concepts/{sse-parser.ts,sse-reconnect.ts,section-2-sse-protocol.test.ts}` (our models; streams built by the test): `Section 2: the WHATWG example stream dispatches three events and the bare id resets the last event ID`; `Section 2: a CRLF split across two chunks ends one line, not two`; `Section 2: an event with no blank line before the end of the stream is discarded`; `Section 2: retry with a non-digit value is ignored`; `Section 2: a dropped connection reconnects with Last-Event-ID, a 204 stops and a 500 fails without reconnecting`.
- **Questions drilled:** Q43.04, Q43.05. Practised in Exercise 43.1.
- **Misconceptions:** "each `data` line is a separate event" (cause: one line per message is the common case in demos; lines join until a blank line, F10); "`EventSource` retries every error" (cause: it reconnects after drops, which is what people see in development; a non-200 or wrong content type fails for good, F9); "`retry: 5s` sets five seconds" (cause: other configs accept units; the field takes ASCII digits only and the value is milliseconds, F10); "the server must remember each client to resume" (cause: resuming sounds like a session; the client sends `Last-Event-ID`, and the server needs only an event log keyed by id, §3).

### 3. Server-Sent Events in Spring: `SseEmitter` in Spring MVC and a `Flux` of `ServerSentEvent` in WebFlux · delta 380 · SEC-M43-03
- **Problem:** an `SseEmitter` endpoint works locally and every client is cut at 30 seconds in staging; the list of emitters grows with every page reload until the heap fills; a client that closed its tab is only noticed when the next event is sent an hour later; after a deploy, clients reconnect with `Last-Event-ID` and the server ignores it (41:931, 41:2047 handoffs).
- **Model:** in Spring MVC a controller returns an **`SseEmitter`**; the request goes async (the Servlet thread returns), and any thread calls `send(event().id(…).name(…).data(…))`, which writes `id:`/`event:`/`data:` lines (F16); the **timeout** is the emitter's, else MVC's `spring.mvc.async.request-timeout`, else the container's (F16, F19, C1); `onCompletion`/`onTimeout`/`onError` must remove the emitter from any registry; **the Servlet API does not report a client that went away**, so a periodic comment event makes the write fail and completes the emitter (F17). In WebFlux a controller returns a **`Flux<ServerSentEvent<T>>`** with `text/event-stream` (F18): cancellation reaches the flux when the connection closes and a write fails, so heartbeats matter there too (F18, C10). Resume: read the `Last-Event-ID` header and replay newer events from a bounded **event log**; if the id is older than the log, send a "reload" event. Analogy: a radio presenter (the emitter) who cannot see whether anyone is listening and only learns the line is dead when the next broadcast fails. Diagram: `flowchart LR`: controller → `SseEmitter` registered in a map → service thread `send(...)` → container writes lines; `onCompletion` / `onTimeout` / `onError` → remove from map; a scheduled heartbeat → `send(comment)` → write fails → `completeWithError` → removed.
- **Mechanism:** **read from Spring Framework 7.0.9 `mvc-ann-async.adoc`** (F17) to answer "why does the server not notice a closed tab?" (no Servlet notification; only a failed write reveals it) and **from `SseEmitter`'s javadoc** (F16) why staging cuts at 30 seconds (the timeout falls through to the container's default, C1); our `sse-format.ts` mirrors `SseEventBuilderImpl`'s line format (internal, F16) and `event-log.ts` the replay logic, both ours (C16).
- **Code:** (1) Java: an `SseEmitter` endpoint with `new SseEmitter(0L)` or an explicit timeout, registration in a `ConcurrentHashMap`, the three callbacks removing it, reading `@RequestHeader(name = "Last-Event-ID", required = false)` to replay, and a scheduled comment heartbeat, because a write is the only way to detect a gone client (F16, F17; banner); (2) Java: the WebFlux variant returning `Flux<ServerSentEvent<Price>>` built with `ServerSentEvent.builder().id(…).event(…).data(…)` (F18; heartbeat only as C10 decides; banner); (3) TypeScript: `formatEvent` and `EventLog.since(lastEventId)` (Excerpt of `concepts/sse-format.ts` and `concepts/event-log.ts`), which returns either the newer events or a `too-old` result, because a log that silently skips is worse than an explicit reload.
- **Callouts:** **Coming from the backend** (required): an `SseEmitter` is a `DeferredResult` that can be completed many times (F17); **where it breaks**: the client is a browser that reconnects by itself and replays `Last-Event-ID`, so the server must be idempotent per id, and a proxy between them may buffer or cut the stream (44 file-level once).
- **First-use definitions:** `SseEmitter`, async request processing, emitter registry, async request timeout, `ServerSentEvent`, event log (replay buffer), heartbeat comment.
- **Verification:** `labs/ts-js/src/modules/43-fullstack-realtime/concepts/{sse-format.ts,event-log.ts,section-3-spring-sse.test.ts}` (imports `sse-parser.ts` read-only; our mirror of F16's format): `Section 3: our SseEmitter-style lines parse back into the same id, event and data`; `Section 3: a multi-line data value becomes several data lines and parses back to one value`; `Section 3: the event log replays only events after Last-Event-ID`; `Section 3: a Last-Event-ID older than the log returns too-old instead of a partial replay`.
- **Questions drilled:** Q43.06, Q43.07, Q43.08.
- **Misconceptions:** "an `SseEmitter` without a timeout never times out" (cause: "no timeout set" reads like "infinite"; the MVC or container default applies, F16, F19); "the server knows when the browser tab closes" (cause: TCP closes, so it feels observable; the Servlet API gives no notification until a write fails, F17); "WebFlux needs no heartbeat" (cause: reactive streams cancel on disconnect; the disconnect is only seen on a write, F18); "`Last-Event-ID` is handled by Spring" (cause: the browser sends it automatically, so it looks end to end; Spring passes the header, and the app must read it and replay, F16).

### 4. The Angular SSE client: `EventSource` or a `fetch` stream as an Observable, and when `HttpClient` fits · delta 380 · SEC-M43-04
- **Problem:** a component opens an `EventSource` in `ngOnInit` and never closes it, so navigating back and forth opens six connections and the app stalls under HTTP/1.1; the SSE endpoint needs `Authorization: Bearer` and `EventSource` cannot send it; someone streams with `HttpClient` and `reportDownloadProgress` and memory climbs for hours; the page never re-renders without zone.js (27:2579 handoff).
- **Model:** **Angular has no SSE API** (F7): the client wraps a platform source in an **Observable** whose teardown closes it (22 §3: a cold Observable, one connection per subscriber unless shared, §8). Three sources: **`EventSource`** (cookies only via `withCredentials`, no headers, reconnection and `Last-Event-ID` built in, named events through `addEventListener`, F9); **`fetch` with a stream reader** (any header, `AbortController` to stop, but parsing and reconnection are yours: §2's parser, Exercise 43.1; 09 §2 and Q09.04 own `getReader`); **`HttpClient` with `reportDownloadProgress`** (interceptors apply, but `partialText` is cumulative and the body is held until the end, F8; fine for a finite stream, not for an endless one; 27 §9 owns progress events). `EventSource` emits `error` both for a reconnect and a fatal failure; `readyState` tells them apart (`CONNECTING` versus `CLOSED`, F9). Zoneless: a signal set from the subscription schedules rendering (21 §5, Q21.17). Analogy: a radio (EventSource: tune in, it re-tunes by itself, but you cannot tell the station who you are), a phone call you dial yourself (fetch: you can say who you are, but redial is yours), a recorder that keeps the whole tape before you can play it (HttpClient progress). Diagram: `stateDiagram-v2`: Subscribed → `CONNECTING` → `OPEN` (emit values) → error with `readyState` `CONNECTING` (emit nothing, wait) → `OPEN`; error with `CLOSED` → Observable errors; unsubscribe from any state → `close()`.
- **Mechanism:** **read from `@angular/common` 22.2.1 `FetchBackend`** (F8) to answer "why not `HttpClient` for SSE?" (cumulative `partialText`, body kept until the end; `HTTP_FETCH_MAX_RESPONSE_SIZE` is internal and `null` in the browser); **read from WHATWG §9.2** (F9) why `EventSource` takes no headers (only `withCredentials`) and how `readyState` separates a reconnect from a failure. Teardown of a fetch stream aborts the request (C5).

### 5. WebSockets and STOMP in Spring: the handshake, frames, `@MessageMapping`, brokers, user destinations and heart-beats · delta 400 · SEC-M43-05 (Opus)
- **Problem:** a chat built on raw WebSocket messages grows its own "type" field, routing table and acknowledgments; a message for one user reaches everyone; the client's heart-beat timer closes a healthy connection every minute; a second instance behind the load balancer sees only half the subscribers.
- **Model:** the **handshake** is an HTTP `GET` with `Upgrade: websocket` answered `101` (F11); then **frames** flow both ways (clients mask, servers do not). **STOMP** puts a text protocol on top: commands (`CONNECT`, `SUBSCRIBE`, `SEND`, `MESSAGE`, …), headers, a body and a NULL byte (F12). Spring routes by **destination prefix**: `/app/**` to `@MessageMapping` methods, `/topic/**` and `/queue/**` to the broker; a method's return value goes to `/topic/<same>` or where `@SendTo` says (F20); **user destinations** (`/user/queue/x`) resolve to the current user's sessions (F23, C3). The **simple broker** is in memory, single instance (F20); the **broker relay** forwards to RabbitMQ or ActiveMQ (§9, F21). **Heart-beats**: each side offers `heart-beat:<send>,<expect>` and the agreed interval per direction is the max of what one sends and the other expects, 0 disabling it; Spring's simple broker answers `0,0` unless it has a `TaskScheduler` (F12, F20). Analogy: a post office on top of a telephone line: the line (WebSocket) carries sound, STOMP adds addressed envelopes, and Spring is the sorting office with counters for the app and pigeonholes for the broker. Diagram: `sequenceDiagram`: Browser → Spring `GET /ws` `Upgrade` → `101` → `CONNECT` (`heart-beat:10000,10000`) → `CONNECTED` (`heart-beat:0,0`) → `SUBSCRIBE /topic/room.1` → `SEND /app/room.1` → `@MessageMapping("/room.{id}")` → broker → `MESSAGE` to subscribers.
- **Mechanism:** **read from Spring Framework 7.0.9 `StompSubProtocolHandler`** and `handle-simple-broker.adoc` (F20; lesson 16: re-read which side sends and which checks before writing) to answer "why does my client get `heart-beat:0,0`?" (no `TaskScheduler` on the simple broker); **read from STOMP 1.2** the max rule (F12) and **from stompjs 7.5.0** the client's tolerance multiplier (F3). The docs' "stompjs splits at 16K" is stated against stompjs 7.5.0's 8 KiB default with splitting off (F22, F3). Our `stomp-frame.ts` encodes, decodes and negotiates (C16).
- **Code:** (1) Java: `@EnableWebSocketMessageBroker` with `registerStompEndpoints` (`addEndpoint("/ws")`, `setAllowedOriginPatterns`, §7) and `configureMessageBroker` (`setApplicationDestinationPrefixes("/app")`, `enableSimpleBroker("/topic", "/queue").setTaskScheduler(…).setHeartbeatValue(new long[] {10000, 10000})`), because without the scheduler the broker sends no heart-beats (F20; banner); (2) Java: a `@MessageMapping("/room.{id}")` method with `@DestinationVariable` and `@SendTo`, and `@SendToUser("/queue/errors")` for a per-user reply (F20, F23; banner); (3) a `CONNECT` and a `MESSAGE` frame as `text` (F12); (4) TypeScript: `encodeFrame`, `decodeFrame` and `negotiateHeartBeat(client, server)` (Excerpt of `concepts/stomp-frame.ts`), which applies the max rule per direction and returns 0 when either side offers 0.
- **Callouts:** **Coming from the backend** (required): `@MessageMapping` is `@RequestMapping` for messages and the simple broker is an in-process `ApplicationEventMulticaster`-like fan-out; **where it breaks**: there is no request per message to load-balance, a session lives on one instance for hours, and the simple broker cannot span instances (F20, §9).
- **First-use definitions:** opening handshake, `101 Switching Protocols`, frame, masking, close code, STOMP, destination, application destination prefix, `@MessageMapping`, simple broker, broker relay (defined in §9; forward link), user destination, `@SendToUser`, heart-beat, SockJS (one "once true" bullet).
