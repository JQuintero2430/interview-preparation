### 1. ES modules: static structure, linking and live bindings · ~800 words · SEC-M05-01
- Problem: a script-tag app where load order and globals decide correctness; two scripts define `config`.
- Model: the module graph as a build manifest read before any code runs; analogy: a wiring diagram checked before power is switched on. **Diagram** (flowchart): parse → load dependencies → link (bindings resolved) → evaluate post-order. "What to notice" sentence.
- Mechanism: Module Records, the three phases (spec terms: `LoadRequestedModules`, `Link`, `Evaluate`, §16.2.1.5 area, check numbers in the current ECMA-262 HTML); imports are read-only views of the exporter's binding (live); each module evaluates once per realm and graph (singleton); module code is strict and `this` is `undefined` at the top level; post-order evaluation; cycles: a module may read a binding before the exporter evaluated it → TDZ `ReferenceError` (link 02 §2), function declarations are hoisted and work.
- Claims and verification: live binding, evaluation order, once-only evaluation, cycle TDZ and the hoisted-function escape, top-level `this` → fixtures under `labs/ts-js/src/outputs/05-…/fixtures/` run with `node` from tests named `Section 1: …` or after the Q IDs; spec algorithm names from ECMA-262 (cite).
- Callout: *Coming from the backend*, Java packages/`import` are compile-time name resolution while ESM imports are runtime bindings; where the analogy breaks: Java class init is lazy per class, ESM evaluation is eager per graph.
- Questions drilled: Q05.01–Q05.04.

### 2. CommonJS, interop and dynamic `import()` · ~750 words · SEC-M05-02
- Problem: a library that `require`s conditionally ships whole to the browser; a CommonJS consumer cannot `require` an ESM-only package (before Node 22.12/20.19).
- Model: CommonJS is a function call that returns a value (`module.exports`) at run time; ESM is a declaration read before run time.
- Mechanism: the CommonJS wrapper function (`exports, require, module, __filename, __dirname`), the `require` cache and partial exports in cycles (contrast with section 1), value copies vs live bindings; interop in Node 24: `import` of CommonJS gives `module.exports` as default plus named exports detected by static analysis (cjs-module-lexer), `require(esm)` returns the namespace object and throws `ERR_REQUIRE_ASYNC_MODULE` for a graph with top-level `await` (check the code and versions in nodejs.org/api/modules.html and the Node changelog: unflagged in 22.12.0 and 20.19.0); `import()` returns a promise of the namespace, works in both systems, and is the code-splitting point for bundlers (link 24 lazy routes, 18 `@defer`); tree-shaking prerequisites: static `import`/`export`, no side effects at module top level, the `sideEffects` field and `/*#__PURE__*/` annotations (esbuild and webpack docs), why CommonJS defeats it.
- Claims and verification: CommonJS copy vs ESM live binding, partial exports in a CommonJS cycle, default/named interop, `require(esm)` result and its error with top-level `await`, `import()` caching (same namespace object twice) → fixtures run with `node`; bundler behavior → cited docs (esbuild "tree shaking", webpack "sideEffects"), not observed.
- Legacy subsection: AMD/UMD in one paragraph, with why they faded.
- Questions drilled: Q05.05–Q05.08.

### 3. Import maps, `import.meta` and import attributes · ~500 words · SEC-M05-03
- Problem: bare specifiers (`import 'lodash-es'`) do not resolve in a browser without a bundler; a JSON file imported as JavaScript is a security hole (why the `type` attribute exists).
- Model: an import map is a lookup table the browser consults before fetching; `import.meta` is per-module context.
- Mechanism: `<script type="importmap">`, `imports` and `scopes`, one map per document rules (HTML Standard; multiple import maps support status via MDN BCD, cite); `import.meta.url`, `import.meta.resolve` (HTML and Node), Node's `dirname`/`filename` (Node docs, versions); import attributes `with { type: 'json' }` [Added in ES2025] and the older `assert` syntax (Once true… removed: check V8/Node version history, cite); JSON modules give a default export only.
- Claims and verification: Node `import.meta` fields, JSON import with and without the attribute (the error code) → fixtures; import maps → HTML Standard and MDN, cited; Native Federation's use of import maps → one sentence + link 38.
- Questions drilled: Q05.09, Q05.10.

### 4. Garbage collection and memory leaks · ~750 words · SEC-M05-04
- Problem: a dashboard tab that grows 20 MB per route change until it crashes; nothing "holds" the data in the developer's mind.
- Model: memory as a graph from roots; anything unreachable is garbage. Analogy: a tour of the warehouse starting at the doors; boxes no corridor reaches are thrown away. **Diagram** (flowchart): roots → objects, one reachable path kept alive by a forgotten listener.
- Mechanism: roots (globals, the stack, active handles such as timers and listeners), mark-and-sweep (mark-compact) and why reference counting fails on cycles; generational hypothesis, young generation scavenger and old generation in V8 (v8.dev "Trash talk" / Orinoco posts, cite; conceptual only); the leak catalogue: listeners on long-lived targets, uncleared intervals, closures (one sentence + [Q02.08](02-js-scope-closures-this.md#q02-08)), detached DOM nodes still referenced from JS, unbounded caches; how to see one (heap snapshot comparison; DevTools workflow is module 31's).
- Claims and verification: a reachable-through-timer object is not collected and becomes collectable after `clearInterval` → fixture run with `node --expose-gc` using a `FinalizationRegistry` or `WeakRef` probe (observed in Node 24.21, labelled "observed, not guaranteed by the spec"); V8 internals → cited.
- Callout: *Coming from the backend*, the JVM's generational collectors and `OutOfMemoryError` heap dumps; where the analogy breaks: a browser tab has one heap per agent, no `-Xmx` tuning, and leaks often come from the DOM, not from the language.
- Questions drilled: Q05.11, Q05.12. Exercise 05.1.

### 5. Weak references: `WeakMap`, `WeakSet`, `WeakRef` and `FinalizationRegistry` · ~650 words · SEC-M05-05
- Problem: a per-object cache (the E03.2 proxy cache, a computed-style cache) keeps every object alive forever.
- Model: a weak edge is one the collector ignores when it decides reachability.
- Mechanism: `WeakMap` as an ephemeron table (key keeps value alive only while the key is alive), no iteration and no `size` and why (observable GC would be non-deterministic); keys must be objects or non-registered symbols [Changed in ES2023: Symbols as WeakMap keys]; `WeakRef.deref()` and the "kept alive until the end of the current job" rule (spec `AddToKeptObjects`, cite); `FinalizationRegistry` callbacks may never run (proposal README warnings, cite); when to use none of them (an LRU with a bound).
- Claims and verification: `WeakMap` has no `size`/iteration, registered-symbol key throws `TypeError`, `deref()` same-job stability, a collected `WeakRef` returns `undefined` after `gc()` and a later task → tests (pure ones in Vitest; GC ones via `node --expose-gc` fixtures, observed in Node 24.21, not guaranteed).
- Questions drilled: Q05.13–Q05.15.

### 6. Errors: subclasses, causes, aggregation and global handlers · ~750 words · SEC-M05-06
- Problem: a log line "Error: failed" with no idea which HTTP call or which user input caused it; `catch (e) { throw new Error('save failed') }` destroys the original stack.
- Model: an error is a value plus a chain of "because" links; handling happens at boundaries.
- Mechanism: `Error` subclasses with `name` and extra fields (class fields, `super(message, { cause })`), `cause` [Added in ES2022] and how consoles print it (Node 24 shows `[cause]`, observed), `AggregateError` [Added in ES2021] (link Q04.16 for `Promise.any`), `stack` is non-standard (V8 `Error.captureStackTrace`, cite V8 docs), `instanceof` fails across realms (iframes, `vm` contexts) and `Error.isError` [Added in ES2026] checks the internal slot (proposal README), `throw` of a non-Error and `unknown` in `catch` (TypeScript `useUnknownInCatchVariables`, link 06); global handlers: `window` `error` event / `onerror` (HTML Standard), Node `uncaughtException` and why the process should exit (Node docs), rejections → link 04 §8 and Q04.27, Angular's `ErrorHandler` → link 37.
- Claims and verification: subclass `name`/`instanceof`, `cause` chain walk, `AggregateError.errors`, `Error.isError` true across a `vm` realm where `instanceof` is false (fixture with `node:vm`), non-Error throws → tests; browser handlers → cited.
- Callout: *Coming from the backend*, Java's checked exceptions and `Throwable.getCause()`/`addSuppressed`; where it breaks: JavaScript has no checked exceptions and anything can be thrown.
- Questions drilled: Q05.16–Q05.18. Exercise 05.2.

### 7. Explicit resource management: `using` and `DisposableStack` · ~550 words · SEC-M05-07
- Problem: a `try/finally` per resource nests three deep, and a cleanup that throws hides the original error.
- Model: `using` ties a resource's cleanup to a block, the way a stack frame ties a local's lifetime.
- Mechanism: `using` / `await using`, `Symbol.dispose` / `Symbol.asyncDispose`, reverse-order disposal, `SuppressedError` (`error` and `suppressed`) when both the body and a disposer throw, `DisposableStack` / `AsyncDisposableStack` (`use`, `adopt`, `defer`, `move`); status: Stage 4 May 2026, **ES2027** (marker `[Added in ES2027]`, noting the edition is published mid-2027), shipped in Node 24 (observed) and in browsers per MDN BCD (cite versions); TypeScript support since 5.2 and what the downlevel emits (check `tsc` output in the task).
- Claims and verification: disposal order, `SuppressedError` shape, `DisposableStack.move`, `await using` ordering → Vitest tests (downleveled) **and** one fixture run natively by `node`, so both paths are shown; status → finished-proposals, TC39 notes 2026-05, BCD.
- Callout: *Coming from the backend*, Java try-with-resources and `AutoCloseable`, C# `using`; where it breaks: no checked `close` exceptions, disposal is opt-in per object via a symbol, and `using` declarations are block-scoped `const`s.
- Questions drilled: Q05.19, Q05.20. Exercise 05.1 (a listener handle that is `Disposable`).

- Questions drilled: Q05.21.

## Exercises (3, ceiling 3)

Each lives in `labs/ts-js/src/modules/05-js-modules-memory-modern-features/` with one `describe` per exercise (`E05.n …`) and one `it` per criterion, titled with the criterion's wording, in checklist order (the convention 01–04 settled on).

1. **Exercise 05.1 · A leak-free listener handle** (EX-M05-01; sections 4, 7). `listen(target, type, handler, options?)` returns a handle that is `Disposable` and also removes itself when an optional `AbortSignal` aborts. Criteria: the handler runs until disposal; `using` removes it at block end; an aborted signal removes it and later dispose is a no-op; an already-aborted signal never adds it; disposal is idempotent; several handles in a `DisposableStack` are removed in reverse order. Tests on Node's `EventTarget`.
2. **Exercise 05.2 · An error chain toolkit** (EX-M05-02; section 6). `class AppError extends Error` with `code` and `cause`; `describeChain(error)` returns the lines of a `cause` chain, expands `AggregateError.errors` with indentation, stops on cycles, and accepts non-Error throwables; `isAppError` works across realms via `Error.isError` plus a brand. Criteria each mapped to a test, including a `node:vm` realm case.
3. **Exercise 05.3 · A tiny CommonJS loader** (EX-M05-03; sections 1, 2, 6; integrates). `createRequire(files)` over an in-memory `{ path: source }` map: wrapper function, module cache, `module.exports` vs `exports`, partial exports in a cycle (asserted against what real Node prints for the same two files, run as fixtures), a missing module error with `code: 'MODULE_NOT_FOUND'` and `cause` for a failing module body. Alternative approach and follow-ups contrast it with ESM's link-before-evaluate.
