- F9. **The `min`/`max` truth in v22 (r, c, R-ng).** In `@angular/forms` **22.2.1 and 21.2.25** (`npm pack` compared) `minValidator` and `maxValidator` are identical (`parseFloat` of the value) and `MinValidator`/`MaxValidator` have the selector `input[type=number][min][formControlName],input[type=number][min][formControl],input[type=number][min][ngModel]` (the same for `max`). Run: `min="5"` on a `type="text"` input bound to a control with value `'1'` → no error (the directive does not match); on a `type="number"` input with value `1` → `{ min: { min: 5, actual: 1 } }`; `NumberValueAccessor` turned the typed `'7'` into `7`. The 22.0.0 **breaking change** under `### forms` reads "`min` and `max` validation rules no longer support string values. Bound values must be numbers or null." with the commit "remove string support from min and max validation rules"; the Signal Forms typings declare `min<TValue extends number | null, …>(path, minValue: number | LogicFn<…>)` `@publicApi 22.0` (`types/signals.d.ts`). **So the SYLLABUS checkbox's "`min`/`max` numeric only `[Changed in v22]`" is a Signal Forms rule change (module 26), not a change to `Validators.min`/`max` or the `min`/`max` directives**, which still parse strings. ### 1. Two forms APIs: template-driven and reactive, and the control, directive and accessor triangle · delta 900 (800 + 100 verification paragraph) · SEC-M25-01

### 6. Async validators: pending status, cancellation and debouncing · delta 800 · SEC-M25-06
- **Problem:** a username-availability check fires a request on every keystroke; responses arrive out of order and an old "taken" overwrites a newer "free"; the submit button stays disabled forever because the form is `PENDING`; the check runs even when the username is empty.
- **Model:** an **async validator** returns an Observable or Promise of `ValidationErrors | null`; it runs **only when every sync validator passes**, sets the status to **`PENDING`**, and is **unsubscribed when the next value arrives** (the same cancellation as `switchMap`, link 23 §1). Debouncing therefore lives inside the validator (`timer(ms)` before the request): a cancelled timer never reaches the server. With one async validator the first emission decides; with several they are joined with `forkJoin`, which needs every Observable to complete. Analogy: a fact-checker who drops the article you just replaced and only phones the source after you stop typing for a moment. Diagram: `stateDiagram-v2`: `VALID`/`INVALID` (sync) → sync passes → `PENDING` → emission → `VALID` or `INVALID`; `PENDING` → new value → cancel → `PENDING` again. **What to notice:** a sync failure skips the async step entirely.
- **Mechanism:** F13 (the run: statuses, the three calls, the two teardowns; the debounced validator calling the server once), read from the source: `updateValueAndValidity` → `_cancelExistingSubscription()` → sync validators → `_runAsyncValidator` only when `VALID` or `PENDING` (internal); F14 (one validator: first emission; two: `composeAsync` with `forkJoin` waits for completion; the docs line versus the run, C5: "make it complete"); `updateOn: 'blur'` as the other cost cut (forward link §7, F13 docs line); the `AsyncValidator` interface and `NG_ASYNC_VALIDATORS` for directives (typings, one sentence); debounce operators are 22's (link 22 §8, Q22.30); `HttpClient` is 27's (a fake service here).
- **First-use definitions:** async validator, `AsyncValidatorFn`, `PENDING`, cancellation (unsubscribe), debounce inside a validator, `forkJoin` (link 22 §7), `NG_ASYNC_VALIDATORS`.
- **Verification:** `section-6-async-validators.spec.ts` (fake timers): `Section 6: async validators wait for the sync validators to pass` (F13), `Section 6: a new value cancels the running async validator` (F13 teardown log), `Section 6: the control is PENDING while the async validator runs` (F13), `Section 6: a timer inside the validator sends one request per pause` (F13 debounce), `Section 6: one async validator settles on its first emission` (F14), `Section 6: two async validators wait for both to complete` (F14).

### 7. Status, `updateOn`, `valueChanges` and the unified `events` stream · delta 900 · SEC-M25-07
- **Problem:** a summary panel subscribed to `valueChanges` shows stale totals because it reads the parent's value; a "save" indicator misses `touched` changes; a zoneless page shows the old value after `setValue` from a service while the input already shows the new one; a validation that runs on every keystroke floods a slow rule.
- **Model:** every control has a **status** (`VALID`, `INVALID`, `PENDING`, `DISABLED`) and three interaction flags (**pristine/dirty**: changed by the user; **touched/untouched**: blurred). `updateOn` (`'change'`, `'blur'`, `'submit'`) decides **when the view writes to the model**. Changes are announced by `valueChanges`, `statusChanges` and, since v18, by one **`events`** stream of typed events (`ValueChangeEvent`, `StatusChangeEvent`, `PristineChangeEvent`, `TouchedChangeEvent`, `FormSubmittedEvent`, `FormResetEvent`) with a `source`. A value change runs **bottom-up**: the child updates and emits, then the parent recomputes and emits. **Status, pristine, touched and submitted are backed by internal signals; `value` is not.** Analogy: a relay race: the child runs its leg and shouts its time before the parent's stopwatch has moved.
