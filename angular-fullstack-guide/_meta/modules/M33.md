### 1. Threat model of an Angular single-page app · delta 850 (750 + 100 verification paragraph) · SEC-M33-01 (Opus)

### 2. XSS and Angular's template model · delta 700 · SEC-M33-02
- **Problem:** a search page echoes `?q=` into the page by `nativeElement.innerHTML`; a directive renders reviews with `Renderer2.setProperty(el, 'innerHTML', …)` "because the renderer is safe"; a CMS team wants to ship templates as strings and compile them in the browser.
- **Model:** **XSS** (cross-site scripting) runs attacker-supplied script in your page; **stored** (saved on the server, served to others), **reflected** (echoed from the request), **DOM-based** (the page's own script moves untrusted data into a dangerous sink; OWASP's definitions, dated). Angular treats **templates as code and values as data**: `{{ }}` and `[textContent]` create text, so markup in a value stays text; HTML only enters through an HTML-context binding, which is sanitized (§3). The holes are **paths around the template**: `nativeElement`, `Renderer2` (typings: no extra security, 14 §1), `document.write`, `eval`/`new Function` (13's exercise pointer), third-party DOM libraries, run-time compiled templates (12 §7), and `bypassSecurityTrust*` (§4). A **sink** is an API that turns a string into markup or code (09 §8). Analogy: a mail room that opens every parcel addressed through reception, and a side door nobody watches. Diagram: `flowchart TB`: `"untrusted value"` → `"template binding"` → `"text node or sanitized HTML"`; `"untrusted value"` → `"nativeElement / Renderer2 / eval / JIT"` → `"no Angular check"`. **What to notice:** Angular guards one road; the others are yours.
- **Mechanism:** interpolation compiles to text instructions that set a text node's value (12 §8, linked); template injection: an AOT app compiles templates at build time, so braces in served HTML are not evaluated (probe first), while JIT plus user strings executes them (F17 "AOT template compiler"; 12 §7); server-side templating that writes user input into the page (F17 "Server-side XSS protection"); **read from the `@angular/platform-browser` 22.2.1 source** (`_dom_renderer-chunk.mjs`, `setProperty` of the default renderer, internal) as the reason `Renderer2` writes `innerHTML` unsanitized (it assigns the property directly). Link 13 §2 and 14 §1 once each.
- **Callouts:** optional *Coming from the backend* (C3: Thymeleaf).
- **First-use definitions:** stored, reflected and DOM-based XSS, sink, template injection, payload.
- **Verification:** `labs/angular/src/app/modules/33-security/concepts/section-2-template-model.spec.ts` (`ng test`): `Section 2: interpolation renders markup as text`, `Section 2: an [innerHTML] binding removes the script and the event handler`, `Section 2: Renderer2.setProperty writes innerHTML without sanitizing`; `labs/e2e/tests/33-security/concepts/section-2-template-model.spec.ts` (page `/m33/xss/sinks?q=` added by SEC-M33-02: four regions rendering `q` by interpolation, `[innerHTML]`, `[textContent]` and `nativeElement.innerHTML` in `afterNextRender`; payload `<img src=x onerror="window.__m33Hits=(window.__m33Hits||0)+1">`): `Section 2: only the direct innerHTML write runs the injected handler`, `Section 2: interpolation braces in the served HTML are not evaluated` (probe first; the route's server module serves a variant of the shell with `{{ 7 * 7 }}` in a paragraph outside the root, asserted as literal text).

### 3. Sanitization by security context · delta 750 · SEC-M33-03

### 4. `DomSanitizer` and `bypassSecurityTrust*` · delta 700 · SEC-M33-04
- **Problem:** a team adds a `safeHtml` pipe that calls `bypassSecurityTrustHtml` on CMS content to keep inline styles; a video page concatenates a user-pasted URL into an embed URL and trusts it; nobody can find where a bypass was introduced.

### 8. Where the token lives: memory, Web Storage, `HttpOnly` cookies and a backend-for-frontend · delta 750 · SEC-M33-08 (Opus)
- **Problem:** an XSS payload reads the access token from `localStorage` and sends it away; the team moves it to memory and users are logged out on every reload; a refresh token sits in `localStorage` for months.
- **Model:** ask two questions of every option: **can injected script read it** (and take it elsewhere)? **can injected script use it** while the page is open? **Memory** (a signal in a service): not in any store, lost on reload, still reachable by script that wraps the app's requests (probe); **`localStorage`/`sessionStorage`**: readable by any script on the origin (09 §7); **`HttpOnly` cookie**: unreadable, but attached automatically, so usable by injected script and exposed to CSRF (§9); **backend-for-frontend (BFF)**: no token in the browser, a session cookie to a server that holds the tokens (42 builds it). The matrix (a Markdown table in the section): rows = options, columns = readable by XSS, usable by XSS, survives reload, CSRF exposure, needs a server. Analogy: house keys in your pocket, under the mat, with the doorman, or with a concierge who opens doors for you. Diagram: `flowchart TB` decision: `"must survive reload?"` → `"server session available?"` → `BFF` / `"memory + HttpOnly refresh cookie"`; `"any script-readable store"` → `"exfiltration risk"`. **What to notice:** no option stops script running in the page from acting as the user; options differ in theft and lifetime.
- **Mechanism:** 09 §6-§7 (attributes and stores, linked), 27 §7 (attaching tokens, linked), the IETF browser-apps draft and OWASP guidance (C6, dated), 42 for flows; **read from the `@angular/common` 22.2.1 source**: `FetchBackend` maps `withCredentials` to `credentials: 'include'` (private) as the reason a cookie rides a cross-origin API call only when asked, and how the backend obtains `fetch` (probe input for the in-memory test, C4).
- **First-use definitions:** access token, refresh token (link 27 §7), exfiltration, backend-for-frontend, session cookie, JWT (one clause; link 42).
- **Verification:** `labs/e2e/tests/33-security/concepts/section-8-token-storage.spec.ts` (pages `/m33/tokens/local`, `/memory`, `/cookie` added by SEC-M33-08; server module `08-tokens.mjs`: login issuing a token or an `HttpOnly` session cookie, `GET /api/m33/tokens/me`; "injected script" = `page.evaluate`): `Section 8: injected script reads a token kept in localStorage`, `Section 8: injected script cannot read an HttpOnly session cookie`, `Section 8: injected script can call the API with the HttpOnly session cookie`, `Section 8: a token kept in memory is gone after a reload`, `Section 8: injected script captures an in-memory token from the app's next request` (probe first, C4: the run decides the title's claim).
- **Questions drilled:** Q33.21, Q33.22, Q33.23; Exercise 33.4.
- **Misconceptions:** "a token in memory is safe from XSS" (cause: it is in no store; injected script can wrap the app's requests, probe); "`sessionStorage` is safer than `localStorage` against XSS" (cause: it is per tab; same-origin script reads both, 09 §7); "a BFF removes the need for CSRF protection" (cause: there is no token in the browser; the session cookie is now the ambient credential, §9); "a JWT's contents are secret" (cause: it looks opaque; a signed JWT is base64url text anyone can decode, RFC 7519, dated).

### 9. CSRF in single-page apps · delta 700 · SEC-M33-09
- **Problem:** §8's move from a bearer header to a session cookie reopens CSRF; the backend never checks `X-XSRF-TOKEN`, so Angular's header protects nothing (27 §8); a JSON API is assumed CSRF-proof because "browsers preflight JSON".
- **Model:** CSRF needs an **ambient credential**, one the browser attaches by itself (cookies, HTTP auth, client certificates). An API authenticated by an `Authorization` header that script sets is not CSRF-prone (it is XSS-prone instead). With cookies, layer: **`SameSite`** (the browser's rule, 09 §6), a **token check** (cookie-to-header, Angular sends the header, 27 §8; the server must compare), **Fetch Metadata and `Origin` checks** (`Sec-Fetch-Site`, F14), and **no state change on GET**. **XSSI**: a JSON response loaded as a script by another site; `HttpClient` strips the `)]}',` prefix servers can add (F13). Analogy: a bank that accepts any cheque signed with your stamp versus one that also wants your PIN. Diagram: `sequenceDiagram`: `"attacker page (127.0.0.1)"`, Browser, API: `"form POST"` → `"cookies per SameSite"` → `"Sec-Fetch-Site: cross-site, no X-XSRF-TOKEN"` → `"403"`; `"app POST with X-XSRF-TOKEN"` → `"200"`. **What to notice:** the server's check decides; the browser's rules only reduce what reaches it.
- **Mechanism:** F14 (run, re-asserted), F13, F17 (docs XSRF and XSSI), Fetch Metadata (W3C spec or web.dev, dated), 27 §8 linked for which requests carry the header (never retold), 42 file-level for Spring's `CookieCsrfTokenRepository` (one sentence); **read from the `@angular/common` 22.2.1 source**: the XSSI regex in both backends (F13) as the reason an Angular client can read prefixed JSON that a `<script>` include cannot run.
- **First-use definitions:** ambient credential, Fetch Metadata, `Sec-Fetch-Site`, `Origin` check, XSSI.
- **Verification:** `labs/e2e/tests/33-security/concepts/section-9-csrf.spec.ts` (page `/m33/csrf/bank` with an `HttpClient` POST added by SEC-M33-09; server module `09-csrf.mjs`: login setting the four cookies of F14 plus `XSRF-TOKEN`, `POST /api/m33/csrf/transfer` that logs cookies and headers and requires the header, attacker pages on `127.0.0.1`, `GET /api/m33/csrf/xssi` answering `)]}',\n{"ok":true}`): `Section 9: a cross-site form post carries only the None cookie and the cookie without SameSite`, `Section 9: a cross-site no-cors fetch carries only the None cookie`, `Section 9: the forged request arrives with Sec-Fetch-Site cross-site`, `Section 9: the app's own post carries the XSRF header and is accepted`, `Section 9: the forged post without the header is rejected`, `Section 9: HttpClient strips the XSSI prefix before parsing JSON`.
- **Questions drilled:** Q33.24, Q33.25; Exercise 33.3; links Q27.26 once.
- **Misconceptions:** "`SameSite=Lax` makes CSRF tokens unnecessary" (cause: browsers default to `Lax`; a cookie without the attribute rode a cross-site `POST` in the lab, `None` cookies ride every request, and same-site subdomains count as same site, 09 §6); "JSON APIs are CSRF-proof" (cause: a JSON `Content-Type` triggers a preflight; a form or no-cors `fetch` with `text/plain` needs none, so the server must check the content type and the token); "CORS stops CSRF" (cause: CORS errors appear in the console; CORS hides responses, it does not stop the request, [Q09.12](../../modules/09-web-networking-storage-security.md#q09-12)); "bearer-token APIs need XSRF tokens" (cause: habit from cookie apps; there is no ambient credential, so the risk is XSS, §8).

### 10. Route guards are UX: authorization belongs on the server · delta 550 · SEC-M33-10
- **Problem:** an admin area hidden behind `canMatch`; a user sets a flag in `localStorage` and sees the admin screens; the admin chunk is fetched by URL; the API answers because "the guard already checked".
- **Model:** everything in the bundle and every decision in the browser is advisory: guards, hidden buttons and disabled fields shape **UX**; **authorization** happens on the server for every request (who are you: 401; may you: 403; 09 §1). Analogy: a "staff only" sign versus a locked door. Diagram: `flowchart LR`: `user` → `"router guard (UX)"` → `"admin page or redirect"`; `user` → `"API: authenticate + authorize"` → `"200 / 401 / 403"`; `user` → `"GET chunk-*.js"` → `"static file (public)"`. **What to notice:** the guard sits on only one of three paths.

### 11. Dependency and supply-chain security · delta 700 · SEC-M33-11
- **Problem:** a transitive package publishes a malicious version that runs a script at install; CI installs whatever the ranges allow that morning; a script tag served from another host is altered.
- **Model:** a chain of trust from registry to browser, with a check at each hop: the **lockfile** pins every package's exact version and **integrity hash** (`sha512`); **`npm ci`** installs exactly the lockfile and fails if it disagrees with `package.json`; **install scripts** run arbitrary code at install (`ignore-scripts`); **release-age delays** (`min-release-age`, `before`) skip versions published too recently; **`npm audit`** reports known advisories and **`npm audit signatures`** verifies registry signatures and provenance; **Subresource Integrity (SRI)** makes the browser refuse a script whose hash differs from the `integrity` attribute (the CLI's `subresourceIntegrity` option, F12). Keeping Angular current (its support policy, dated) belongs here. Analogy: a sealed shipping manifest, a seal check at each warehouse, and a final check at the shop door. Diagram: `flowchart LR`: `registry` → `"lockfile (version + sha512)"` → `"npm ci"` → `"install scripts?"` → `build` → `"index.html integrity=sha384"` → `browser`. **What to notice:** each check covers one hop; none covers what the package author published on purpose.
- **Mechanism:** F18 (npm docs read from the shipped files), F12, the SRI spec (W3C, dated) for hash format, the lockfile's shape (tested), the security fixes in the 21.x-22.x CHANGELOGs (F16) as the reason to update (versions read), at most two incidents per C6; **read from the `@angular/build` 22.2.1 source**: where the builder adds `integrity` attributes and the import map (the task finds it by `grep -rn subresourceIntegrity`, names the file and function) as the reason lazy chunks are covered too (probe).
- **First-use definitions:** lockfile, integrity hash, `npm ci`, install script, release-age delay, advisory, provenance, SRI, transitive dependency.
- **Verification:** `labs/ts-js/src/modules/33-security/section-11-supply-chain.test.ts`: `Section 11: every package in the labs/angular lockfile pins a version and a sha512 integrity hash` (exceptions as the run shows, C4), `Section 11: an SRI hash changes when one byte of the file changes`; `labs/e2e/tests/33-security/concepts/section-11-supply-chain.spec.ts`: `Section 11: the built index.html carries integrity attributes that match the served scripts`, `Section 11: a tampered main bundle is refused and the app does not boot` (`page.route` alters the body; the console error text from the run).
- **Questions drilled:** Q33.27, Q33.28.
- **Misconceptions:** "a clean `npm audit` means the dependencies are safe" (cause: zero findings looks like a pass; it knows only reported advisories, not a malicious version published this morning); "exact versions in `package.json` pin everything" (cause: the top level looks pinned; transitive ranges float without a lockfile and `npm ci`, F18); "SRI protects against a compromised npm package" (cause: "integrity" sounds total; SRI checks that the browser got the files you built, not what you built from); "lockfiles are only for reproducibility" (cause: they are introduced as such; their integrity hashes also refuse a swapped tarball, F18).

### 12. Under the hood: from a template binding to a sanitized DOM write · delta 650 · SEC-M33-12 (Opus)
- **Problem:** an interviewer asks how Angular knows that `[href]` needs URL sanitization and `[title]` does not, when the check runs, and why the HTML sanitizer parses its input more than once.
- **Model:** decided at compile time, run at update time. The **compiler** looks up `(element, property)` in the security schema (F2) and emits the property instruction with a sanitizer function reference (`ɵɵproperty('href', ctx.url, ɵɵsanitizeUrl)`, F3); static attributes become trusted constants. At **run time**, each time the binding's value changes, the instruction calls the sanitizer: a custom `Sanitizer` if one is provided (`DomSanitizerImpl` in browser apps), else the built-in functions; HTML goes through an **inert document**, is re-parsed until stable (**mutation XSS**: markup that changes meaning when re-parsed, F4), serialized from allowlists and wrapped by the `angular` Trusted Types policy (F9). Diagram: `flowchart TB` with subgraphs `compile` (`"template"` → `"schema lookup"` → `"ɵɵproperty + sanitizer ref"`) and `run` (`"value changes"` → `"sanitizer"` → `"inert doc parse x≤5"` → `"allowlist serialize"` → `"TrustedHTML"` → `"DOM write"`). **What to notice:** no binding pays for sanitization unless the schema says its context needs it.
- **Mechanism:** read from `@angular/compiler` 22.2.1 (`SECURITY_SCHEMA`, `DomElementSchemaRegistry.securityContext`, where the template pipeline attaches the sanitizer; found by `grep`), `@angular/core` 22.2.1 (`ɵɵproperty`, `getSanitizer`, `ɵɵsanitize*`, `_sanitizeHtml`, `SanitizingHtmlSerializer`, clobbering checks) and `@angular/platform-browser` 22.2.1 (`DomSanitizerImpl` as the `Sanitizer`), each file and function named, a few lines of pseudo-code (C8). Link 12 §8 for instructions in general.
- **First-use definitions:** security schema, sanitizer function reference, inert document, mutation XSS, DOM clobbering.
- **Verification:** `labs/angular/src/app/modules/33-security/concepts/section-12-under-the-hood.spec.ts` (`ng test`): `Section 12: the compiled template passes a URL sanitizer with an href binding` (probe first, C4), `Section 12: the compiled template passes no sanitizer with a title binding`, `Section 12: the sanitizer runs again when the bound value changes` (a spy-free check: the second value is sanitized too); anything the probe cannot inspect is "read, not run".
- **Questions drilled:** Q33.29.
- **Misconceptions:** "sanitization happens once, when the component is created" (cause: constructor-time thinking; each change of the bound value runs it, tested); "Angular strips tags with regular expressions" (cause: older sanitizers did; it uses the browser's parser in an inert document, read); "static attributes in a template are sanitized like bindings" (cause: they look alike; static values are compile-time constants the developer wrote, read).
